tool_search 評価レポート

出番の限られるツールを検索して読み込む tool_search が、ツールの数・言語・言い換えに対してどこまで正しく当てられるか。製品の BM25F、Ruri v3 埋め込み、両者の RRF 融合、cross-encoder の再順位付けを、1,003 ツールの合成カタログで比べた。

カタログ 1,003 ツール（実 13 ＋ 合成 990・45 サービス） 評価クエリ 592（正解 148 × 4 種） skill 493・依頼 60 LLM qwen3.6-plus（推論なし） 埋め込み ruri-v3-30m・reranker japanese-reranker-xsmall-v1

結論

    E1 · 規模

    ツールが増えると BM25 は落ちる

    カタログをサービス単位で増やしたときの R@5（正解が上位 5 件に入る率。製品は 5 件を読み込む）。横軸は対数で、各点はサービスの境界（実ツール 13 件のあと合成サービスを 1, 2, 4, … 個足した時点）。RRF ＋ reranker は CPU で 1 クエリ 3 秒以上かかるため、全カタログでだけ測った。

    規模が大きいほど評価クエリも増える（N=13 では実ツールの 52 件、N=1,003 で 592 件）。製品の相対カットオフは 0.25 だと小さいカタログで正解を落としていた（N=13 で 90.4% → 86.5%）ため 0.1 に下げた（#518）。現在は N=13 で打ち切り前 %・製品が読み込む 5 件 %。

    評価クエリを固定して妨害ツールだけを増やしても、同じ形で落ちる（N=148 → 1,003 で BM25 R@5 は 、RRF は ）。劣化は候補の数そのものによる。

    E3 · 言語と言い換え

    英語の説明 × 日本語の依頼で BM25 は崩れ、埋め込みが救う

    全カタログ（1,003 件）での R@5。外部の MCP ツールは英語の説明が多く、利用者は日本語で頼むので、この組み合わせは実運用で起きる。agent は依頼文からモデルが tool_search に渡しそうな検索語を作ったもので、実運用の入力に最も近い。

    言い換え（ja_para：ツールの語を避けた口語）は、どの方式も 4 割に届かない。語彙のずれは検索だけでは埋まらず、モデルが検索語を言い直すこと（agent の行）に頼っている。

    正解の一意性

    正解が一意な依頼に限ると、RRF は BM25 より 7 ポイント上

    サービス名を含まない依頼（「プロジェクトのチャットに送って」）は、別サービスの同等ツールでも満たせるため正解が一意でない。依頼文がサービスを名指ししているもの（と製品の実ツール）を「一意」として分けた。

    E4 · 読み込み件数

    5 件読み込みで 1 件あたり約 130 トークン、k を増やすほど逓減する

    全カタログ・全クエリ。括弧内は読み込む定義の平均トークン（UTF-8 4 バイト ≒ 1 トークンの近似）。
    融合の調整

    RRF の k は 60 より 10、埋め込みには名前と引数まで渡す

    全カタログでの R@5（各セルは「全クエリ / 一意な依頼」・重み 1:1）。k が小さいほど各方式の上位を重く見る。crates/rag の既定 k=60 は文書検索向けで、ツール検索では上位の一致を薄めすぎる。特に英語の説明では BM25 がほとんど当たらず、k=60 だと融合が埋め込み単体を下回る。

    E5 · コスト

    検索 1 回のコスト

    tool_search の説明に載る「検索できるツール」の文字数。100 件までは名前の一覧で件数に比例して伸び、超えると名前空間ごとの件数の要約に切り替わる（#519。切り替え前は 1,003 件で 24,461 字）。
    E2E · LLM に選ばせる

    tool_search は入力トークンを大きく減らすが、聞き返して終える会話が増える

    正解ツール 30 件 × 日英の依頼 60 件（1,000 件の規模は全条件で同じ 30 件）。全ツールを提示する場合と、tool_search だけを提示して読み込ませる場合を比べた（読み込みは OpenAI 互換アダプタと同じく定義を末尾に追記）。正解以外のツールにはモックの結果を返して会話を続け、6 ステップ以内に正解ツールを呼べたかで判定した。入力トークンは会話全体の合計。tool_search の結果本文は、製品の文面（CatalogSearch::loaded_message・本文の比較はこちら）と、評価側の簡略版（読み込んだ名前だけ・初回の計測）の 2 通りで測った。

    どのツールも呼ばずに終えた会話を 12 件抜き取って同じ条件で再生すると、11 件はチャンネル ID・カード ID・ファイルの中身などの不足を利用者に聞き返して終えていた（全ツール提示 4 件・tool_search 8 件。残る 1 件は再生では別のツールを呼んだ）。聞き返し自体は全ツールを提示した場合にも起き、ID を調べられる一覧・検索系のツールが提示されていても起きている。tool_search の条件で多い理由は、この評価では切り分けていない（読み込まれる 5 件に下調べのツールが入らないこと、検索で 1 往復増えることなどが考えられる）。

    E2E · 聞き返しの切り分け（#545）

    1,000 件の tool_search で下がる正解率の大半は、ID を調べるツールを読み込まずに聞き返すため

    正解ツールを呼ばずに文章で終えた会話（一覧・検索のツールを呼んでから終えたものを含む）を、「避けられた聞き返し（その会話のカタログにあるツールで調べられる ID などを聞いている）」「正当な聞き返し（宛先・本文・保存先など、カタログのツールでは得られない情報を聞いている）」「その他（別サービスの同等ツールで済ませた・別のツールで終えた）」に分けた。

    主要な比較（1,000 件・同じ 30 件の依頼・現行の system prompt・目視で分類）

    system prompt とツールの応答を変えた比較（LLM による分類）

    system prompt は、評価の現行（1 行）、製品の通常チャット、現行に「利用者に尋ねる前にツールで調べる」を足したもの、の 3 通り。ツールの応答は、一律の文面（「該当の項目」）と、依頼に沿った内容を LLM で作ったもの、の 2 通り。分類は LLM で行い、「避けられた」は挙げたツールで本当に調べられるかを別の呼び出しで検算した。検算の前は「避けられた」を多く、検算の後は少なく見積もる（主要な比較の目視では 5 件のところ 2 件）ので、この表の「避けられた」は下限として読む。値は全会話に対する割合で、「正解ツール」から「未判定」までが終わり方の内訳（足すと 100%）。「正解＋正当」と「下調べしてから終えた」は参考の列。

    • 正当な聞き返しが多い。依頼文に宛先・本文・保存先・日付が無いもの、カタログに ID を引く一覧・検索ツールが無いものが多い。E2E の正解率の絶対値が低い主な理由で、依頼データを作り直した（#547・次の節）。
    • 製品の system prompt は正解率を下げる。全ツール提示 200 件で 60.0% → 48.3%、tool_search で 200 件 46.7% → 36.7%、1,000 件 20.0% → 10.0%。
    • 「調べてから尋ねる」指示は正解率を上げない。60.0% → 45.0%（全ツール提示 200 件）、46.7% → 40.0%（tool_search 200 件）、20.0% → 13.3%（1,000 件）。一覧・検索のツールを呼ぶ会話は増える（全ツール提示 200 件で 3.3% → 16.7%）が、そのあと得られない情報（相手のメールアドレス・本文など）を聞いて終える。
    • 依頼に沿ったモックにしても大きくは変わらない。一律の文面との差は正解率で 0〜3 ポイント程度。
    • 製品は今日の日付を system prompt に入れていなかった。「来週の金曜」などの依頼は日付を決められずに聞き返していた（#546 で対応）。
    E2E · 依頼データ v2（#547）

    必要な値が揃う依頼では全ツール提示はほぼ満点、1,000 件の tool_search だけが 1 割落ちる

    依頼を作り直した。依頼文と一緒に正解ツールまでの手順（呼ぶツールと引数）を出させ、必須引数がすべて「依頼文に書かれた値」か「その会話のカタログにある一覧・検索・取得のツール」で埋まることを機械的に検査した。宛先・本文・日付など、ツールで得られない値は必ず依頼文に書く。ID は、カタログのツールで調べられるものだけを依頼文から省いた（書いていたら作り直させた）。カタログの規模で調べられるものが違うので、依頼は規模ごとに作った（200 件は正解ツール 30 件 × 日英、1,000 件は 15 件 × 日英）。system prompt には固定の今日の日付を入れ、ツールの応答は依頼に沿ったモック、応答の上限は 10 回にした。さらに、ツールでは得られない必須の値をわざと 1 つ書かない依頼を、200 件に 8 件、1,000 件に 4 件混ぜた。前の節までの E2E とは依頼もモックも違うので、数値は比べられない。

    • 外した会話（1,000 件の tool_search の 3 件・目で分類）。Figma のファイルキーを尋ねた（figma_search_files で調べられる・避けられた聞き返し）、「outlook」だけで検索して削除のツールを読み込めず「機能が無い」と答えた、一覧の応答に詳細が含まれていたのでそれで答えた、の 3 件。
    • 評価の不具合を直した。検索せずに提示されていないツール名（gdrive.files.create など）を呼ぶと、評価は成功のモックを返していた。製品は unknown tool のエラーを返すので、それに合わせた（その名前を呼んだ会話だけ取り直した）。直すと、200 件の tool_search で外していた 1 件は、検索し直して正解した。前の節までの E2E（旧データ）は直す前の結果で、tool_search の条件ごとに 0〜3 件、この形の会話を含む（全ツール提示には無い）。
    • 情報が足りない依頼では、どちらの条件でも尋ねずに正解ツールを呼ぶことが多い。「通知先は社内の標準エンドポイント」「本文はいつものテンプレート」のような依頼で起きる。ただし、値を作ったのか、別サービスのツールで調べたのか（「担当者に確認済みのメールアドレス」をメール検索で探す、「田中さん」を Slack のユーザー検索で探す、など）、引数を省いたのかは、この結果では区別できない（呼んだ引数を記録していなかった。以後は記録する）。差は条件の間より依頼の書き方で大きく、件数も少ないので、ここから tool_search の良し悪しは読まない。
    • 揺れ。temperature 0 でも、同じ依頼を回し直すと 1,000 件の tool_search の正解は 30 件中 1 件動いた。数ポイントの差は読めない。
    skill

    先頭 50 件で切る一覧は 200 件で崩れ、skill 専用の検索は約 500 件でも 9 割を保つ

    製品の skill ツールは説明に name: description を一覧し、name 順の先頭 50 件で切る。上限なしの一覧、skill 専用の検索（製品の BM25F・説明は名前を持たない固定文）、名前一覧を説明に載せた検索と比べた。

    LLM が正解の skill を読み込めた率。N=20 は依頼 10 件、N=50 は 25 件、N=100 は 50 件、N≥200 は 60 件。

    比較の限界: 検索方式の skill ツールには「名前が分からなければ先に skill_search で探すこと」と書いてあり、一覧方式には読み込みを促す同等の文が無い。一覧方式で読み込み自体が少ないのは、この文言の差も含む。件数による差（先頭 50 件の一覧が N≥200 で崩れること、上限なしの一覧のトークンが件数に比例して伸びること）は、この差とは別に読める。製品は上限を超えたときに一覧（先頭 50 件）と skill_search を併せて出す構成で、この組み合わせそのものは測っていない。

    方法と限界

    どう測ったか

    • BM25F は製品のコードそのもの（agent_core::CatalogSearch と順位 CLI）。埋め込み・reranker はプレビュー環境の ingestion-worker を製品と同じ契約で呼んだ。
    • 合成カタログは 45 の業務 SaaS（GitHub・Slack・freee・SmartHR・kintone など）について MCP 風のツールを LLM に作らせ、説明と引数を日英で持たせた。
    • 依頼文は、同じサービスの紛らわしい近縁ツールを見せたうえで「正解ツールでしか満たせない」ものに限定して生成した。ツール名がそのまま含まれる依頼は 0 件。
    • 限界: データは LLM 生成で、生成と E2E が同じモデル。E2E は推論トークンを止めて回した。実ツールは dev 構成で配線された 13 件だけ。Anthropic の tool_reference 経路は実 API で測っていない。
