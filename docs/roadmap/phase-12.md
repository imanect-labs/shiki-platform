# Phase 12 — SaaS アルファ運用（管理・フィードバック・IaC・消去/DR）

> 目的: プライベートアルファを**顧客に配れる運用体制**を完成させる。
> 管理ダッシュボード2枚（顧客管理者／ベンダーコンソール）・フィードバック（二段同意）・ヘルプ・
> IaC（OpenTofu プール環境）・テナント消去機構・バックアップ/DR・API レート制限（design §4.12）。
> 完了の定義(DoD): 「契約 → ベンダーコンソールからテナントプロビジョニング（フルプールへの論理登録）→ 顧客管理者がメンバー/モデル/予算を設定 →
> 利用 → フィードバックが Imanect に届く → 解約で消去証明が出る」が一気通貫で回る。
> サポートアクセスは break-glass のみで、サイレントアクセスの経路が存在しないことをテストで担保する。
>
> ⚠️ **着手前に [設計上の落とし穴](../design-caveats.md) の PIT-26〜28（共有プレーンの blast radius・利用量整合）・
> PIT-38（バックアップの整合スナップショット）を確認すること。**

## 詳細

### Task 12.1: モデルカタログ管理
- **area**: api / **path**: `crates/llm-gateway`, `crates/api`
- **仕様**: テナント管理者が許可モデルリスト・既定モデル・モデル別単価（課金単価表と同居）・
  国外処理バッジ・予算上限（org/ユーザー/アプリ別）を管理。ユーザーのモデル選択 UI と思考強度3段階はカタログ範囲内。
- **受け入れ条件**:
  - [ ] 許可外モデルの指定が API レベルで拒否される
  - [ ] 予算上限到達で該当スコープの呼び出しが抑制され通知される
  - [ ] 国外処理モデルにバッジが表示される

### Task 12.2: 顧客管理者ダッシュボード
- **area**: frontend / **path**: `web/`
- **仕様**: 使用量（トークン/コストを org・ユーザー・アプリ・ワークフロー別）・監査ログビューア＋エクスポート・
  組織ポリシー（フィードバック本文添付可否等）・プラン/請求（Stripe カスタマーポータル）。統一シェル＋
  マイクロフロントエンド（SK.6）に載せ、オンプレは単独動作。
- **受け入れ条件**:
  - [ ] 使用量が SAAS.3 の会計と一致して表示される
  - [ ] 監査ログを期間/種別で絞ってエクスポートできる
  - [ ] オンプレ構成で共有プレーン なしに単独動作する

### Task 12.3: 同意・委譲の棚卸し UI
- **area**: frontend / **path**: `web/`
- **仕様**: ワークフロー委譲（委譲者・スコープ・状態）・skill インストール・secret 利用許可を一覧・失効。
  fail-closed 停止中のワークフローと再同意導線。
- **受け入れ条件**:
  - [ ] 管理者が全委譲を一覧し任意に失効できる
  - [ ] 失効が次回実行前に効く（監査に残る）

### Task 12.4: ベンダーコンソール
- **area**: infra / **path**: 共有コントロールプレーン, `web/`
- **仕様**: テナントライフサイクル（プロビジョニング・停止・解約）・プラン/サブスク・テナント別機能フラグ・
  全テナント横断の**集約**使用量/SLO/ヘルス。**顧客データ本文に到達する API を持たない**（構造的不能）。
- **受け入れ条件**:
  - [ ] テナント作成〜停止〜解約がコンソールから実行できる
  - [ ] コンソールのどの API からも顧客コンテンツ本文が取得できない（テストで担保）

### Task 12.5: break-glass サポートアクセス
- **area**: auth / **path**: 共有コントロールプレーン, `crates/api`
- **仕様**: 顧客管理者の明示許可→時限付きアクセス→全操作監査→顧客画面にバナー。サイレントアクセス経路なし。
- **受け入れ条件**:
  - [ ] 許可なし・期限切れのサポートアクセスが拒否される
  - [ ] アクセス中バナーが顧客側に表示され、全操作が顧客の監査ログに残る

### Task 12.6: フィードバック機構
- **area**: obs / **path**: `crates/api`, 共有コントロールプレーン
- **仕様**: 👎＋カテゴリ（「やり方がわからなかった」含む）＋run_id/trace_id を feedback ストアへ（既定は本文なし）。
  **内容の共有＝本文添付と自由記述コメントを同格の「顧客コンテンツ」として扱う**（コメント欄への会話貼り付けが
  本文添付ポリシーの迂回にならないように）: ユーザー明示チェック＋組織ポリシー許可の二重ゲート・共有事実を監査。
  組織ポリシーで禁止時はカテゴリ選択のみ（自由記述欄自体を出さない）。ベンダー側で Langfuse/監査と trace_id 突合。
- **受け入れ条件**:
  - [ ] 既定送信に会話本文・自由記述が含まれない（スキーマレベルで不能）
  - [ ] 組織ポリシーで内容共有を禁止すると本文チェックと自由記述欄の両方が UI から消える
  - [ ] trace_id でベンダー側テレメトリと突合できる

### Task 12.7: ヘルプ基盤
- **area**: frontend / **path**: `help/`, `web/`, `crates/rag`
- **仕様**: `help/`（md・リリース同バージョン）1ソース→①ヘルプセンター UI ②RAG 組み込みスコープ「shiki-help」
  （事前インデックス同梱・テナントデータと別インデックス・認可チェック不要の公開コーパス）。
  チャット doc_search が help に当たる。
- **受け入れ条件**:
  - [ ] 「◯◯のやり方」がチャットで help 由来の引用付きで返る
  - [ ] help インデックスがテナントデータと分離されている

### Task 12.8: IaC・テナントプロビジョニング自動化
- **area**: infra / **path**: `deploy/tofu/`, CI
- **仕様**: **既定はフルプール**（design §4.1）なので、テナント追加は**論理プロビジョニング**:
  ベンダーコンソール→tenant レジストリ登録・**共有 identity pool（単一 realm）内への tenant group 作成**・
  DNS・OpenFGA 名前空間・初期管理者招待（SAAS.2 の admin API と結線・インフラ変更なし・冪等）。
  **realm を新規作成するのは専用ストア（cell）契約時のみ**——既定のフルプール経路では Phase 0 で定義した
  共有 identity pool の realm を使い、テナント境界は group で表す。
  GCP は OpenTofu で記述し **環境（プール）＝モジュールのインスタンス化**とする。プール増設および
  専用ストア（cell）契約時のみ CI パイプライン→`tofu apply` を走らせる。冪等・dry-run。
- **受け入れ条件**:
  - [ ] 新規テナントがコンソール操作1回で使用可能になり初期管理者がログインできる（インフラ変更を伴わない）
  - [ ] プール環境の増設が `tofu apply` で再現可能
  - [ ] 再実行が冪等で、失敗時に途中状態から再開できる

### Task 12.9: テナント消去機構
- **area**: infra / **path**: `crates/storage`, `crates/data`, `deploy/`
- **仕様**: `purge_tenant` を全ストアへ拡張: DB 行・blob・Qdrant/Tantivy・FGA タプル・セッション・Langfuse・
  監査（削除証跡は保持）・**バックアップからの期限付き消滅**（保持期限経過で完全消滅する設計＋消滅証明の発行）。
  **フルプールでは「ストアごと捨てる」ができないため、消去の網羅性を機械で保証する**: tenant スコープを持つ
  全テーブル／全ストアの台帳を単一定義から生成し、purge 実装が欠けている対象を CI で検出して落とす
  （テーブル追加時に消去経路の実装を強制する。design §4.12）。
  **保持対象の例外を先に定義する**（「全ストアに痕跡なし」と「削除証跡は残す」は素朴には矛盾するため）:
  | 区分 | 対象 | 消去時点 |
  |---|---|---|
  | **運用データストア** | Postgres 行・blob・Qdrant・Tantivy・FGA タプル・セッション・Langfuse | 消去実行時に即時・痕跡ゼロ |
  | **保持する例外** | 監査の削除証跡（誰が・いつ・どの範囲を消したか。本文は含まない） | 消さない（法令・説明責任のため） |
  | **期限付き例外** | バックアップ内の当該テナントデータ | 保持期限の経過時に消滅。期限後に消滅証明を発行 |
- **受け入れ条件**:
  - [ ] 消去後、**運用データストア**に該当テナントの痕跡がない（検証ジョブ）
  - [ ] tenant スコープを持つ新規テーブルを purge 未実装で追加すると CI が落ちる
  - [ ] 監査の削除証跡だけが残り、その本文に顧客コンテンツが含まれない
  - [ ] バックアップ保持期限の経過後に、当該テナントデータの消滅を確認した消滅証明
        （何を・いつ・どの範囲で）が出力できる

### Task 12.10: バックアップ/DR
- **area**: infra / **path**: `deploy/`, `docs/guides/`
- **仕様**: バックアップ・復元手順・RPO/RTO 宣言。Postgres・blob・Qdrant・FGA の
  **整合スナップショット**（同一時点への復元。PIT-38: バラバラ復元は FGA タプルとデータがズレて権限事故）。
  復元リハーサルを定期実行。
  **フルプールの制約**: 共有ストアのため「1テナントだけ指定時点へ戻す」は物理 PITR では実現できない。
  ①プール全体の PITR（全テナント巻き戻し・災害時のみ）②**テナント論理エクスポート/インポートによる
  部分復旧**（整合点を明示・権限も同時に復元）の 2 経路を用意し、どちらで何が保証されるかを宣言する。

  **ストアごとの DR 方針を明示する**（12.9 の消去対象と対応させ、抜けを作らない）:
  | ストア | 方針 | 根拠 |
  |---|---|---|
  | Postgres（全ドメイン） | **スナップショット復元**（正本） | 権限・データの整合点はここが決める |
  | blob（MinIO/GCS） | **スナップショット復元** | Postgres のメタと同一時点で揃える（PIT-38） |
  | OpenFGA タプル | **スナップショット復元** | データとズレると権限事故 |
  | Qdrant / Tantivy | **再構築**（Postgres から再インデックス） | 導出データ。復元より再構築が確実かつ安価 |
  | Redis セッション | **DR 対象外**（再ログイン） | 揮発前提 |
  | Langfuse | **DR 対象外**（観測データ） | 業務データではない。欠損を許容すると宣言する |
- **受け入れ条件**:
  - [ ] プール全体を指定時点へ復元でき、権限とデータが整合する
  - [ ] 単一テナントを論理エクスポートから復旧でき、FGA タプルとデータが整合する（整合点を明示）
  - [ ] **復旧後に「再構築」対象（Qdrant/Tantivy）の再インデックスが完了し、
        復元データとの不整合（孤児チャンク・欠損）が検出ゼロであることを検証ジョブで確認**
  - [ ] **単一テナント復旧後に、他テナントのデータが混入していない／当該テナントの残存旧データが
        残っていないことを検出できる**（論理復旧特有の事故を潰す）
  - [ ] RPO/RTO が宣言値内であることをリハーサルで実証
