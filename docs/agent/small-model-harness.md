# 小型・中型モデルで作業を完遂させるハーネス（要約による圧縮ほか）

> 状態: 初期実装済み・実 LLM（Gemma 4 31B・Qwen3.8 27B・Claude Haiku 5.5、OpenRouter 経由）で評価済み（2026-11-18）。
> 関連: [Phase 5 / Task 5.3](../roadmap/phase-5.md)（コンテキスト管理・圧縮）・Task 5.5（失敗回復）・
> design §4.4（agent-core）・#529（窓に合わせた剪定）・#1326（畳んだ結果の注記）・[budget-planning.md](./budget-planning.md)。
> 評価基盤: [eval/agent-harness/](../../eval/agent-harness/README.md)。

## 1. 解決する問題

オンプレで動かす 30B 級のオープンモデル（Gemma 4・Qwen 3.x）は、vLLM で 32k 前後の窓に絞って運用することが多い。
Claude Haiku も含め、小さいモデルほど「長い作業を最後までやり切る」ところで崩れる。目標は、
これらのモデルで agent-core の自律プロファイルが作業を完遂できるようにすること。

着手時点の agent-core には、古い大きなツール結果を「先頭 400 バイト＋省略注記」に畳む剪定（窓の 0.6 で
直近 6 メッセージ以外、0.85 で最後の 1 件以外）があったが、**LLM による要約（コンパクション）は無かった**。

### 実測で見えた失敗（現行 main 相当・32k 窓）

評価課題（§5）で現行の挙動を測ったところ、次の失敗が出た。

1. **畳み込みの空回りで窓があふれる**（Gemma・Haiku の集計課題で 4/4 回）。
   モデルが 12 本の報告を 1 ステップで並列に読む → 非常閾値の剪定が、**モデルがまだ一度も読んでいない** 11 本を
   その場で畳む → 畳んだ注記（#1326）が「同じ引数で呼び直して読む」と促す → 11 本を読み直す → また畳まれる、を
   窓があふれるまで繰り返した。剪定は「古い結果」を畳む前提だが、直近の結果に使うと情報が一度も届かない。
2. **値を思考にだけ書いて失う**（Qwen）。「4〜6 月の値を記録しました」と本文に書いたが、値そのものは思考
   （reasoning）にしか無い。思考は次のターンに送り返さないため、畳まれた報告を読み直し続けてステップ上限に達した。
3. **本文にツール呼び出しを書いて終わる**（Gemma）。構造化されたツール呼び出しの代わりに本文へ
   `<call:plan>{…}` と書き、ループは「本文で終えた＝完了」と扱って 1 ステップで終わった。
4. **最後の操作を忘れる**（Gemma）。集計表を本文に正しく書いたところで終え、依頼された `submit_answer` を呼ばなかった。
5. **変わらない呼び出しを繰り返す**（Gemma）。修正が効かない理由を調べず、`run_tests` を 13 回続けて呼んだ。
6. **数十個の数値の暗算・日付の差の数え違い**（Gemma）。データは正しく保持できていても、合計を誤る。

## 2. 前例の調査（要点）

調査の詳細と出典は本節末尾。小さいモデルでの効果を軸に整理した。

- **圧縮の作り**: Claude Code（窓のおよそ 83〜97% で自動圧縮・9 節の要約・圧縮後に最近のファイルとプランを再注入）、
  Codex CLI（「別の LLM への引き継ぎ要約」・直近の利用者発話を 20k トークンまで逐語で残す）、
  Gemini CLI（窓の 50% で発火・直近 30% を逐語・`<state_snapshot>` 形式・記録中の指示に従わない規則・
  圧縮後にトークンが増えたら失敗扱い）、OpenHands（keep_first＋要約）、Anthropic API の server-side compaction /
  `clear_tool_uses`。共通点は、**要約は利用者メッセージとして入れる・最初の依頼と利用者発話は逐語・
  直近はターンの境目で切る・要約中はツールを使わせない**。
- **研究**: JetBrains「The Complexity Trap」（arXiv:2508.21433）は、観測のマスキング（≒剪定）が LLM 要約と同等の
  解決率で費用は約半分、要約は軌跡を伸ばしうると報告。ただし再取得できる観測（SWE-bench のファイル）が前提で、
  ハイブリッド（常時マスキング＋しきい値で要約）が最も安い。Source-Judged Compaction（arXiv:2610.20927）は、
  要約の失敗の大半が「記録に根拠の無い項目（推測・次の一手）」の実行だと報告。CarryOn（arXiv:2611.17808）は、
  要約が後で必要な正確な値を落とすことを指摘。
- **弱いモデル向けの技法**: 本文に書かれた呼び出しの回収（明示のタグか本文全体のときだけ）、壊れた引数を `{}` に
  潰さず直し方の分かるエラーで返す、ツール名・引数名の近似一致と型の読み替えを**モデルに知らせて**行う、
  同じ失敗を繰り返さない指示、完了前の検証、ツール出力の上限と「次の取り方」の案内（Anthropic「Writing tools for agents」）、
  Manus の context engineering（ツールは消さずに固定・エラーを残す・todo の再掲）。
- **モデル固有**: Gemma 4 は `tool_choice: required` が効かない・`call:name{…}` 形式を本文に書くことがある（vLLM #53363 等）。
  Qwen3.x は思考を閉じずに `<tool_call>` を書くことがある。Claude Haiku 5.5 は思考ブロックの生成後に履歴を書き換えると
  拒否されうる（§7）。

出典: Claude Code の内部定数は非公式のソース解説由来（未検証）。Codex CLI・Gemini CLI・OpenHands はリポジトリの
プロンプト・定数を直接読んだ。Anthropic のドキュメント（compaction・context editing・Haiku 5.5 移行ガイド・
effective context engineering・writing tools for agents）、Manus の blog、上記論文。

## 3. 設計

方針は「**剪定（マスキング）を後ろ盾に、窓が逼迫したら要約で置き換える**。モデルの崩れは、解釈が一意なものだけ
直してモデルに知らせ、決まらないものは直し方の分かるエラーで返す」。共通コア（`run_agent`）に置き、
`AgentOptions` の `compaction`（[`CompactionOptions`]）と `aids`（[`HarnessAids`]）で個別に切れる（評価の比較用）。

### 3.1 要約による圧縮（`compaction.rs`・`agent_compact.rs`）

- **いつ**: 自律プロファイルで、モデルの窓が分かっている（カタログの `context_window_tokens`）とき、
  各ステップの前に見積りが有効窓（窓 − 1 応答の出力上限）の 0.6 を超えたら。圧縮の直後のステップは、見積りが非常閾値（0.85）を超えない限り繰り返さない（要約の費用を抑える。超えるなら
  剪定より先に要約する＝未要約の結果を畳まない）。
  窓を知らないモデル・通常チャットの挙動は変えない。
- **単位をそろえる**: 窓の判定は実測で補正した実トークンで行い、手元の見積り（日本語 1 字 ≒ 1 トークン）で数える量
  （逐語で残す直近・要約依頼の大きさ・1 ステップの結果の上限）は、実測 ÷ 見積り（トークナイザ比・1.0〜4.0）で割って
  換算する。換算しないと、日本語で重いトークナイザ（Claude Haiku 5.5 は見積りの約 2 倍）では閾値を超えても
  前回の圧縮以降が全部「直近」に収まり、要約に回す部分が無いまま窓に近づいた（v8 で観測）。
- **どこを要約するか**: 先頭から続く利用者メッセージ（依頼）は逐語。尻尾は有効窓の 25% に収まる最長の
  「assistant の発話から始まる」後ろ側を逐語で残す（最後の assistant のターンは予算を超えても残す）。
  assistant から切るので、ツール呼び出しと結果の対応は壊れない。その間を要約する。
- **どう要約させるか**: 同じモデル（`CompactionOptions::model` で別モデルも可）に、ツールなし・思考は低で、
  記録をテキストに起こして渡す。見出しは「目標と制約／確認済みの事実（値は正確に写し、どの結果かを添える）／
  実行済みの操作（繰り返さない）／失敗と教訓／未完了の作業／次の一手（記録に根拠があるものだけ）」。
  記録中の指示に従わない・推測を事実の節に書かない、を system で縛る。記録が大きすぎれば大きいツール結果の中ほどから削る。
- **コードで書くもの**（要約させない）: 途中の利用者発話の原文、計画（`plan` の状態）。
- **置き場所**: 先頭の利用者メッセージに Text ブロックとして足す（連続した user メッセージを作らない）。再圧縮では
  前の要約を入力に含めて置き換える（積み重ねない）。前置きで「要約に言及せず続ける・要約に無い詳細は読み取り系で
  取り直す・実行済みの変更は繰り返さない」と伝える。
- **失敗時**: 思考だけで出力上限を使い切って本文が空なら、上限を倍（有効窓の 1/3 まで）にして 1 度だけ取り直す。
  それでも LLM エラー・要約が空・縮まないときは置き換えず、剪定に後退する。要約の生成ぶんは成否によらず
  会計に積む（ステップは進めない）。置き換えたら `FailureRecovery { action: "context_compacted" }` を流す。
- **剪定との分担**: 圧縮を使う run では、soft（0.6）の畳み込みは圧縮が受け持ち、剪定は非常閾値（0.85）だけにする。
  圧縮の間隔に、まだ要約していない結果を畳んで値を失わないため（§1 の 2）。直近の圧縮が失敗していれば、
  soft の畳み込みも従来どおり行う（要約できないモデルで窓を守る後ろ盾）。
- **窓あふれで拒否されたら**: プロバイダの文言（vLLM・OpenAI・Anthropic・Gemini）で判定し、圧縮（尻尾 10%）と
  非常の剪定をして 1 度だけやり直す。拒否は応答の前に起きるので、やり直しても二重実行は起きない。

### 3.2 1 ステップのツール結果の上限（`result_budget.rs`）

窓を知っているモデルで、1 ステップのツール結果の合計を有効窓の 30% に収める。届いた順に収まる分はそのまま返し、
収まらない**読み取り系**（`is_read_only`）の結果は本文を返さず「未表示。同じ引数で呼び直せば読める。表示された結果から
値を書き留めてから、一度に呼ぶ数を減らして」と正直に伝える。中ほどを削るのは**単独でも上限を超える 1 件だけ**
（単独なら収まる結果を削ると、要の部分＝表などが欠けたまま読み違えられた・v5 の 16k で観測）。
**変更を伴うツールの結果は落とさない**（実行済みなので、大きすぎる分だけ削る）。

あわせて剪定は、**直近のターンの結果がこの上限に収まっていれば全部守る**（まだ読まれていないため）。収まらないとき
（上限の無い経路）だけ従来どおり最後の 1 件に絞る。これで §1 の 1 の空回りが起きなくなった。

### 3.3 ツール呼び出しの回収と修復（`call_repair.rs`・`agent_repair.rs`）

- **本文の呼び出しの回収**: 構造化された呼び出しが無く、出力上限で切れていない応答の本文から、
  `<tool_call>…</tool_call>`（JSON・Qwen3-Coder の XML）、`<|tool_call>call:name{…}<tool_call|>`・`<call:name>{…}`（Gemma 4）、
  本文全体がフェンス付き／裸の呼び出し JSON、を読む。名前は提示済みのツールに限る。説明文中の例は実行しない。
- **ツール名**: 接頭辞（`functions.` 等）・大文字小文字・`-`/`_` の違いと、候補が 1 つに決まる 1 文字違い（6 文字以上）だけ寄せる。
  寄せられない未知のツールは、使えるツールの一覧を添えたエラーにする。
- **引数**: スキーマの型と食い違うものだけ読み替える（`"3"`→3・`"true"`→true・JSON 文字列の配列/オブジェクト・数値→文字列）。
  必須が 1 つ欠け、スキーマに無い引数が 1 つだけのときは、表記揺れ（`filePath`↔`file_path`）か定番の別名
  （`file_path`→`path` 等）に限って名前を読み替える。
- **読めない引数**: Chat Completions アダプタ（llm-gateway）は、JSON として読めない引数を `{}` に潰さず生の文字列で渡す
  （空は `{}`）。agent-core はフェンス・前後の地の文・末尾のカンマだけ直し、それでも読めなければ**実行せずに**
  「読めなかった・受け取った先頭・スキーマ」をエラーで返す。履歴の tool_use は `{}` にする（厳格なプロバイダが拒否しない形）。
  ループ検出にも失敗として数える。
- **読み替えたら結果に添える**: 「呼び出しを読み替えて実行しました: …。次からはツール定義どおりに」。
- **出力上限で切れた応答**: 従来は 1 件でも引数が切れていれば全件を実行しなかった。切れるのは最後に書いていた
  呼び出しなので、**書き終えた呼び出しは実行し、切れた末尾だけ**「切れた・小さく分けて呼び直して」と返す
  （実測: Haiku が 22 件の処理を 1 応答に書いて末尾で切れ、全件未処理のまま「何も進まない」と諦めた）。
- **空の応答**: 催促しても本文も呼び出しも無い応答は、空の assistant メッセージとして履歴に積まない
  （content が空のメッセージを拒否するプロバイダがある。従来は積んでいた）。

### 3.4 停滞の注記（`loop_detect.rs` の `RepeatTracker`）

同じ呼び出し（名前＋引数）が同じ結果を返したら数え、3 回目から結果に「同じ引数で n 回目・結果は同じ・別の方法で
調べるか現状を報告して終える」と添える。止めはしない（成功の反復は正しいこともある）。チェックポイントに載せる。

### 3.5 作業の作法（system）と未完了の確認

- 自律版でツールがあるとき、system に短い作法を足す: 呼ぶと書いたらその応答で呼ぶ／後で使う値は本文に書き留める
  （古い結果は省かれ要約に置き換わる。**思考に書いた内容は次の応答で見えない**）／多くの数値は途中を書きながら計算し、
  日付の差は数えて確かめる／同じ呼び出しを繰り返さない／完了前に依頼の項目を満たしたか確かめる。run 内で固定する
  （プロンプトキャッシュを壊さない）。
- 計画（`plan`）に todo / doing が残ったまま本文で終えたら、**1 度だけ**利用者発話として「未完了: …。実行していない
  操作（提出・保存など）があれば今すぐ。終わっているなら計画は更新せず最終回答だけ」と確かめさせる。計画を更新しないまま
  正しく終えるモデルも多いので、余分な手は 1 ステップに留める。

## 4. 変えていないこと・未実装

- 通常チャット（Chat プロファイル）には圧縮・作法・未完了の確認を入れていない（剪定も従来どおり無効）。
  1 ステップの結果の上限・呼び出しの修復は両プロファイルに効く（窓あふれは常に致命的なため）。
- 窓を知らないモデル（カタログに `context_window_tokens` が無い）では、圧縮と結果の上限は効かない（剪定は従来どおり）。
  窓あふれの拒否からのやり直しだけは効く。
- Anthropic Messages / OpenAI Responses アダプタの「読めない引数」の扱いは変えていない（Chat Completions だけ）。
- 思考の中に書かれたツール呼び出し（Qwen が `</think>` を閉じずに書く）の回収は未実装（今回の評価では観測していない）。
- Qwen3.8 のモデルカードは、エージェント用途で過去の思考を履歴に残すこと（preserve thinking）を勧めているが、Chat Completions
  アダプタは思考を送り返さない。思考に書いた値が次で見えない問題（§1 の 2）は作法の system で緩和しただけ。
- 窓の狭い設定（16k）では圧縮が 2〜3 ステップごとに走り、費用とステップが増える（Haiku の tickets-long で 11〜31 回）。
  要約を差分で更新する（前回の要約を固定して新しい分だけ要約する）等は未着手。
- OpenRouter は無通信の間も keep-alive を送るため、gateway の無通信タイムアウト（120 秒）が効かず、詰まった生成は
  全体の上限（15 分）まで待つ（評価中に Qwen で 1 回発生）。
- 本文に書かれた呼び出しは、回収前に本文として画面へ流れる（ストリーミングを取り消せない）。

## 5. 評価

### 5.1 方法

[eval/agent-harness/](../../eval/agent-harness/README.md) の Rust 例（`harness_eval`）で、製品と同じ `run_agent` を実モデルで回す。
課題はメモリ上のツールだけで閉じ、決定的に採点する。

| 課題 | 内容 | 上限 |
| --- | --- | --- |
| ledger | 長い月次報告 12 本から地域別合計・最大地域・単月最大・障害月数を出して提出。途中に訂正 1 件。計算用の `calculate` あり（製品の code_interpreter の代わり） | 30 ステップ |
| codefix | 仮想リポジトリの失敗テスト 4 件（設定値・境界条件・改名漏れ 2 か所）を、読む・検索・完全一致置換・テスト実行で直す | 30 |
| tickets | 規程を読み 10 件を処理。境界値（30 日目）・優先順位・初回だけ失敗する照会 | 40 |
| tickets-long | 同じ規程で 30 件（擬似乱数生成・正解は規程の関数で決める） | 70 |

窓は 32k を模擬する（実測 prompt＋出力枠 4k が窓を超えたら、vLLM と同じ文言で拒否されたとみなす）。
`baseline` は今回の機能をすべて切った構成（現行 main 相当）、`improved` は既定（すべて有効）。

### 5.2 結果

表の各マスは「成功 run 数 / run 数（平均点）」。成功は満点。`溢れ` は窓あふれで拒否された run。

**32k 窓（出力上限 4k）・同じ課題データ（seed 1）で baseline と improved を比較**

| 課題 | Gemma 4 31B | Qwen3.8 27B | Claude Haiku 5.5 |
| --- | --- | --- | --- |
| ledger | 0/3（0.00・溢れ 3）→ **2/3（0.67）** | 0/3（0.13・上限まで読み直し）→ **3/3（1.00）**※v7 | 0/3（0.00・溢れ 3）→ **3/3（1.00）** |
| tickets-long | 0/3（0.88）→ 1/3（0.94） | 2/3（0.99）→ **3/3（1.00）**※v7 | 0/3（**0.21**）→ **3/3（1.00）** |
| tickets | 0/3（0.90）→ 1/3（0.93） | 3/3 → 3/3 ※v7 | 3/3 → 3/3 |
| codefix | 3/3 → 3/3 | 3/3 → 3/3 ※v7 | 3/3 → 3/3 |

improved は v4（Qwen の ledger 以降は v7）。別の課題データ（seed 11）で v5 を回した確認では、Haiku は ledger・tickets・
tickets-long とも 3/3、Gemma は ledger 1/3（0.70）・tickets-long 0/3（0.91）・tickets 0/3（0.90）。

| ledger | 0/2（溢れ 2）→ 1/2（0.50） | 0/2（溢れ 2）→ **2/2（1.00）** |
| tickets-long | 0/2（0.47）→ 1/2（0.95）・0/2（0.93） | 0/2（溢れ 2）→ **4/4（1.00）** |

improved は v5・v6（16k の ledger は v6＝結果の上限の修正後）。16k の tickets-long は圧縮が 11〜31 回走り、ステップ・費用が増える（Haiku 1 run $0.09〜0.17）。

**読み取れること**

- 窓あふれは improved で 0 件になった（拒否からのやり直しを含む）。baseline の ledger は 3 モデルとも 1 度も完遂できない。
- 最も効いたのは「未読の結果を畳まない＋1 ステップの結果の上限」と「圧縮」の組み合わせ。Haiku の tickets-long（0.21 → 1.00）は、
  1 応答に 22 件の処理を書いて出力上限で切れ、全件未実行になって諦める失敗が、結果の上限で読む量が絞られて起きなくなった。
- Gemma に残る失敗はハーネスより能力の側: 日付の差（30 日の境界）の数え違い（tickets の T-1010 が毎回）、合計の暗算違い
  （`calculate` があっても使わない run がある）、要約の後に同じ報告を読み直す。作法の system で平均点は上がる（ledger 0.22 → 0.50・v2）。
- Qwen は思考が長く、1 run の費用が他の 2〜10 倍（ledger で $0.05〜0.48）。要約が思考で空になる失敗（v5）を、取り直しと
  剪定への後退で直した（v7 で 3/3・$0.05〜0.10）。
- codefix・tickets は 3 モデルとも baseline で既にほぼ満点で、改善の余地がない（悪化もしていない）。

## 6. 結果の読み方の注意

- run 数は課題・モデルごとに 2〜3 回で、比較対照はこの評価課題だけ。改善率を一般化しない。
- 評価課題は日本語・メモリ上のツール。製品のツール（fs・web_fetch・doc_search）での確認は別途必要。
- 窓あふれは模擬（OpenRouter は 32k で拒否しない）。拒否の判定は「実測 prompt＋出力枠 > 窓」。
- Haiku は OpenRouter の OpenAI 互換口で呼んだ（製品の Anthropic アダプタではない）。思考は使っていない。

## 7. human に判断してほしいこと

1. **自律プロファイルで圧縮を既定で有効にするか**。今回の実装は既定で有効（窓を知っているモデルのみ）。
   要約の 1 生成ぶん費用が増え、要約の内容がモデルに渡る（要約もモデルの出力なので、新たな外部送信は無い）。
2. **Claude Haiku 5.5 を思考あり（adaptive thinking）で Anthropic アダプタから使う場合**、思考ブロックの生成後に
   履歴（古いツール結果）を書き換えると API が拒否しうる（2026-08-31 以降に作成したアカウントの既定・移行ガイド）。
   既存の剪定はその場で書き換えるため該当しうる。圧縮（履歴全体を要約 1 本に置き換える）は該当しにくいが、
   実 API での確認はしていない。対応（サーバ側の context editing を使う・`prefix_mismatch_behavior` を指定する等）は別途。
3. 窓の小さいモデルを本番で使うなら、カタログに `context_window_tokens` を入れること（入れないと圧縮・結果の上限が効かない）。
