> 状態: 初期実装済み・Haiku 実 LLM 少数ケース検証通過（2026-11-11）。Issue [#1175](https://github.com/imanect-labs/shiki-platform/issues/1175)。
> 実装コミット: `e898e127`。関連: [Phase 5 / Task 5.7](../roadmap/phase-5.md)、#407、#426。

## 1. 解決する問題と確認した事例

通常チャットで確認・調査を重ね、重要な編集や保存を実行する前にステップ上限へ達し、
未完了の説明だけが返る。自律モードも長いタスクでは同じ問題を起こし得る。

調査時点の実装では、通常チャットの既定は 6 ステップ、自律は 50 ステップ。
残量のモデルへの通知は自律限定で、上限到達後はツールを外した最終回答だけを生成していた。
その最終回答で未実行の操作を取り戻すことはできない。

既存記録は以下のとおり。今回ユーザーが遭遇した個別 run のログは取得していない。

- [#407](https://github.com/imanect-labs/shiki-platform/issues/407): 実走で子エージェント 7 体中 6 体が
  8 ステップの上限で停止。モデルに残量が届いていなかった。
- [#426 の実測コメント](https://github.com/imanect-labs/shiki-platform/issues/426#issuecomment-6282322729):
  2026-10-20 時点の直近 30 日・通常チャット 96 run 中、上限 6 ステップを使い切ったのは 2 件。
  いずれも検索改善前に `doc_search` を繰り返していた。この集計から現在の操作依頼の失敗率は判断できない。
- [#889](https://github.com/imanect-labs/shiki-platform/issues/889): 編集後の生成失敗から最初に戻って再試行し、
  同じ段落を二重挿入した。続行の設計では実行済み操作を引き継ぐ必要がある。

関連研究では [The Danger of Overthinking](https://arxiv.org/abs/2502.08235) が分析から行動に進めない挙動を、
[BAGEN](https://arxiv.org/abs/2606.00198) がモデルの予算見積もりの楽観性を報告している。
研究の改善率を本製品の改善率とは扱わない。

## 2. 初期実装の方針

ユーザーと合意した方針は、**最初から上限と数え方を知らせ、完了までの短い計画を立てさせる**こと。
計画のためだけに 1 ターンを使わず、最初の操作と同じ生成で返させる。

### 初回の指示

`agent_observation::budget_system_prompt` が、呼び出し元の system に以下を追加する。

- この run のステップ上限。
- LLM 生成 1 回が 1 ステップ。ツール結果を受けた後の生成、計画ツールの呼び出し、最終回答も含む。
- 同じ生成で複数ツールを呼んでも 1 ステップ。ただし依存する操作は結果を見てから進める。
- 調査・操作・結果確認・最終回答までを上限内に収める短い手順の見積もり。
- 複数工程の依頼では、何をどの順で確認・実行するかを利用者向けの本文に 1〜3 文で出す。
  詳細な内部思考や予算数値を表示する指示ではない。単純な質問には計画表示を要求しない。
- 計画の本文と最初のツール呼び出しを同じ生成で返す。
- ツールを提示しない run（計画専用の子など）では本文計画・ツール呼び出しを要求せず、
  指定された JSON 等の出力形式を守って成果物を返す。予算の説明は共通で渡す。
- 既存のスキル等が求める計画・承認は尊重し、必須確認・承認を省略しない。

`run_agent` 内で options を複製して system を組み立て、通常生成・上限後の最終生成・
コンテキスト見積もりで同じ system を使う。呼び出し元の options は変更しない。
同じ options で再開しても指示が累積しない。共通コアに置くため通常チャット・自律・子エージェントに適用される。

### 各ステップ後の通知

最後のツール結果に `Budget::remaining` の観測を添える処理を、通常チャットにも適用する。
残量は予算ガードと同じ消費から計算する。ステップ境界の checkpoint にもこの観測が残る。

上限と計画の作法は run 内で固定の system に置き、毎回変わる残量はツール結果に載せる。
system の前置きを毎ステップ変更してプロンプトキャッシュを壊すことを避ける。
独立した user メッセージや Tool ロールの単独 Text を追加する方法は、既存プロバイダ変換との相性から採用しない。

### 上限が近いとき

既存のしきい値（残り 2 ステップ以下、またはトークン・時間の残りが 15% 未満）は維持する。
指示を「次の応答で結論を書いて終える」から、次へ変更する。

- 任意の追加探索を切り上げる。
- 操作依頼では、依頼された操作・結果確認・最終回答に残量を使う。
- 調査依頼では、取得済みの根拠で回答する。
- 必須の確認や承認を省かず、未実行・未確認を完了と報告しない。
- 必須工程が収まらないと分かった時点で、実行済み・未実行と不足条件を示す。

ハード上限と、超過後のツールなし最終生成は維持する。最終生成は通常のステップ枠とは別に 1 回発生し得る。
費用・トークン上限で停止した場合も、既存実装は最終生成 1 回ぶんの超過を許す。

## 3. 計画の表示

参考画像の意図に合わせ、最初に「何を調べ、どのように確かめるか」を短い本文として表示し、
続けてツール実行へ進む。既存の `AgentEvent::Text` → `StreamEventKind::Token` →
`MessageTimeline` の本文表示を利用する。新しいイベント型や UI コンポーネントは追加していない。

表示例:

> 現在の文書を確認し、提出締切を金曜日に変更します。変更後に本文を読み直して、反映を確かめます。

通常チャットに計画承認待ちは追加しない。スキップボタンや専用の計画カードも今回の実装には含めない。
本文に計画を出すことはモデルへの指示であり、機械的な表示保証ではない。実 LLM での追従確認が必要。

## 4. 今回実装していないこと

以下は調査で提案した後続案。初期実装と混同しない。

- 実行・検証の手数をオーケストレータが強制的に予約する仕組み。現状は指示による配分。
- タスク別のステップ枠変更、自動増額、自動的な自律モード移行。
- 成功する検索の反復など、情報の増えない停滞の検出。既存の同一エラー反復検出は維持。
- 生成終了と業務上の完了を区別する永続状態・API・UI。既存の `RunStatus::Done` の意味は変えていない。
- 書き込みの冪等化や再試行方式の変更。
- 通常チャットへの委譲。#426 の human 判断を変更しない。

まず実 LLM でこの初期実装を測り、必要な後続案を判断する。

## 6. Claude Haiku での実 LLM 検証・引き継ぎ

### 作業の取得と環境

- リポジトリ: `imanect-labs/shiki-platform`。
- ブランチ: `investigate/chat-budget-completion`。このブランチで作業を継続する。
- Issue: #1175。PR はまだ作成していない。
- Rust は `rust-toolchain.toml` の 1.96.0。テスト専用の PostgreSQL 17 と
  `STORAGE_TEST_DATABASE_URL` を用意する。テスト自身が migration を適用する。
- 新しいタスクでは Docker のテスト DB やローカルの依存導入状態を引き継ぐと仮定しない。

ユーザーは環境設定へキーを登録して公開済みと申告しているが、旧タスクの実行環境では
シークレットが見えず、API を呼んでいない。
[公式ドキュメント](https://learn.chatgpt.com/docs/environments/cloud-environments)に従い、
公開済みの更新を使う新しいタスクで検証する。

秘密変数名は `ANTHROPIC_TEST_API_KEY`、送信先は `api.anthropic.com`。
環境の設定・ready 状態を確認し、キーや Authorization ヘッダーを表示・ログ出力しない。
Network secret の場合は、その環境が供給するプレースホルダーを使い、実値を取得しようとしない。
ユーザーにキーをチャットへ貼るよう依頼しない。

### 実行するテスト

`resume_it::haiku_budget_plan_live` を明示実行する。接続先は `https://api.anthropic.com` 固定。
既定モデルは `claude-haiku-5-5`。必要なら `ANTHROPIC_TEST_MODEL` で Haiku の利用可能なモデルを指定する。
TLS を中継する環境では `ANTHROPIC_TEST_CA` に環境が供給する PEM CA ファイルを指定する。
例: `ANTHROPIC_TEST_CA="$CODEX_PROXY_CERT"`。テスト用クライアントの信頼先へ追加し、証明書検証は無効化しない。

DB の接続先と秘密変数を環境へ設定してから、リポジトリ直下で実行する。

```sh
SHIKI_REQUIRE_IT=1 cargo test -p shiki-agent-core --test resume_it \
  haiku_budget_plan_live -- --ignored --nocapture
```

検証対象はメモリ上のテスト文書のみ。外部の実文書を編集しない。
「読む → 締切を金曜日に変更 → 本文を再取得して確認」を通常・自律の 2 プロファイルで実行する。
いずれも上限 6 ステップ、生成上限 2048 トークン。計画メタツールは提示しない。
最大は各プロファイル 6 生成と予算超過時の最終生成 1 回。まずこの少数ケースに限定する。

テストは次を確認し、モデル名・プロファイル・計画本文・停止理由・ステップ数・
累積トークン・編集回数・再読込の有無を JSON で出力する。

1. 最初のツール実行前に計画本文がある。
2. 最初のツール呼び出しが step 0。計画だけのターンを消費しない。
3. 編集は 1 回で、編集後に本文を再取得している。
4. 6 ステップ以内に `Completed` で終了する。

初期テストの「計画本文」判定は非空かどうかまでなので、実際の本文が具体的な手順を説明しているかも読む。
結果を本書に追記し、不具合があれば最小限修正して関連チェックを再実行する。
サンプルが少なく比較対照もないため、成功しても改善率や一般的な完了保証は主張しない。

最終報告には計画の実例、両プロファイルのステップ数・停止理由・編集と確認の成否を載せる。
認証やモデル利用権限で止まった場合は、実行成功とせず具体的な阻害要因を報告する。

## 7. Claude Haiku 実 LLM 検証結果（2026-11-11）

新しいクラウド環境で `ANTHROPIC_TEST_API_KEY` の ready 状態を確認し、Rust 1.96.0 と
PostgreSQL 17 の専用テスト DB を用意して §6 のテストを明示実行した。キー値・認証ヘッダーは表示していない。

初回は API リクエストの送信エラーで失敗した。認証なしの curl 疎通では HTTP 401 を受信できたため、
テストクライアントに追加 CA の指定 `ANTHROPIC_TEST_CA` を実装し、環境が供給する CA を指定したところ解消した。
本番コードと予算・計画の指示は変更していない。

実行コマンド（`STORAGE_TEST_DATABASE_URL` は専用 DB に設定済み）:

```sh
SHIKI_REQUIRE_IT=1 ANTHROPIC_TEST_CA="$CODEX_PROXY_CERT" \
  cargo test -p shiki-agent-core --test resume_it \
  haiku_budget_plan_live -- --ignored --nocapture
```

結果: `1 passed; 0 failed; 0 ignored`。1 テスト内で次の 2 プロファイルが両方通過した。

| モデル | プロファイル | ステップ数 / 上限 | 停止理由 | 累積トークン | 編集回数 | 編集後の再取得 |
| --- | --- | --- | --- | --- | --- | --- |
| `claude-haiku-5-5` | Chat | 4 / 6 | `Completed` | 5304 | 1 | 成功 |
| `claude-haiku-5-5` | Autonomous | 4 / 6 | `Completed` | 5450 | 1 | 成功 |

通常チャットの計画本文:

> まず文書を読み、現在の締切の記載を確認します。その後、提出締切を金曜日に変更し、変更後の本文を再読込して確認します。

自律モードの計画本文:

> まず文書の現在の内容を確認し、提出締切の記載を特定します。その後、締切を金曜日に変更し、再読み込みで変更後の本文を確認します。

両方とも空でないだけでなく、読む・変更する・再取得して確認する順序を具体的に示している。
テストの assertion で、最初のツール実行前に本文があり、最初のツール呼び出しが step 0
（計画本文と最初の操作が同じ生成）であることも確認した。締切は金曜日に変更され、
編集は重複せず、変更後の本文が再取得された。

CA 設定追加後の関連チェックも通過した。

- `SHIKI_REQUIRE_IT=1 cargo test -p shiki-agent-core --test resume_it`: 回帰 6 件通過。
  実 LLM の 1 件はこのコマンドでは ignore（上記の別実行で通過済み）。
- `cargo clippy -p shiki-agent-core --all-targets --all-features -- -D warnings`。
- `cargo fmt --all --check`、`git diff --check`、`bash scripts/check-file-size.sh`。

各プロファイル 1 run の少数ケースであり、比較対照はない。一般的な完了保証や改善率を示すものではない。
今回はイベント列で本文を確認しており、ブラウザでの実画面確認は引き続き未実施。

### PR レビューでの補強

ツールを持たない計画専用の子に本文計画とツール呼び出しを要求すると、既存の計画 JSON 形式と
衝突するため、実際にツールを提示する run にだけこの指示を追加するよう修正した。
ツールなしでも予算説明は渡し、既存の出力形式を尊重することを両プロファイルで回帰検証する。
また、再開後に system をエコーさせ、計画指示が 1 回だけ含まれることを検証する。
補強後に単体 346 件・結合 25 件（`resume_it` は 7 件）と、agent-core の clippy・fmt・
差分・ファイルサイズ検査が通過した。ツールを持つ run の計画指示は同一で、上記の Haiku 実測値は再利用している。
