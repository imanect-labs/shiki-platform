# shiki ローンチ法務・コンプライアンス チェックリスト

> 本書は shiki-platform を日本市場で SaaS としてローンチするにあたり、**(A) 必要な届出・許認可**、
> **(B) 取得を検討すべき資格・認証**、**(C) 作成すべき規約・ポリシー・免責事項** を調査・整理したもの。
> プロダクトの具体機能（[要件定義](../requirements.md) / [設計](../design.md)）に各規制を紐付けている。
>
> ⚠️ **免責**: 本書はエンジニアによる一次調査のサマリであり、法的助言ではない。最終判断は必ず
> 弁護士・行政書士・個人情報保護の専門家に確認すること（CLAUDE.md「判断に迷ったら human に相談」の原則）。
> 法令・ガイドラインは改正が早い領域（特に個人情報保護法・AI 関連）なので、施行日・最新版を都度確認する。
>
> 想定: SaaS版（GCP・マルチテナント・課金あり・外部LLM API or 自己ホスト）を優先ターゲット。
> オンプレ/エアギャップ版は別途追記（§5）。

## 0. なぜ shiki は規制対象になりやすいか（機能 → 法令の対応表）

| shiki の機能 | 法的トリガ | 主な論点 |
|---|---|---|
| チャットスレッド共有・ファイル/フォルダ共有（FR-1, FR-2, FR-4） | **電気通信事業法** | ユーザー間の通信を「媒介」→ 届出が必要な可能性大（§1.1） |
| **職員間メッセージ（チャンネル／DM・FR-18）** | **電気通信事業法（届出・通信の秘密・事故報告）**・個人情報保護法 | 「利用者間のメッセージの媒介」そのもの → **SaaS 版は届出が必要になるとみてよい**。管理者の DM 閲覧・AI 連携・漏えい報告（§7） |
| 顧客文書を預かるストレージ＋RAG（FR-2, FR-3） | **個人情報保護法** | 委託・安全管理措置・顧客文書中の個人情報（§2.1） |
| 外部 LLM API（Anthropic / Gemini / Azure）への送信（design §4.5） | **個人情報保護法 越境移転** | 外国第三者提供 or 委託の判断・本人同意/基準適合体制（§2.2） |
| マルチテナント課金・サブスク（FR-1.1 請求） | **特定商取引法**・消費者契約法 | 通信販売の表示義務（BtoB は適用除外だが表記推奨）（§1.2, §3.2） |
| 生成 AI チャット・自律エージェント・generative UI（FR-4〜6, 11） | **AI 推進法 / AI 事業者ガイドライン** | 努力義務・透明性・ガバナンス体制（§4） |
| RAG が顧客文書/外部文書を引用生成（FR-3） | **著作権法**（30条の4 / 47条の5） | 学習・索引・出力段階の権利処理（§4.3） |
| エンタープライズ調達（金融・製造・官公庁） | 任意だが事実上必須 | **ISMS / SOC 2 / ISMAP / P マーク**（§2.3） |
| サンドボックスで任意コード実行（FR-5） | 刑法・不正アクセス禁止法（運用） | 悪用防止・ログ・AUP（§3.4） |
| オンプレ/エアギャップ・暗号実装（NFR-2） | 外為法（輸出管理） | 将来の海外提供時に該当判断（§5） |

## 1. 届出・許認可（A）

### 1.1 電気通信事業法 — 届出（**該当可能性：高。要・専門家確認**）

> **2026-09 追記**: 職員間メッセージ（FR-18・Phase 14）を加えると、SaaS 版は届出が必要になるとみてよい。
> 総務省の参入マニュアルが「利用者間のメッセージの媒介（アプリ、SaaS）」（主機能でなく一部の機能でも同じ）と
> 「クローズド・チャット」を、登録または届出が必要な事業の例に挙げているため（回線設備を持たない shiki は届出の側）。届出後に負う義務（通信の秘密・事故報告）は §7 にまとめた。

- **論点**: shiki はチャットスレッド共有（FR-4）・ストレージのファイル/フォルダ共有（FR-2）を持つ。
  これは「他人の通信を媒介する」＝**電気通信役務**に当たり得る。総務省の整理では、
  **メール・DM・ファイル共有・Web会議・グループウェア（Slack/Teams 相当）は届出対象**とされる。
  - 「ユーザーが運営者とだけやり取りする／メッセージ機能がない」なら不要だが、shiki は
    **ユーザー間でスレッド・ファイルを共有する**ため、対象になる可能性が高い。
- **必要な手続**: 該当する場合、原則 **電気通信事業の「届出」**（登録ではなく届出で足りる規模が通常）。
  - あわせて改正電気通信事業法（令和4年改正）の **「外部送信規律」（いわゆる Cookie 規律・27条の12）** と
    **「利用者情報の適正な取扱い」** への対応が必要になり得る（Web に計測タグ等を入れる場合）。
- **アクション**:
  - [ ] 行政書士／通信法務に「shiki の機能セットが届出対象か」を確認（**ローンチ前必須**）。
  - [ ] 対象なら総務省へ電気通信事業者の届出。
  - [ ] 外部送信規律の該当確認（web/ の解析タグ・広告タグの棚卸し）。
  - [ ] 対象事業者になる場合、**通信の秘密**の保護体制・電気通信事業法上の管理規程整備。
- 参考: 総務省「電気通信事業参入マニュアル［追補版］」、令和4年改正の解説（§出典）。

### 1.2 特定商取引法 — 「特定商取引法に基づく表記」（**BtoB は適用除外だが掲載推奨**）

- SaaS は「役務提供」＝**通信販売**に当たり得る。「営業として締結する」BtoB 契約は適用除外だが、
  個人事業主・一般消費者の購入可能性を踏まえ、**「特定商取引法に基づく表記」ページは用意するのが実務標準**。
- サブスク（継続課金）は、継続契約である旨・金額・契約期間・解約条件の適切な表示が求められる。
- **アクション**: [ ] `特定商取引法に基づく表記` ページ（販売事業者・所在地・連絡先・料金・支払/解約条件）を整備。

### 1.3 その他の届出・許認可（現時点では原則不要、ただし要確認）

- **資金決済法**: 自社で前払式支払手段（ポイント等）を発行しないなら不要。決済は Stripe 等の収納代行に委ねる前提なら登録不要。**社内クレジット/チャージ残高を作る場合は要再検討**。
- **古物商・金融業・医療/医薬**等の業法: shiki 自体は非該当。ただし **顧客が規制業種で使う場合**、当該業界ガイドライン（金融庁 FISC、医療情報3省2ガイドライン等）への準拠を顧客から求められる → §2.3。
- **下請法**: 開発を外注する場合の自社の取引慣行に影響（プロダクト規制ではない）。

## 2. データ保護・セキュリティ（A/B 横断・最重要）

### 2.1 個人情報保護法（APPI）— プライバシーポリシーと安全管理措置（**必須**）

shiki は顧客の文書・チャットを預かり、顧客従業員（エンドユーザー）の個人情報も扱う。

- **立場の整理**（day-1 に固める）:
  - 顧客がアップロードした文書・チャット内の個人情報 → shiki は通常 **「委託」を受けた取扱事業者**。
    顧客（委託元）に対し、**委託先の監督（25条）に応えられる体制**（安全管理措置の説明・監査受入・再委託管理）が必要。
  - shiki が自社で取得するアカウント情報・課金情報・サポート問合せ → shiki が **管理者**としてプラポリ義務。
- **必須対応**:
  - [ ] **利用目的の特定・公表**（プライバシーポリシー）。
  - [ ] **安全管理措置**（組織的・人的・物理的・技術的）の整備と記録。設計の単一チョークポイント
    （StorageService / OpenFGA / llm-gateway）・監査ログ（FR-9, NFR-6）はこの根拠資料になる。
  - [ ] **委託先の監督**: 外部 LLM API・GCS・Qdrant 等を再委託として管理（DPA 締結）。
  - [ ] **漏えい時の報告**: 個人情報保護委員会への報告・本人通知の体制（重大事案は義務）。
  - [ ] **保有個人データの開示・訂正・利用停止請求**への対応窓口。
- 改正動向（2025〜）: 生成 AI・Cookie 等外部送信規律・課徴金/団体訴訟の導入など議論中。**継続ウォッチ**。

### 2.2 越境移転規制（**外部 LLM API を使うなら必須の設計判断**）

- **論点**: Anthropic / OpenAI / Google（米国法人）等へ個人データを送ると **「外国にある第三者への提供」**
  に当たり得る。EU・英国は十分性で例外だが、**米国宛は原則 本人同意 or 基準適合体制 が必要**。
- **「提供」か「委託」かの判断**:
  - API 利用で **学習に使われない・データ保持しない契約（DPA / ゼロ保持）** が取れるなら「委託」と整理し得るが、
    25条の監督が及ぶ仕組みが要る。整理は専門家確認必須（業界では「提供」前提で同意を取る保守運用も多い）。
  - **注（2026-09）**: 委託と整理しても、移転先が外国の第三者なら**28条の規律は外れない**（27条5項の委託の例外は28条に及ばない）。
    本人同意か基準適合体制（＋継続的な措置と本人の求めに応じた情報提供）のどちらかの根拠が必ず要る（§7.4）。
- **必須対応**:
  - [ ] 利用する LLM プロバイダごとに **データ処理契約（DPA）・学習不使用・データ所在地**を確認し記録。
  - [ ] プライバシーポリシー／顧客契約に **移転先の国名・当該国の制度概要・移転先のポリシー**を明示
    （本人同意ルートを採る場合の法定記載事項）。
  - [ ] **設計反映**: llm-gateway（design §4.5）に「テナント単位で外部送信可否・送信先リージョンを制御」する
    ポリシ層を持たせる（オンプレ/エアギャップは外部送信ゼロで成立 = NFR-2 が強い差別化＆コンプラ的退避路）。
  - [ ] プロンプト/文書を外部送信する前の **PII マスキング/不送信オプション**を提供（エンタープライズ要件）。

### 2.3 セキュリティ認証（B・任意だがエンタープライズ調達で事実上必須）

| 認証 | 位置づけ | shiki での優先度 |
|---|---|---|
| **ISMS（ISO/IEC 27001:2022）** | 組織の情報セキュリティ管理。国内大手・金融・製造で事実上の前提 | **最優先**（国内エンタープライズ狙いの本命） |
| **ISO/IEC 27017** | クラウドサービス向け 27001 アドオン | ISMS 後に追加検討 |
| **SOC 2（Type I→II）** | クラウド運用状況の第三者保証。外資・海外向けに汎用 | 海外/外資顧客が視野なら取得 |
| **ISMAP** | 政府調達クラウドの登録制度。官公庁案件は登録が事実上必須 | 公共セクター展開時に検討（コスト大） |
| **プライバシーマーク** | 個人情報保護の組織認証。国内で広く要求 | 中堅顧客向けに有効 |

- コスト感: ISMS で初期 50〜300万円＋年次維持。商談の入口要件になりがちで、**投資対効果は高い**。
- **アクション**: [ ] 販路（国内エンタープライズ／官公庁／海外）を決め、**ISMS を起点**にロードマップ化。
  設計の監査ログ・認可チョークポイント・テナント隔離（NFR-8）は認証審査で有利に働くので、
  **ローンチ前から証跡（ログ・ポリシ文書）を貯める**。

## 3. 作成すべき規約・ポリシー・免責事項（C）

ローンチに向けて最低限そろえるドキュメント一式。**契約は弁護士レビュー必須**。

### 3.1 利用規約（Terms of Service）— **必須**

- BtoB SaaS なので **免責・責任制限条項は原則有効**（消費者契約法の制約を受けにくい）。盛り込むべき要点:
  - [ ] サービス内容・SLA（可用性目標）・保守/メンテナンス。
  - [ ] **責任制限**（損害賠償の上限＝直近 N ヶ月の利用料等、間接損害の排除）。
  - [ ] **データの取扱い**: 顧客データの所有権は顧客に帰属／shiki は提供目的でのみ処理。
  - [ ] **データ消失・バックアップ**の責任分界（バージョニング＝FR-2 はあるが免責は明記）。
  - [ ] **禁止事項（AUP）**: サンドボックス（FR-5）の悪用＝マルウェア・攻撃・不正アクセス・暗号資産採掘・
    大量送信等の禁止。違反時の停止権限。
  - [ ] **AI 生成物の取扱い**（§3.3 免責へ）。
  - [ ] 反社条項・準拠法/裁判管轄・解約/返金・規約変更手続。
- マルチサービス（shiki × skillex / FR-1.1）の **請求は Org 単位 1 枚・サービス別内訳** という構造を契約に反映。

### 3.2 特定商取引法に基づく表記 — **掲載推奨**（§1.2）

### 3.3 AI 利用に関する免責・注意事項（**必須・shiki 固有の肝**）

生成 AI・自律エージェント・generative UI を持つため、専用の免責/注意喚起を用意する。

- [ ] **正確性の非保証**: LLM 出力は誤り（ハルシネーション）を含み得る。重要判断は人間が検証する旨。
- [ ] **AI による生成である旨の明示**（透明性。AI 事業者ガイドライン／AI 推進法の透明性要請、海外の表示義務動向に整合）。
- [ ] **専門的助言ではない**: 法務・医療・税務・投資等の助言として依拠しない旨。
- [ ] **自律エージェントの実行リスク**: エージェントがファイル作成/編集/削除・コマンド実行する（FR-5）。
  破壊的操作の確認フロー・ユーザー責任・ロールバック（バージョニング）の範囲を明記。
- [ ] **生成物の権利・責任**: 出力の利用は顧客責任。第三者著作物との類似が生じ得る点の注意喚起（§4.3）。
- [ ] **入力データの取扱い**: 顧客が入力したデータが（設定により）外部 LLM に送信される条件・無効化方法。

### 3.4 プライバシーポリシー — **必須**（§2.1, §2.2 の記載事項を反映）

- [ ] 取得する情報・利用目的・第三者提供/委託（外部 LLM・クラウドを含む）・**越境移転（国名・制度・移転先ポリシ）**・
  安全管理措置の概要・開示等請求窓口・Cookie 等外部送信（該当時）・問い合わせ先。

### 3.5 その他用意すると強い文書（エンタープライズ調達で求められる）

- [ ] **DPA（データ処理契約）テンプレート**: 顧客＝委託元、shiki＝委託先、外部 LLM＝再委託の三層を明記。
- [ ] **セキュリティホワイトペーパー / Trust ページ**: テナント隔離・暗号化・認可モデル・監査・サブプロセッサ一覧。
- [ ] **SLA 文書**（可用性・サポート応答・クレジット）。
- [ ] **サブプロセッサ一覧**（GCP / LLM プロバイダ / Qdrant 等）と更新通知ポリシ。
- [ ] **AI 利用ポリシー / 受入可能利用（AUP）**。
- [ ] オンプレ顧客向け **OSS ライセンス順守（SBOM / ライセンス表記）**: Firecracker・gVisor・OpenFGA・Keycloak・
  Docling・vLLM 等の OSS ライセンス（Apache-2.0 / AGPL 等）を棚卸しし、再配布条件を確認（特に **AGPL 系**に注意）。

## 4. AI 固有の規制・ガイドライン（C/努力義務）

### 4.1 AI 推進法（人工知能関連技術の研究開発及び活用の推進に関する法律・2025年施行）

- **性格**: EU AI Act のような規制法ではなく **振興法。罰則なし**。事業者は **第7条の努力義務**
  （基本理念に沿った活用・国の施策への協力）のみ。
- ただし **重大な権利侵害事案では国の調査・事業者名公表**があり得るため、ガバナンス体制は実装すべき。
- 政府の「適正性指針」（2025年策定）が事実上の標準になる見込み → **準拠を前提に設計**。

### 4.2 AI 事業者ガイドライン（総務省・経産省、第1.2 版＝2026年3月）

- ソフトロー。**共通の指針10項目**: 人間中心／安全性／公平性／プライバシー保護／セキュリティ／
  透明性／説明責任／教育・リテラシー／公正競争／イノベーション。
- shiki は **「AI 提供者」**（プラットフォーム提供）かつ機能により **「AI 利用者」**。両立場の実践事項に対応:
  - [ ] **透明性**: AI 生成の明示・引用ソース表示（FR-3, FR-4 で実装済みの引用機能が効く）。
  - [ ] **説明責任 / 監査**: 監査ログ＋Langfuse トレースの trace_id 突合（FR-10, NFR-6）が直接の証跡。
  - [ ] **安全性 / セキュリティ**: サンドボックス隔離・egress 遮断・二段 authz（NFR-1）。
  - [ ] **ガバナンス体制**: AI ポリシー策定・リスク評価・インシデント対応フローの社内整備。

### 4.3 著作権法（RAG・学習・出力）

- **学習・索引（30条の4 / 47条の5）**: AI 学習目的・RAG 用ベクトル DB 作成等は権利制限の適用余地がある。
- **出力段階**: 既存著作物との **類似性・依拠性**があれば侵害になり得る。RAG が原文を「軽微利用」を超えて
  提示する場合は許諾が要る可能性。
- **アクション**:
  - [ ] RAG は **顧客が正当な権利/利用権を持つ自社文書**を対象にする前提を契約で明確化（顧客が権利保証）。
  - [ ] 出力に**引用元を明示**し、原文の大量転載を避ける設計（FR-3 のチャンク引用と整合）。
  - [ ] Web 検索ツール（FR-4・クラウド版）経由の外部コンテンツ取り込みは、出力での再利用範囲に注意。

## 5. オンプレ / エアギャップ版・海外展開の追加論点

- **外為法（輸出管理）**: 暗号機能（Keycloak/TLS 等）を含むソフトを **海外提供**する場合、該非判定が必要に
  なり得る。国内提供のみなら当面対象外だが、**海外顧客・海外拠点配布の前に判定**。
- **オンプレはコンプラ的に有利**: 外部送信ゼロ・顧客環境完結（NFR-2）のため、越境移転・委託の論点を
  顧客側に閉じられる。**規制業種（金融 FISC・医療3省2ガイドライン・公共 ISMAP）向けの強い売り**になる。
- **海外データ保護法**: 海外顧客を取る場合は **GDPR（EU）・各国法**が別途必要（本書は日本前提）。

通信の秘密と直接かかわるので、規約・同意・設計のどこで手当てするかを先に決める。

### 7.1 電気通信事業法 — 届出（SaaS 版・**届出が必要になるとみてよい**）

- **根拠**: 電気通信役務は「電気通信設備を用いて他人の通信を媒介」すること（法2条3号）。参入マニュアル［追補版］は
  「利用者間のメッセージの媒介（アプリ、SaaS）」を登録または届出が必要な例に挙げ、**主たるサービスでなく一部の機能として
  媒介する場合も同じ**とする。別の事例として「クローズド・チャット（特定の利用者の間のみに閉じた会話）」も
  登録または届出が必要とされる。FR-18 はこれらの例にそのまま当たる（登録と届出のどちらかは次項）。
- **テナント内だけの会話でも除外されない**: 「自己の需要」の例外は、自社の業務のために自社で設備を運用する場合の話で、
  shiki のように**他社（顧客）の従業員どうしの通信を事業として媒介する場合には当たらない**。
- **登録ではなく届出**: 電気通信回線設備を自前で設置しない（GCP 上の SaaS）ので、通常は届出（法16条）で足りる。
  **国外リージョンのサーバを使っても、国内の利用者向けなら届出は要る**（参入マニュアルの事例）。
- **時期**: 届出は「営もうとする」段階、つまり**機能を SaaS 利用者に公開する前**に出す。
  社内でのドッグフーディングや、試験的・一時的な提供は「事業」に当たらない余地があるが、
  **顧客テナントに開放する時点では届出を済ませておく**。
- **すでに届出済みの場合（ファイル共有等を理由に §1.1 で届け出たとき）**:
  - まず提出済みの「提供する電気通信役務」（様式第四）と構成図を確認する。利用者間のメッセージ媒介がすでに記載に
    含まれていれば、FR-18 の追加だけでは手続は生じない。**記載事項に変更が生じる場合に限り**、
    施行規則10条の変更報告（様式第十＋変更後の様式第四＋構成図に変更があればネットワーク構成図）を遅滞なく出す。
    事後の報告でよい。→ 記載内容は行政書士/総合通信局に確認する。
  - 業務区域・事業用電気通信設備の概要を変えるときは法16条4項の届出（様式第九）。
  - 氏名・住所・代表者等を変えたときは**遅滞なく**変更届出（法16条3項）。業務区域・設備概要を変えるときは届出（同条4項）。
- **届出後に続く手続**: 事業の休止・廃止は遅滞なく届出（法18条）。事業報告規則に基づく定期報告の要否も、届出時に確認する。
- **外部送信規律（法27条の12）**: 「他人の通信を媒介する電気通信役務」は対象の役務に入る。web/ に計測・解析タグ等
  （利用者の端末から第三者へ情報を送らせるもの）を入れるなら、**原則として通知・公表（外部送信ポリシー）が要る**（同意取得・オプトアウト等の例外あり・法27条の12 ただし書）。
  §1.1 のタグ棚卸しをメッセージ画面にも広げる。
- **大規模事業者向けの規律は当面対象外**: 特定利用者情報の規律（法27条の5以下・情報取扱規程）は総務大臣の指定を受けた
  大規模事業者だけが対象。**利用者数が指定基準に近づいたら見直す**。
- **情報流通プラットフォーム対処法（旧プロバイダ責任制限法）**: 対象の「特定電気通信」は不特定の者が受信する通信で、
  テナント内に閉じた公開チャンネル・DM は該当しにくい。**Phase 13 の匿名公開（HTML ページ/サイト）とは分けて判断する**。

### 7.2 通信の秘密（法4条）と事故報告（法28条）— **届出事業者になると負う義務**

- **保護の範囲**: 発言本文だけでなく、**誰が・誰に・いつ・何件**送ったか（通信履歴）も通信の秘密に当たる。
  `channel_member`・`read_state`・`audit_log` の発言系イベント・pub/sub のメタデータも対象と考える。
- **侵害になる行為**: 知得・窃用・漏えい。**機械による処理でも侵害になり得る**。約款の包括的な同意では足りず、
  **個別・具体的で明確な同意**が要る。課金・障害対応など役務提供に不可欠な処理は正当業務行為になり得る。スパム/ウイルスのフィルタリングは
  同意の取り方に個別の整理がある（総務省の整理を参照）。
- **shiki の運用に引き直すと**:
  - [ ] **従事者の守秘（法4条2項）**: 運用・サポート担当者の誓約書と社内規程。退職後も義務が続く。
  - [ ] **サポートアクセス（break-glass・requirements FR-9）が発言本文へ届かない**こと。届かせる必要がある場合は、
    顧客管理者の許可に加えて**当事者（利用者）の同意**が要るかを専門家に確認する。
  - [ ] **フィードバック（FR-16）の「本文添付」**: メッセージから呼び出した AI の回答に**他人の発言**が含まれていると、
    送信者本人の同意だけでは**第三者（他の発言者）の通信の秘密**を shiki（運営者）へ渡すことになる。
    → メッセージ由来の文脈を含む対話ではフィードバックの本文添付を禁止するか、発言を除いて送る（**設計への提案**）。
  - [ ] **発言の分析・品質改善・モデル改善への利用**は、正当業務の範囲を超えるので**しない**（するなら個別同意）。
  - [ ] **法執行機関への対応ポリシ**: 通信の内容・通信履歴は**令状（差押許可状等）がある場合に限って**開示する。
    捜査関係事項照会だけでは開示しない。対応記録を残す。
- **事故報告（法28条）**: **通信の秘密の漏えいは規模にかかわらず報告対象**。事業者に落ち度がない漏えい（外部からの攻撃等）
  も含む。**知った後速やかに**第一報（電話・メール可）、そのうえで**様式第五十の二の報告書を、漏えいを知った日から30日以内**に
  提出する（施行規則57条・法定期限）。報告先は総務省（本省・総合通信局）。
  なお、法28条2項の「おそれ」の報告は現行省令（施行規則58条の2）では設備系の重大事故に限られ、
  通信の秘密の漏えいのおそれは対象外。漏えいのおそれを社内でどうエスカレーションするかは手順で決める。
  - **個人データの漏えい等**のうち、個人情報保護法施行規則7条の報告対象事態（要配慮個人情報を含む・財産的被害のおそれ・
    不正目的のおそれ・本人1,000人超、またはそれらのおそれ）に当たるものは同法26条で報告義務がある。電気通信事業に関わる個人データは、個人情報保護委員会から総務大臣への権限委任により総務省が報告の窓口になる。速報（おおむね3〜5日）・
    確報（30日、不正目的なら60日）の期限は個人情報保護法に従う。
  - **設計上の落とし穴との対応**: PIT-66（pub/sub トピックの `tenant_id` 欠落 → 他テナントへの配信）・
    PIT-64（剥奪後も購読が残る → 退出者への配信）・PIT-63（読めない発言が AI の回答に混ざる）・
    PIT-65（管理者の閲覧が通常経路に相乗り）は、**起きれば通信の秘密の漏えいとして報告対象になり得る**（特に PIT-65 のテナント内の手続外閲覧が「漏えい」に当たるかは解釈が分かれるので、専門家と事前に判断基準を決めておく）。
    Phase 14 の negative テスト（14.16）は法令対応の証跡としても残す。
  - [ ] インシデント対応手順（§4.2 のガバナンス体制）に「通信の秘密の漏えいか」の判定と総務省への第一報を組み込む。
- **電気通信事業における個人情報等の保護に関するガイドライン**（個人情報保護委員会・総務省）が上乗せで適用される。
  特に**通信履歴は業務上必要な範囲でだけ記録し、保存期間を決めて、過ぎたら消す**という考え方をとる。
  requirements FR-18 の「発言の保存期間は監査と同じ」は、**本文（利用者が保存を求めているデータ）と
  通信履歴（監査ログ側のメタデータ）で保存期間の根拠を分けて説明できるように**しておく（**設計への提案**）。

### 7.3 管理者による閲覧・エクスポート（Phase 14.9）— **規約・同意・テナント側規程の三点で手当て**

- **論点**: 公開チャンネルの管理者閲覧、DM・非公開チャンネルの承認付き閲覧は、shiki（事業者）が提供する機能を使って
  顧客企業が**従業員の通信を読む**ことになる。事業者としての通信の秘密と、雇用主による従業員モニタリング
  （個人情報保護法・労働法上のプライバシー）の両方にかかわる。
- **事業者（shiki）側の手当て**:
  - [ ] **利用規約（契約者＝顧客企業）**: テナント管理者が所定の手続で発言を閲覧・エクスポートできる旨と、
    顧客がその手続を社内規程で定め従業員へ周知する責任を負う旨を定める。
  - [ ] **利用者（従業員）の明示同意**: 約款への包括同意では足りない可能性があるため、**メッセージ機能の初回利用時に
    「管理者が所定の手続で閲覧できる」ことをクリックで同意させる画面**を置く（**設計への提案**・14.11/14.12 の UI）。
    どこまで必要かは専門家に確認する。
  - [ ] **shiki 自身は閲覧の主体にならない**: 閲覧は顧客管理者の権限と承認レコードでだけ実行され、
    shiki の運用者が代理で読む経路を作らない（PIT-65・break-glass の除外）。
- **顧客（テナント）側に求めること**（運用ガイド/ホワイトペーパーで提供する）:
  - 個人情報保護委員会の考え方（従業者の監督としてのモニタリング）に沿って、**目的の特定と通知・社内規程の整備・
    責任者の決定・運用の点検**をする。承認者の定義と保存期間（14.9 の 🔒 決定事項）は、この社内規程と揃える。
  - 就業規則・情報管理規程での周知。私的な利用の扱い。
- **エクスポートした発言の持ち出し**は、顧客の責任で管理される旨を規約で分担し、全操作を `audit_log` に残す（FR-9）。

### 7.4 AI 連携・検索 — **越境移転と同意の範囲が「他人の発言」に広がる**

- **14.8 メッセージから AI を呼び出す**: 照会者が読める発言を文脈として LLM に送る。照会者は正当な受信者だが、
  **外部 LLM（米国等）に送られるのは他の発言者の通信・個人データ**でもある。
  - [ ] **外国の LLM プロバイダへの送信は、委託と整理しても個人情報保護法28条の「外国にある第三者への提供」の規律を受ける**
    （委託の例外は28条には及ばない）。メッセージを扱うプロバイダごとに、**28条の移転根拠（本人同意、または基準適合体制＋
    本人の求めに応じた情報提供）のどちらを採るかを必須項目として決め**、DPA・学習不使用・データ所在地とあわせて記録する（§2.2）。
  - [ ] プラポリ・規約に「受信した発言を AI 機能に渡すと外部 LLM（国名）で処理される」ことを書く。
  - [ ] テナント設定で「メッセージ文脈の外部 LLM 送信」を無効化できるようにする（llm-gateway のテナント別送信制御・§2.2 と同じ層）。
  - [ ] 事業者が他人の通信を第三者（LLM プロバイダ）へ送ることが通信の秘密の「漏えい」に当たらないか、
    **受信者の指示による処理として整理できるか**を専門家に確認する（ゼロ保持・学習不使用の契約が前提）。
- **14.7 発言の全文検索**: 利用者自身の検索のための索引化はサービス提供に必要な処理として整理できる。
  **索引をサービス提供以外（分析・学習）に使わない**ことをプラポリに書く。
- DM には健康・人事・ハラスメント相談など**要配慮個人情報**が入り得る。顧客との DPA で
  「顧客データに要配慮個人情報が含まれ得る」前提の安全管理措置（§2.1）を明記する。

### 7.5 規約・ポリシーへの追加事項（§3 への追記）

- **利用規約（§3.1）**
  - [ ] 通信の秘密の保護と、その例外（法令に基づく場合・正当業務・利用者の同意）。
  - [ ] 管理者による閲覧・エクスポート（§7.3）。
  - [ ] **AUP の追加**: ハラスメント・差別・脅迫・違法情報・スパム・なりすまし・マルウェアの送信を禁止。
    違反時の利用停止。**運営者は内容を監視しない**こと、**通報を受けた場合に通報者の同意のもとで該当発言を確認する**手続。
  - [ ] 削除の扱い（論理削除・14.3）と、削除後の保存期間・監査上の保持。
- **プライバシーポリシー（§3.4）**
  - [ ] 取得する情報に「メッセージ本文・添付の参照・通信履歴（送受信者・日時・既読）」を追加。
  - [ ] 利用目的・保存期間・AI 機能での処理（外部 LLM を含む）・管理者閲覧の可能性。
- **サブプロセッサ一覧（§3.5）**: 配信（Redis）は GCP（Memorystore）上なので既存の GCP の記載で足りる。発言を扱う外部事業者が
  増える場合（SaaS の検索サービス等を採用したとき）に追記する。
- **運用ガイド**: テナント管理者向けの「メッセージ閲覧手続の作り方」（§7.3）。

### 7.6 オンプレ版・その他

- **オンプレ版は shiki が電気通信事業者にならない**: 顧客が自社の設備で自社の従業員のために運用するのは「自己の需要」で、
  電気通信事業に当たらない。shiki はソフトウェアの提供者。ただし**保守で顧客環境に入る場合**は、発言本文に触れない
  運用（守秘契約・アクセス記録）を保守契約で定める。
- **SaaS で 1 社だけに提供する専用構成**（例: 特定顧客向けの専用セルを shiki が運用し、他社には提供しない）は
  「専ら一の者に提供する電気通信事業」（法164条1項1号）として適用除外になり得るが、**shiki は複数社へ提供するので
  事業全体としては対象**。個別の専用構成を別事業として扱えるかは専門家に確認する。適用除外でも通信の秘密（法4条）は残る。
- **労働法**: DM でのハラスメントの記録・保全は顧客の雇用管理の問題（労働施策総合推進法等）。
  shiki は承認付きエクスポート（14.9）で支える。**保全（リーガルホールド）は現仕様にない**ので、必要なら追加を提案する。
  追加する場合、削除とリーガルホールドが衝突したときの優先は
  14.9 の決定事項に含めて human と決める。
- **メール通知**（現仕様ではメール通知は未定。14.13 でメール通知をする場合）: 取引上の通知で広告を含まない限り、特定電子メール法の対象外。
  広告を載せるなら同法の同意・表示義務が要る。
