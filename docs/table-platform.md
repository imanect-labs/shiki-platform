# テーブル基盤 統合設計（Teable / Microsoft Lists 級の構造化データ体験）

> 本書は [要件定義書](./requirements.md) FR-18 の設計正本。
> Phase 9 で実装済みの構造化データサービス（`crates/data`・design §4.10）を、
> **ユーザーが直接作成・共有・編集できる第一級の「テーブル」プロダクト**（Teable / Airtable /
> Microsoft Lists 相当）へ昇格させ、チャット・generative UI・ワークフロー・shiki script・
> ミニアプリの全消費面から同一契約で参照できるようにする。
> 将来の「AI が作った簡単なアプリケーションをデプロイできる PaaS」のデータ層を兼ねる。
>
> 認可・ストレージ・LLM の不変条件（単一チョークポイント・AuthContext・二重ゲート・二段 authz）は
> design.md §1/§4 が正本。行 authz の脅威モデルは [design-caveats PIT-17〜21](./design-caveats.md)、
> 本書で新設した落とし穴は [PIT-53〜57](./design-caveats.md) を実装前に必ず確認すること。
> 実装順は [roadmap Phase 13](./roadmap/phase-13.md)。

## 0. 決定サマリ

| # | 論点 | 決定 |
|---|------|------|
| D1 | 保存モデル | **JSONB 共有テーブル（現行 `data_record`）を維持**。Teable 式の「テーブルごとに物理 CREATE TABLE」は採らない（§2）。性能は式インデックス＋keyset ページング＋クォータ＋パーティション準備で担保し、限界時の退路はクエリコンパイラ境界での差し替え |
| D2 | テーブルの位置づけ | **スタンドアロンのテーブルを第一級アーティファクトに昇格**（`app_id` null は既に許容）。ミニアプリ所有テーブルと同一実体・同一チョークポイント。base（テーブルグループ）は将来 |

| D9 | 消費面 | chat ツール / workflow ノード / `Shiki.data.*` / genui コンポーネント / gateway 能力 / グリッド UI の**全てが `crates/data` の同一チョークポイントを通る**。語彙は codegen 単一定義（§6） |
| D10 | スキーマ進化 | 安全変換行列（閉集合）のみ許可。大テーブルの backfill は jobq ジョブ。式インデックスは `CREATE INDEX CONCURRENTLY` を状態機械付きジョブで（§7） |

## 1. 目的と位置づけ

### 1.1 何を作るか

kintone / Microsoft Lists / Teable が担っている「非エンジニアが構造化データを定義し、
ビューで眺め、フォームで集め、権限を絞って共有し、自動化につなぐ」体験を shiki の第一級機能にする。

- **今日の実体**: Phase 9 の `crates/data` は行レベル authz・フィールドマスク・リビジョン・FSM ガード・
  保存ビュー・宣言的クエリまで実装済みだが、消費者は**ミニアプリ（gateway 能力）だけ**で、
  ユーザーが直接テーブルを作る UI も、チャット/genui/script からの参照も未配線。
- **本設計後**: テーブルは共有可能な第一級オブジェクトになり、同じテーブルを
  ①グリッド UI で人間が編集 ②チャットで AI が読み書き ③genui の一覧/フォームで表示
  ④ワークフローが自動処理 ⑤shiki script が関数から操作 ⑥ミニアプリが所有・参照、できる。

### 1.2 PaaS データ層としての役割

「AI が作った簡単なアプリをデプロイできる PaaS」は、shiki では**新しいホスティング基盤ではなく
既存 3 点セット（構造化データ＋サンドボックス/B1/B2 ランタイム＋公開 API ゲートウェイ）の組み合わせ**で
実現する（FR-11 の「汎用 PaaS/DBaaS は作らない」原則は維持）。本設計はその**データ層の完成**にあたる:

- AI がチャットで `table_schema` を生成 → 検証済みスペックとして保存（workflow IR・genui スペックと
  同じ「AI 生成物は常に閉じた語彙へ照合して保存」パターン）→ ビュー/フォーム/ワークフローを束ね、
  必要ならミニアプリ・マニフェストへ昇格して配布する。**テーブル単体でもアプリ未満の価値が立つ**
  （Lists 的な使い方）ことが、ミニアプリへの自然な導線になる。
- ミニアプリのマニフェストは従来の**所有テーブル（インストール時プロビジョン）**に加えて、
  **既存スタンドアロンテーブルへの参照**（要求スコープ＋インストール同意で ReBAC 付与）を宣言できる
  （§6.6）。全社マスタ（顧客一覧・品目マスタ）を複数アプリで共有する PaaS 的ユースケースの土台。

### 1.3 CSV / tabular との役割分担（既存決定の再確認）

design §4.8.2 の分担を変えない: **ファイルとして持ち込む/持ち出す表データは CSV（ファイル単位 ReBAC・
DuckDB クエリ）／行レベル権限・参照整合・フォーム・自動化が要るデータはテーブル（本書）**。
両者はインポート/エクスポートで相互変換できる（§8）。グリッド UI のフロント実装（無限スクロール・
セル編集・範囲選択）は CSV エディタと最大限共有する。

## 2. 保存モデル: JSONB 共有テーブル維持の決定（D1）

Teable は「ユーザーテーブル＝実 Postgres テーブル」（ランタイム DDL）で、ネイティブ型・複合インデックス・
生 SQL 到達性という性能利点を得ている。shiki は**これを採らない**。理由:

1. **心臓部が既に JSONB 上に実装済み**: 行述語コンパイラ（WHERE 強制注入・集計適用・PIT-17〜21 対策）・
   フィールドマスク・個別共有・FSM ガード・リビジョンは全て単一 `data_record` を前提に検証済み。
   物理テーブル化はこの最も正しさがクリティカルな層の全面書き直しになる。
2. **マルチテナント運用との相性**: ランタイム DDL はカタログ肥大・DDL ロック・cell プロビジョニング/消去
   （NFR-10/11）・整合バックアップ（PIT-38）・将来のフルプール化（tenant_id 行分離）の全てと衝突する。
   スキーマ数がテナント×アプリ×テーブルで増殖する運用は「部品点数最小化」に反する。
3. **生 SQL 到達性は目的ではない**: 生 SQL は二段 authz と FSM 不変条件をバイパスし得るため
   構造的に公開しない（workflow ir.md §7 の既決定）。物理テーブルの主要な果実を最初から捨てている。

### 2.1 性能担保の設計（「JSONB だから遅い」を運用で言わせない）

| 対策 | 内容 |
|------|------|
| 式インデックス | 宣言フィールド（`indexed`/`unique`）に JSONB 式 B-tree（実装済み・`data_index_registry`）。DateTime は固定幅 ISO 文字列正規化済みで辞書順＝時刻順（実装済み） |
| keyset ページング | 一覧/ビューのページングは **keyset（`(sort キー, id)` カーソル）を正**とし、offset は小さい値のみ許容。無限スクロールと API の両方で共通 |
| 非索引フィルタのガード | 索引の無いフィールドでの filter/sort は**テーブル行数がしきい値（既定 5 万行）以下の場合のみ許可**。超過テーブルでは「インデックス必須」エラー（400）を返し、UI がその場で索引追加を提案する。statement_timeout をクエリ級別に強制 |
| クォータ | §9 の既定値（フィールド数・索引数・行サイズ・ページ長・バッチ長）。全て fail-closed |
| パーティション準備 | PK は `(tenant_id, id)`＋`table_id` 索引（実装済み）。行数が cell 単位で閾値を超えたら `data_record` を **HASH(table_id) パーティション**へ移行できるようキー設計を維持（v1 では張らない・追加のみで移行可能な形を崩さない） |
| 集計 | 述語合成済み SQL 集計（実装済み）＋スモールセル抑制。BI 級の重い分析は将来「テーブル→（権限適用済み）スナップショットを tabular/DuckDB へエクスポート」の別トラックで受け、オンライン経路に混ぜない |

**性能目標（cell 単位・受け入れ条件に落とす）**: テーブル 100 万行・テナント合計 2,000 万行を包絡とし、
点読取 p95 < 20ms／索引フィルタ 1 ページ（50 行）p95 < 100ms／1,000 行バッチ書込 < 2s。

### 2.2 退路（差し替え点）

「トレイト裏で差し替え」原則に従い、宣言的クエリ AST → SQL のコンパイラと実行器（`crates/data::query`）の
境界を汚さないこと自体を退路とする。将来スケールで JSONB が限界になった場合、同じ AST を
物理ワイドテーブル/列指向バックエンドへコンパイルする実装を**この境界の裏に追加**できる
（能力面・認可の式・監査は不変のまま）。v1 で抽象トレイトは切らない（実装が 1 つの間は過剰設計）。

## 3. ドメインモデル拡張

### 3.1 フィールド安定キーと表示名の分離（D3）

現行 `FieldDef` は `name` が JSONB 保存キー・ポリシー/ビュー/lookup の参照キー・表示名を兼ねており、
**rename が構造的に不可能**（PIT-55）。次のように分離する:

- `key`: 不変。作成時の name がそのまま key になる（`^[a-z][a-z0-9_]{0,63}$` 検証は現行どおり）。
  JSONB のキー・式インデックス DDL・row_policy/field_policy/lookup/formula/ビュー設定は**全て key 参照**。
- `label`: 可変の表示名（UTF-8 自由・テーブル内で大文字小文字無視の一意）。UI・フォーム・AI への
  スキーマ提示は label を使う（AI には key⇄label 両方を渡し、ツール引数は key で受ける）。
- 後方互換: 既存テーブルは `label = key` として読み替え（serde default）。データ移行ゼロ。
- フィールド削除は**論理削除**（key を墓標として予約・再利用禁止）。物理削除はリビジョン履歴・
  監査との整合を壊すため行わない。値の物理削除が要る場合（個人情報消去）は専用のパージ操作として
  監査付きで実装する（NFR-10 の消去経路に接続）。

### 3.2 フィールド型カタログの拡張（D4）

閉集合 `FieldType` に追加する（既存 12 種は維持・serde 後方互換）:

| 型 | 保存表現 | 検証 | 備考 |
|----|---------|------|------|
| `checkbox` | bool | ─ | filter/sort 可 |
| `url` / `email` | text | 形式検証（書込時） | filter/sort 可 |
| `rating` | number（0..max） | max はフィールド定義（既定 5） | |
| `percent` / `currency` | number | 表示ヒントのみ（`format` 定義）・値は数値のまま保存（PIT-52 と同じ思想: 値と表示を混ぜない） | currency は通貨コードを定義に持つ |
| `auto_number` | number | サーバ採番・書込不可 | テーブル単位の連番（採番はシーケンステーブルで原子的） |
| `attachment` | file_ref の配列 | 各要素を StorageService 経由で存在＋可読検証（既存 file_ref と同じ） | `file_ref` の複数版。表示は成果物カードと同系 |
| `formula` | **保存しない**（read-time 評価） | スキーマ保存時に型検査 | §3.3 |
| `rollup` | **保存しない**（read-time 評価） | スキーマ保存時に参照整合検証 | §3.4 |
| システム | `created_at` / `updated_at` / `created_by` / `updated_by` | 列由来の仮想フィールド・書込不可 | スキーマ宣言不要で全テーブルに常在。ビュー/フィルタから key で参照可（`_created_at` 等の予約 key） |

既存 `record_ref` / `file_ref` に `multiple: bool`（既定 false）を追加し、複数リンク・複数添付を表す
（JSONB は配列保存・参照整合検証は要素ごと）。

### 3.3 formula（閉じた型付き式 AST・D5）

自由式のインジェクション面を作らない、という現行 `ComputedOp`（sum/concat）の思想を保ったまま
表現力を Teable/Excel の常用域まで広げる:

- **正本は AST**（JSON）。UI/AI は式文字列（`if(status == "done", amount * 1.1, 0)` 風）で書き、
  サーバのパーサが AST 化 → **スキーマ保存時に型検査**（各部分式が text/number/bool/date/datetime の
  いずれかに解決・不一致は保存拒否）。関数カタログは閉集合:
  四則・比較・論理、`if` / `coalesce`、`round/floor/ceil/abs`、
  `concat/len/upper/lower/trim/contains/left/right`、`today/now/days_between/add_days`。
- **評価は read-time に Rust で**（クエリ層が取得後に評価）。SQL には一切落とさない
  （SQL 二重実装のセマンティクス乖離＝PIT-54 を v1 で背負わない）。
  評価エラー（0 除算・型不一致 null）は**セル値 null＋エラーマーカー**を応答に含める（黙って null にしない）。
- **filter/sort/group_by/aggregate の対象外**（field_policy マスク除外と同じ機構で強制）。
  索引化したい列は「formula を写した実フィールド＋ワークフロー転記」を案内する。
  将来: SQL コンパイル可能サブセット（決定的・非 now 系）に限り式インデックス化を解禁（PIT-54 の条件付き）。
- 参照可能なのは**自テーブルの実フィールド＋lookup**。formula→formula 参照は深さ 3 まで・循環は保存時拒否。

### 3.4 rollup と双方向リンク（D6）

- `rollup` 定義: `{ source_table, source_ref_field, target_field, op(count/sum/avg/min/max), filter? }`。
  「このレコードを `source_ref_field`（record_ref）で参照している `source_table` の行」を集計する
  （案件 ← 明細の合計、のような backlink 集計）。`filter` は宣言的フィルタのサブセット。
- **権限意味論（最重要）**: 集計対象は**閲覧者本人が source_table の行述語で読める行のみ**
  （PIT-20 の透過適用そのもの）。したがって rollup 値は閲覧者によって異なり得る — これを仕様として
  UI に明示する（「あなたに見える明細の合計」）。読める行だけの集計なので PIT-17 のスモールセル
  抑制は**適用しない**（抑制は「見えない行の存在」を守る機構であり、ここに見えない行は入らない）。
  逆に「全行の合計を権限に関係なく見せたい」需要は rollup では満たさない — それは可視性の穴になる
  （PIT-57）。ワークフローによる転記（サービスプリンシパル権限で計算し実フィールドへ書く）へ誘導する。
- **双方向リンク**: 逆方向（backlink）は保存しない仮想表示とする。レコード詳細 UI が
  「参照元」セクションとして `source_table` を行述語付きでクエリして表示（ページング付き）。
  スキーマにはフィールドとして持たない（保存データの二重化と整合維持を避ける）。
- rollup の走査は source_ref_field の式インデックスを**必須**とする（保存時に強制）。
  走査上限（既定 5 万行）超過は値ではなくエラーマーカーを返す（黙って部分集計しない）。

### 3.5 lookup / computed の既存定義との関係

既存 `Lookup`（via_field 経由の射影）と `Computed`（sum/concat）は維持する。`Computed` は
formula の特殊ケースとして**新規作成を formula へ誘導**し、既存定義は読み替え互換
（`computed(sum, [a,b])` ≡ formula `a + b`）。lookup の解決は従来どおり参照先テーブルの
行ポリシー透過適用（PIT-20）で、formula/rollup と同じ「read-time 評価・filter/sort 対象外」群に入る。

## 4. ビュー（D7）

既存 `artifact(kind=data_view)`（宣言的クエリ＋display・閲覧者権限で毎回再評価）を拡張する。

- `display.kind` を閉集合にする: `grid` / `kanban` / `gallery` / `calendar` / `form`。
  サーバは kind と設定スキーマを検証する（現行「サーバは解釈しない」から**検証はする**へ強化。
  描画自体はフロントの信頼カタログ）。
- 共通設定: 表示フィールド（key 配列・順序）・フィルタ・ソート・グループ化（1 段）・行高。
  マスク対象フィールドはビュー設定に含まれていても**サーバ応答から常に落ちる**（既存保証のまま）。
- kind 別設定: kanban=グループ化フィールド（select/status）・カード表示フィールド／
  calendar=日付フィールド（date/datetime）／gallery=カバー画像（attachment）／
  form=入力フィールド集合・順序・説明文・既定値・必須の**強化のみ**（スキーマの required を緩められない）。
- **form ビュー = 作成専用の入力面**: 送信は通常の record create（送信者本人の AuthContext・
  行ポリシー/検証/監査は通常経路のまま）。「テーブルは読めないがフォーム送信はできる」を成立させるため、
  OpenFGA `data_table` に **`submitter`** relation を追加する（viewer を含意しない・create のみ許可
  ・自分が作った行の読取可否は行ポリシー次第）。匿名/社外公開フォームは**スコープ外**
  （PIT-46 の安全包絡と同種の設計が別途要る・将来イシュー）。
- ビューはテーブルと独立に ReBAC 共有できるが、**実行は常に閲覧者本人のテーブル権限 ∩ ビュー定義**
  （ビュー共有はテーブル可読性を付与しない・既存どおり fail-closed）。

## 5. 書込・整合・ライブ更新

### 5.1 書込セマンティクス（既存の再確認＋バッチ）

- 単一レコード: 現行どおり `rev` 楽観ロック（409）・フィールド単位 changelog・FSM ガード
  （status 直書き禁止・遷移 API のみ）。
- **バッチ API を新設**: `create/update/delete` を混載できる ops 配列（上限 1,000）。
  `atomic: true`（全部成功 or 全部失敗・単一 Tx・エージェント/フォーム向け）と
  `atomic: false`（op ごとに結果を返す・インポート/ワークフロー向け）を選べる。
  **冪等キー**（呼出側供給・エンジン供給）をチョークポイント側で消費して at-least-once 再試行を
  重複排除する（PIT-31 の data 適用・workflow ノードと同一機構）。
- 削除は既定でリビジョン履歴に残る論理削除＋ごみ箱（30 日・復元可）。物理パージは監査付き管理操作。

### 5.2 ライブ更新（D8・PIT-53）

グリッド/ビューを開いている間の他者編集反映は次で実現する:

1. record 書込・遷移・スキーマ変更は既存 outbox イベント（`data.record.created/updated` 等）を発行済み。
   relay がテーブル単位のライブ配信チャネル（Redis pub/sub・チャット run のイベント配信と同型）へ fan-out。
2. クライアントは `GET /data/tables/:id/events`（SSE）を購読。**配信ペイロードは
   `{seq}` の粗い変化通知のみ**（record id・フィールド・値を一切含めない）。デバウンス ≥1s。
3. 受信したクライアントは表示中のページ/ビューを通常のクエリ API で再フェッチする。
   行述語・マスクは**再フェッチ時に必ず評価される**ため、push 経路に認可判定を持ち込まない。
4. 購読開始時に viewer relation をチェックし、以降 **60 秒ごとに再チェック**（剥奪で切断・PIT-37 と同型）。

「record id を push しない」のは性能ではなく認可の要請: id を流すと行述語で見えない行の存在・更新頻度が
漏れる（存在オラクル）。粗い通知＋再フェッチは帯域を犠牲にする代わりに、認可判定点をクエリ
チョークポイント 1 箇所に保つ（PIT-53 に固定）。CRDT は採らない（行データの編集単位はレコード＋rev で
十分・Yjs はドキュメント系の機構）。セル単位の編集競合はフィールド単位 changelog があるため、
409 時に「他者変更フィールドと自分の変更フィールドが素であれば自動リベース」をクライアントで行える。

## 6. 消費面の統一契約（D9）

**全消費面が `crates/data` の同一チョークポイント（述語・マスク・FSM・監査・クォータ）を通る。**
語彙（能力名・ツール名・スコープ）は codegen 認可語彙の単一定義に追加する（design §4.1）。

| 消費面 | 面の形 | 認可の式 | 状態 |
|--------|--------|---------|------|
| グリッド/ビュー UI | `crates/api` routes/data（拡張） | 本人 ReBAC（テーブル relation ＋ 行述語 ∩ マスク） | 既存 API を UI 要件（keyset・バッチ・SSE）へ拡張 |
| チャット（agent-core ツール） | `data_list_tables` / `data_get_schema` / `data_query` / `data_get` / `data_create` / `data_update` / `data_delete` / `data_transition` / `data_create_table` | 発話ユーザー本人の AuthContext（昇格なし）。書込系は承認ゲート対象（承認 3 モードの既存写像に従う）。read 系は `is_read_only` 表明で並列実行（#349） | **新規** |
| generative UI | カタログに `table`（保存ビュー埋め込み/インライン一覧）と `record_form`（作成フォーム）を追加。データ束縛は宣言的アクション（`data.query` / `data.record.create`）のみ | 閲覧者本人 ReBAC（アンビエント権限なし・既存原則） | **新規** |
| ワークフロー | ノード `data.query` / `data.record.create` / `data.record.update` / `data.transition`（IR 語彙は定義済み） | 実行主体（本人 or 委譲プリンシパル）∩ 宣言スコープ ∩ ノード設定・engine-dedup 冪等 | 語彙のみ実装済み → 実行器を実装（Phase 10 Stage B 残） |
| shiki script | `Shiki.data.query/get/create/update/transition/list_tables`（allowlist 定義済み） | 実行主体の AuthContext（ホスト関数ブリッジ→能力ゲートウェイ） | allowlist のみ → ブリッジ実装 |
| ミニアプリ（gateway） | 能力 `data.read/write/schema`（実装済み） | アプリスコープ ∩ ユーザー ReBAC（二重ゲート） | 実装済み |

### 6.1 チャットツールの設計注意

- `data_query` の結果は**ページ上限（既定 50 行）とフィールド射影**を必須にし、LLM コンテキストへ
  全件を流し込まない。集計が要る問いは aggregate を誘導する（ツール description に明記）。
- `data_create_table` は AI が生成した `table_schema` を**閉じた語彙で検証してから**作成する
  承認ゲート対象ツール（genui スペック・workflow IR と同じ「検証済みスペック」パターン）。
  存在しないフィールド型・不正な formula・参照整合違反は保存前に拒否され、エラーが自己修正の
  材料としてモデルへ返る。
- ツール結果には `document_refs` と同型の**テーブル/ビュー参照カード**（`table_ref`）を返し、
  チャットから「開く」でグリッド UI へ遷移できるようにする（office の成果物カードと同じ配線）。

### 6.2 genui のデータ束縛

`table` / `record_form` コンポーネントのデータ源は**宣言済みアクション ID のみ**（既存の
ActionBinding 機構）。スペックに生のテーブル id フィルタを書いても、実行は閲覧者本人の
ReBAC で毎回評価される（作成者権限を引き継がない・保存ビュー実行と同一保証）。

### 6.3 エクスポート/インポートも同一チョークポイント

エクスポート（CSV/xlsx）は宣言的クエリのストリーミング実行として実装する。**マスク対象フィールドは
出力から除外・行述語適用済み・全件が監査に `data.export` として残る**。「UI では見えないが
エクスポートには入る」を構造的に不可能にする。インポートは §8。

### 6.4 FSM・ワークフロー接続（既存決定の再確認）

status 遷移は遷移 API のみ（エンジン直書き禁止）・遷移コミット→outbox→ワークフロートリガ、は
miniapp-platform §1 の既決定のまま。本設計で足すのは「グリッド UI/チャットからの遷移も同じ API を
叩く」配線だけで、新しい状態機構は作らない。

### 6.5 スプレッドシート関数との関係

shiki script の「3 つの顔」のうちスプレッドシート用途（FR-13）は CSV/シート側の将来トラックのまま。
テーブルの formula は §3.3 の閉じた AST であり **script ではない**（ユーザーコードの実行面を
テーブル読取経路に作らない）。テーブルを script から操作するのは `Shiki.data.*` の役割。

### 6.6 ミニアプリからの既存テーブル参照

マニフェストに `table_refs`（既存スタンドアロンテーブルへの参照宣言・read/write 別）を追加する。
インストール同意画面が対象テーブルを明示し、同意時に**アプリスコープを当該テーブルへ資源束縛**する。
実行時は従来どおり二重ゲート（スコープ ∩ 呼出ユーザー ReBAC）なので、アプリに参照を許しても
本人が読めないテーブル/行には到達できない。アンインストールで束縛を撤去（所有テーブルと違い
データは残る）。

## 7. スキーマ進化（D10）

AI とパワーユーザーが頻繁にスキーマを触る前提で、**許可される変更を閉集合**にする:

| 変更 | 扱い |
|------|------|
| フィールド追加 | 常に可（既存行は null・required 追加は default 供給時のみ） |
| label / options 追加 / format / 説明 | 常に可（メタデータのみ） |
| select の選択肢削除・rename | 使用中の値がある場合は**値の写像（old→new）を必須**にし、backfill ジョブで書換（リビジョンは `schema_migration` として 1 括記録） |
| 型変更 | **安全変換行列のみ**: text→select（既存値が選択肢に収まる場合）・text→url/email（全行検証通過時）・number→rating/percent/currency・単一→複数（record_ref/file_ref）。それ以外（number→text 等の非可逆・意味変更）は「新フィールド追加＋転記」を UI/AI が案内し、直接変更は拒否 |
| indexed/unique 変更 | 索引ジョブ（下記）。unique 追加は既存重複の検査が通った場合のみ |
| フィールド削除 | 論理削除（§3.1） |
| formula/rollup/policy 変更 | スキーマ検証（型検査・参照整合・循環）を通った場合のみ。row_policy の緩和方向の変更は監査に明示イベントで残す |

- **backfill・索引構築は jobq ジョブ**: 小テーブル（既定 1 万行未満）は同期、以上は非同期ジョブ。
  `data_index_registry` に状態機械（`pending/building/ready/failed`）を追加し、`CREATE INDEX
  CONCURRENTLY` で本番負荷中もロックしない。**ready になるまで当該フィールドの索引前提クエリ
  （大テーブルの filter/sort）は解禁しない**（§2.1 のガードがそのまま効く）。
- スキーマ変更は `schema_version` インクリメント＋変更差分を artifact 的に履歴保存（誰が・いつ・何を）。
  ミニアプリ所有テーブルのスキーマはマニフェスト版更新経由（既存）・スタンドアロンは直接編集。

## 8. インポート / エクスポート

- **インポート（CSV/xlsx → テーブル）**: ①ファイルを StorageService 経由で受領 ②サンプル行から
  スキーマ推定（AI 支援は任意・確定は人間）③列マッピング UI ④jobq ジョブとして chunk（1,000 行）
  単位の `atomic:false` バッチ書込。**ジョブは冪等**（`(import_id, 行番号)` を冪等キーに・PIT-56）で、
  途中失敗は再開可能。行単位のエラーレポート（検証失敗・参照不整合）を成果物として保存。
  上限: 100 MiB / 100 万行。実行主体はインポートした本人（行 owner・created_by も本人）。
- **エクスポート**: §6.3。ストリーミング CSV（xlsx は既存 DocumentGenerator）。
- **CSV エディタとの導線**: CSV ファイルを開いた画面に「テーブルへ変換」、テーブル側に
  「CSV へエクスポート」を置き、§1.3 の役割分担をユーザーが行き来できるようにする。

## 9. クォータ既定値（PaaS ガードレール）

全て tenant 管理者が引き下げ可能・引き上げはプラン上限まで。超過は fail-closed（明示エラー）。

| 対象 | 既定値 |
|------|--------|
| フィールド数 / テーブル | 200（うち formula+rollup+lookup 合計 50） |
| 索引フィールド数 / テーブル | 20 |
| テーブル数 / テナント | 1,000 |
| レコード JSONB サイズ | 256 KiB |
| バッチ ops / 呼出 | 1,000 |
| クエリページ長 | 既定 50・上限 200 |
| rollup/backlink 走査 | 5 万行（索引必須） |
| formula 深さ / 参照数 | 3 / 16 |
| インポート | 100 MiB / 100 万行 |
| レート制限 | テナント×能力のトークンバケット（workflow-engine の既存機構を data 面へ適用） |

## 10. 認可・監査の総括

| 面 | 権限の式 |
|----|---------|
| グリッド/ビュー/エクスポート | テーブル relation（viewer/editor/owner/**submitter**）∩ 行述語 ∩ マスク |
| チャットツール | 発話ユーザー本人（昇格なし）＋書込は承認ゲート |
| genui | 閲覧者本人（宣言的アクション経由のみ） |
| ワークフロー | 実行主体（本人 or 委譲）∩ 宣言スコープ ∩ ノード設定 |
| script | 実行主体（ホスト関数→能力ゲートウェイ） |
| ミニアプリ | アプリスコープ（所有＋table_refs 束縛）∩ ユーザー ReBAC |
| lookup/rollup/backlink | 参照先テーブルの行述語を閲覧者本人で透過適用（PIT-20/D6） |

監査は既存 `data.*` 計装（Task 9.15）に `data.export` / `data.import` / `data.schema_change`
（緩和方向は要注意フラグ）/ ライブ購読の開始・剥奪切断を追加。全て trace_id で Langfuse と突合可能。

  data/            # 拡張の主戦場: field key/label・型カタログ・formula/rollup 評価器・
