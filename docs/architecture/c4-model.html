shiki C4 アーキテクチャ

権限考慮 RAG・自律エージェント・ミニアプリ基盤を備えるエンタープライズ AI プラットフォームを、C4 モデルの 3 階層（コンテキスト・コンテナ・コンポーネント）と 1 枚の動的図で示す。

基準: main@5313f22（2026-10-10）。出典は docs/design.md・deploy/compose/docker-compose.yml・crates/*/Cargo.toml。設計の正本は docs/ 側で、本ページはその図解。

単一チョークポイント

ストレージは StorageService、認可は OpenFGA クライアント、LLM は llm-gateway を必ず通る。

アンビエント権限の禁止

全データアクセスは AuthContext { principal, org, tenant_id } 経由。

二段 authz

RAG は pre-filter と post-filter の両方を通す。片方が壊れても権限は守られる。

オンプレとクラウドの差はトレイト実装だけで吸収し、本体は分岐させない。

LEVEL 1

システムコンテキスト

shiki を 1 つの箱として、誰が使い、何に依存するかを示す。社員の ID の正本は顧客 IdP にあり、shiki は Keycloak を介してフェデレートする。推論はオンプレではローカル vLLM、SaaS では外部 API に向く。

LEVEL 2

コンテナ

コアは単一バイナリの shiki-server。特権や重い依存を要するもの（サンドボックス制御・DuckDB・Python パーサ）だけを別プロセスに出し、それらには資格情報を渡さない。データストアへ接続するのは shiki-server だけである。

LEVEL 3

コンポーネント: shiki-server

shiki-server 内のクレートを 4 層に分けた。ドメイン層は永続化・認可・LLM 呼出を自前で持たず、必ず単一チョークポイントの層を経由する。層間の矢印は集約表示で、個々の依存は下の表に示す（Cargo.toml の path 依存から抽出）。

DYNAMIC

動的図: RAG 付きチャットの 1 往復

チャット送信はすぐ 202 を返し、生成は jobq 上の run としてサーバ側で続く。ページを離れても生成は止まらない。オレンジの矢印が二段 authz で、pre-filter（ListObjects による可読集合）と post-filter（rerank 前の file 粒度 check）のどちらか一方が壊れても読めない文書は引用されない。

NOTE

設計書との差分

図は現行コード（crates/・compose）に合わせた。次の点は docs/design.md の記述と食い違っているため、設計書側の更新を検討したい。

  • §5 のリポジトリ構成にある crates/sandbox-wasm/ と crates/site/ は存在しない。wasm ティアは sandbox-orchestrator が spawn する secure-exec sidecar（vendor/secure-exec）で実装されている。
  • §5 に無いクレートが存在する: artifact・durable・gui・jobq・jtd・websearch・sandbox-netns・sandbox-agent-proto・sandbox-guest-agent・sandbox-bench。
  • §2 の全体図では ingestion-worker が Qdrant・Tantivy に書く矢印になっているが、実装では worker は /parse・/embed・/rerank・/edit を提供するだけで、索引への書込は shiki-server の rag が行う。
  • §2 では script-runtime を「別プロセス」としているが、現行の配線（api/src/wiring_gateway.rs）は ScriptEngine を in-process で生成している。gRPC サーバ実装（script-runtime/src/server.rs）は別プロセス化用に存在する。
