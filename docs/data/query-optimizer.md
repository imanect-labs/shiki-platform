# 構造化データ v2 のクエリオプティマイザ（自前プランナ）

> 位置づけ: [data-platform.md](../data-platform.md) §3.5（クエリの形）・§5（クエリ IR）・§14（統計）・
> §16.2（最適化層）の詳細設計。実装は [Phase 15](../roadmap/phase-15.md) の Task 15.3（最小構成 O1）と
> Task 15.12（O2・O3）。落とし穴は [PIT-69](../design-caveats.md)（駆動索引の誤選択）・
> PIT-75（統計のサイドチャネル）・PIT-76（書き換えと適応切替の正しさ）。

## 0. 結論

- **プランナは自前で持ち、実行は Postgres に任せる。** 自前にするのは「どの索引から入り、どの順で絞り、
  どこで打ち切るか」（アクセスパスと結合順）だけで、索引走査・ソート・集約の実行エンジンは作らない。
- 効くのは平均ではなく**裾（p99）**である。pivot 索引では駆動の選び方ひとつで桁違いの差が出る
  （§1.2 の試算で 100〜1000 倍、§1.3 の実測で 17〜61 倍。逆向きの決め打ちでは 1 万倍超）。
  自前プランナの価値は「平均を 2 割速くする」ことではなく「最悪ケースを 1〜2 桁潰す」ことにある。
- 構成は 4 本柱: ①テーブル×フィールド単位の**自前統計** ②閲覧者の認可材料まで含めた**コストベースの戦略選択**
  ③推定が外れても損失を抑える**予算付きの適応切替** ④Postgres に別の計画を選ばせない**プランナ耐性 SQL**。
- 安全側の不変条件を 2 つ足す。**最適化は認可述語を弱めない**（型で強制）と、
  **本体取得後に行述語を Rust 側で独立に再評価する**（オプティマイザの誤りを漏洩ではなく欠落に倒す）。

## 1. なぜ Postgres のプランナに任せられないか

### 1.1 構造的な理由

| 理由 | 中身 |
|---|---|
| **統計の粒度が合わない** | `data_index_text` の統計は「プール全体」のもの。「テーブル T のフィールド F で `val = '承認待ち'` が何件か」を Postgres は知らない。拡張統計（`CREATE STATISTICS`）も relation 単位で、`(table_int, field_id)` の切片には効かない |
| **閲覧者ごとに最適が変わる** | 同じクエリでも、全行が見える管理者と 1% しか見えない担当者では最適な駆動が違う。Postgres から見れば行述語は「`ANY($n)` の配列が長いか短いか」でしかなく、汎用プランではその差も消える |
| **汎用プラン** | sqlx は prepared statement を使う。Postgres は 6 回目以降に汎用プラン（パラメータ値を見ない計画）へ切り替え得るため、値に依存した選択が効かなくなる |
| **`ORDER BY … LIMIT` の病理** | 「ソート索引を歩いてフィルタで捨て、`LIMIT` で止める」計画は、フィルタの選択率を楽観すると索引を延々と歩く。Postgres で古くから知られる問題で、pivot ではフィルタが全部 `EXISTS` になるため常に起き得る |
| **半結合の数** | 条件木の葉がそれぞれ `EXISTS` になる。`join_collapse_limit`（既定 8）・`geqo_threshold`（既定 12）を超えると結合順の探索が打ち切られたり遺伝的探索になったりして、計画が実行ごとに揺れる |

### 1.2 差の大きさ（試算）

前提: 100 万行のテーブル、1 ページ 20 行。単価は §5.2 の初期値（索引タプル 1µs・点検索 5µs・本体取得 10µs）。
**数値は計画選択の差を示すための試算で、実測ではない**（Task 15.12 のベンチで置き換える）。

| ケース | ソート索引から入る | フィルタ索引から入る | 比 |
|---|---|---|---|
| ① `状態=承認待ち`（300 行・0.03%）を金額順 | 約 6.7 万エントリを歩く ≈ 400ms | 300 行を拾って並べ替え ≈ 3ms | 約 130 倍 |
| ② `状態=完了`（90%）を金額順 | 22 エントリで止まる ≈ 0.2ms | 90 万行を拾う ≈ 5s 超 | 約 25,000 倍（逆向き） |
| ③ 見える行が 0.01%（100 行）の利用者がフィルタなしで更新日順 | 20 万エントリ × 述語検査 ≈ 1s 超 | 行述語の和集合から入る ≈ 1ms | 約 1,000 倍 |
| ④ `状態=未着手`（5%）を作成日の古い順。ただし未着手は新しい行に偏っている | 独立性の仮定では 400 エントリ（≈2.4ms）のはずが、実際は約 95 万エントリ ≈ 5.7s | 5 万行を拾う ≈ 0.3s | 推定どおりならソート駆動が正解だが、実際はフィルタ駆動の約 19 倍遅い |

①と②は同じクエリの値違いであり、**どちらか一方に決め打ちした実装は必ずどちらかで破綻する**。
③は認可材料で最適が変わる例、④は統計が正しくても相関で推定が外れる例で、④への備えが §6 の適応切替になる。

### 1.3 実測（ローカル PostgreSQL 16・2026-10）

上の試算を、§3.3 と同じ形の pivot 表（ハッシュ 16 分割）で確かめた。対象テーブル 100 万行に加え、
**別テナントの 40 テーブルに `状態=承認待ち` を計 100 万行**入れてある（プール全体の統計を汚す雑音）。
キャッシュが温まった状態の 1 回計測で、性能目標の判定ではなく**計画の差の桁を確かめるため**のもの。

| ケース | Postgres 任せ（素朴な `EXISTS`） | 自前で固定した計画 | 備考 |
|---|---|---|---|
| ① 承認待ち 300 行を金額順 20 件 | **373 ms**（ソート索引を並列で 12.8 万行歩いた） | フィルタ駆動 **6.1 ms** | 約 61 倍。雑音テナントの「承認待ち」で、Postgres は承認待ちを多いと見積もった |
| ② 完了（95%）を金額順 20 件 | **0.6 ms**（ソート駆動・21 行で停止） | フィルタ駆動に決め打ちすると **8,375 ms** | 決め打ちが破綻する側。ここはソート駆動が正解 |
| ③ 担当=user5（0.05%）だけ見える利用者・作成日の新しい順 | 13.7 ms（ハッシュ半結合を選べた） | 認可駆動 5.8 ms | `user5` がプール中でこのテーブルにしか無いため、偶然プール統計が正しかった |
| ④ 未着手（5%・新しい行に偏る）を作成日の古い順 | **4,566 ms**（95 万行歩いた） | フィルタ駆動 **268 ms** | 約 17 倍。相関で外れる典型 |
| ①を予算付きソート駆動で | — | 走査予算 2,000 で打ち切りまで **7.4 ms** → 切替後のフィルタ駆動 6.1 ms | 合計 約 14 ms。推定を誤っても桁は外さない（§6.2） |

- Postgres は**いつも間違えるわけではない**（②③）。問題は、正しく選べるかどうかが**他テナントのデータ分布という
  制御できない要因**で決まることにある。①の誤りは対象テーブルではなく雑音テナントが原因だった
- `OFFSET 0` を入れた `EXISTS` は半結合に引き上げられず、行ごとの SubPlan として残ることを確認した（§6.1）

### 1.4 作らないもの

| 作らない | 理由 |
|---|---|
| 実行エンジン（自前の走査・結合・集約） | Postgres の索引走査・ソート・集約は十分速い。外す必要があるのは計画選択だけ |
| `pg_hint_plan` 依存 | 拡張の有無が環境に依存する（オンプレ・マネージドの差）。データプラットフォーム §15.1 の「Postgres の飛び道具に賭けない」方針に反する |
| Cascades / Volcano 型の汎用最適化フレームワーク | 計画空間が小さい（単一テーブル＋半結合＋リンク）。戦略を列挙して全部の費用を測るので足りる。計画時間は 1ms 未満を目標にする |
| 学習型（ML）カーディナリティ推定 | 説明可能性と再現性を優先する。学習は「補正係数」に留める（§8） |

## 3. 意味論の固定と正規化

オプティマイザは式を書き換える。書き換えが正しいと言うには、まず「その式が何を意味するか」が
決まっていなければならない。**v2 の文書は `Not` を許しているが、値の欠損（null）と多値列での意味を
まだ定めていない**。ここで固定する。

### 3.1 2 値論理を採る（workflow IR に合わせる）

`data.query` ノードは workflow IR の `Condition` を変換なしで渡す（data-platform §5.1）。その workflow IR の
評価器（`crates/workflow-engine/src/control/eval.rs`）は **2 値論理**で、`Neq` は欠損値に対して真になり、
`Not` は単純な真偽の反転である。data 側が SQL の 3 値論理を採ると、**同じ条件がワークフローの分岐と
`data.query` で別の行を選ぶ**ことになる。

→ **IR の意味論は 2 値論理に統一する。** 各レコードのフィールドは「値なし」または「値の集合」（単値なら要素 1 個）
で、比較は次のとおり定義する。

| 演算子 | 単値フィールド | 多値フィールド（`multi_select`・`link`） | 値なし |
|---|---|---|---|
| `Eq c` | 値 = c | c を含む | 偽 |
| `Neq c` | `Not(Eq c)` と同じ | c を含まない | **真** |
| `In [..]` | いずれかに等しい | いずれかを含む | 偽 |
| `Lt` / `Lte` / `Gt` / `Gte` | 通常の比較 | **使えない**（スキーマ検証で 422） | 偽 |
| `StartsWith` / `Contains` / `EndsWith` | 文字列判定 | いずれかの要素が満たす | 偽 |
| `Exists` | 値がある | 要素が 1 個以上 | 偽 |
| `IsNull` | `Not(Exists)` | `Not(Exists)` | 真 |
| `Not X` | X の補集合 | X の補集合 | — |

- これで **`Not(Eq c) ≡ Neq c`、`Not(Exists) ≡ IsNull` が全型で成り立つ**。否定の押し下げ（§3.2）が型を見ずに書ける
- 比較の否定は値なしを含む: `Not(Lt c) ≡ Gte c ∨ IsNull`
- **SQL 前段（§16.1）は 3 値論理の SQL を 2 値論理の IR へ翻訳する。** `f <> c` は `Exists f ∧ Neq c`、
  `NOT (f < c)` は `Gte c`（`IsNull` を足さない）になる。翻訳表は `crates/data/src/sql/` に 1 箇所だけ置き、
  TLP テスト（§9.2）で SQL 経路と IR 経路の一致を確かめる
- `row_policy`（`PolicyExpr`）は従来どおり `Not` を持たない。この非対称は data-platform §5.1 の注のとおり意図的

> ⚠️ **これは公開 API の意味論の決定であり、human の確認が要る。** 3 値論理を採る案もあり得るが、
> その場合は `data.query` ノードに IR → data の翻訳層が必要になり、「変換層が不要」という §11 の前提が崩れる。

### 3.2 正規化の規則

適用順に並べる。**どの規則も意味を変えない**ことが条件で、§9 の差分テストで 1 規則ずつ検証する。

1. **否定の押し下げ（NNF）**: §3.1 の表で `Not` を葉まで降ろす。`Not(All[a,b]) → Any[Not a, Not b]`
2. **平坦化・重複除去**: `All[All[a,b],c] → All[a,b,c]`、同一の葉を 1 つに
3. **定数畳み込み**: `HasRole` は材料解決後に TRUE/FALSE（v1 と同じ）。`All[.., FALSE] → FALSE`、
   `Any[.., TRUE] → TRUE`。**行述語 P 全体が FALSE になったらクエリを実行せず空を返す**
4. **同一フィールドの併合**: `Any[Eq a, Eq b] → In[a,b]`、`All[Gte 10, Lt 20] → Range[10,20)`、
   単値フィールドの `All[Eq a, Eq b]`（a≠b）→ FALSE。多値フィールドでは `All[Eq a, Eq b]` は矛盾ではない
   （a と b の両方を含む）ので併合しない
5. **`StartsWith p` を範囲に**: `Range[p, succ(p))`。`COLLATE "C"` のバイト順なので後続文字列が機械的に作れる
6. **否定の範囲化**: `Neq c`（単値）は索引で引けない。駆動候補から外し、検査（probe）側でだけ使う

### 3.3 認可述語との合成

正規化後の条件 `Q` と行述語 `P`（`row_policy` ∨ 個別共有）を `Q ∧ Guard(P)` に合成する。
`Guard` の扱いは §7.1。**正規化は `Q` の内部にだけ掛け、`P` には定数畳み込みと平坦化以外を掛けない**
（`P` の書き換えを増やすほど、認可の正しさを示す範囲が広がる）。

## 4. 統計とカーディナリティ推定

### 4.1 統計の種類

| 統計 | 単位 | 中身 | 更新 | 用途 |
|---|---|---|---|---|
| **行数** | テーブル | `n_rows`（正確） | outbox 消費側で増減（非同期・数秒遅れ） | 全推定の分母 |
| **値頻度表** | テーブル × フィールド × 値 | 値ごとの件数（正確） | outbox 消費側。**種類数が上限（既定 1,024）以下のフィールドだけ** | `select` / `status` / `user_ref` / `owner` 擬似列の `Eq` / `In`——最頻出のフィルタと行述語の大半 |
| **フィールド統計** | テーブル × フィールド | 値を持つ行数・異なり数・最頻値 100 件・等深ヒストグラム 100 区間・切り詰め率・平均要素数（多値） | 統計収集ジョブ（§4.2） | 範囲・前方一致・高異なり数の `Eq` |
| **リンク統計** | リンク列 × 方向 | 平均・最大ファンアウト、リンクを持つ行の割合 | 同上 | リンク経由の条件・ロールアップ |
| **行幅** | テーブル | 本体の平均バイト数・TOAST 率 | 同上 | covering read の判定（§16.5） |
| **補正係数** | テーブル × （フィルタ列, ソート列） | 推定に対する実測の比（指数移動平均） | §8 | 相関の補正（§1.2 ④） |

格納は `data_table_stats` / `data_field_stats` / `data_value_count` / `data_link_stats` の 4 表。
いずれも `tenant_int` / `table_int` を先頭に持ち、**purge 経路と tenant スコープの CI ゲート（Phase 12.9）の対象に入れる**。

> **値頻度表を書込 Tx で更新しない理由**: 人気の値（`状態=未着手`）の 1 行に全書込が集中し、行ロック待ちで
> 書込スループットが落ちる。outbox 消費側でバッチにまとめ、`INSERT … ON CONFLICT DO UPDATE SET cnt = cnt + excluded.cnt`
> で反映する。**冪等性は消費位置（`delivery_seq`）で担保する**（同じバッチを二度足さない）。

### 4.2 統計収集ジョブ

- 起動条件は Postgres の autoanalyze と同じ形にする: **前回収集からの変更行数 > 50 + 0.1 × `n_rows`**。
  加えて ①索引の昇格完了時（§10）②フィードバックで推定外れが続いたとき（§8）
- ヒストグラムは**値索引を値順に読むだけで作れる**（`(tenant_int, table_int, field_id, val, record_id)` の範囲走査）。
  100 万行までは全件を読む。それを超えたらその行数に比例したサンプリングに切り替える
- jobq のバッチジョブとして動かし、**テナントの公平性の枠（§16.8）で消費する**。重いテナントの統計収集が
  他テナントの読取を圧迫しないようにする

### 4.3 計画時の上限付き件数探索

統計が無い・古い・信頼度が低い述語は、計画時に**上限付きの件数**を直接数える。

```sql
SELECT count(*) FROM (
  SELECT 1 FROM data_index_text
  WHERE tenant_int = $1 AND table_int = $2 AND field_id = $3 AND val = $4
  LIMIT $cap            -- 既定 1,000
) s;
```

上限内なら正確な件数、上限に達したら「cap 以上」と分かる。駆動の選択に必要なのは
「数百件か、数十万件か」の区別なので、上限 1,000 で十分に判定できる。
1 回 1ms 未満で、**計画 1 回あたり最大 3 本**（候補上位の述語と、認可駆動を検討するときの行述語の選言）に制限する。

- 結果は `(テーブル, フィールド, 述語)` をキーに**プロセス内で短時間（既定 60 秒）キャッシュしてよい**。
  統計は全員共通で権限を表さないので、PIT-18 の「材料をキャッシュしない」の対象外である
  （ただし利用者へ返さない・PIT-75）
- **O1（§10）は統計表を持たず、この探索とキャッシュだけで戦略を選ぶ。** 値頻度表は outbox 消費側
  （Task 15.6）を要し、15.3 の時点では存在しないためである。それでも判定が成り立つ理由:
  候補の件数 c が上限内なら、フィルタ駆動のコストは c で直接決まり、上限 1,000 なら高々 10ms 程度で済む。
  上限を超えたなら絶対数として絞れていないので、ソート駆動を予算付き（§6.2）で走らせ、
  予算を使い切ったら切り替えればよい。行数 n が分からなくても、この 2 分岐と予算で最悪ケースは抑えられる

### 4.4 推定式

| 述語 | 推定 | 信頼度 |
|---|---|---|
| `Eq c`（値頻度表あり） | `cnt(c) / n_rows` | 正確 |
| `Eq c`（最頻値に含まれる） | `freq(c)` | 統計 |
| `Eq c`（それ以外） | `(1 − Σ最頻値の頻度) / (異なり数 − 最頻値の数)` | 統計 |
| `In [..]` | 各要素の和（単値）。多値は `1 − Π(1 − sᵢ)` | 要素の最弱 |
| `Range` / `StartsWith` | ヒストグラムの区間内を線形補間 | 統計 |
| `Contains` / `EndsWith` | 固定値 0.01。必要なら §4.3 で探索 | 推測 |
| `Exists` / `IsNull` | 値を持つ行の割合／その補数 | 統計 |
| `Neq` / `Not X` | `1 − s(X)` | X に同じ |
| `All[..]` | **指数バックオフ**: 選択率の小さい順に `s₁ · s₂^(1/2) · s₃^(1/4) · …` | 最弱 |
| `Any[..]` | `1 − Π(1 − sᵢ)`（同一フィールドの `In` は §3.2 で併合済み） | 最弱 |
| `IsOwner` / `owner = me` | owner 擬似列の値頻度表 | 正確 |
| 個別共有 `id ∈ S` | `\|S\| / n_rows`（材料から正確に分かる） | 正確 |

- `All` を単純な積にしないのは、業務データの条件が独立でないことの方が多いからである
  （`部門=営業 ∧ 担当=佐藤` は積よりずっと大きい）。積は過小推定に倒れ、過小推定は
  「ソート索引から入って延々と歩く」という最悪側の選択を招く。バックオフはその偏りを弱める
- 推定は点ではなく**区間 [lo, hi] と信頼度**で持つ。§5.3 の頑健な選択がこれを使う

## 5. 戦略とコストモデル

### 5.1 戦略

主要な形は「条件 `Q ∧ P`・ソート `S`（k キー）・`LIMIT L`・カーソル `C`」である。戦略は次の 5 つ。

| 戦略 | 入口 | 早期終了 | 向く場面 |
|---|---|---|---|
| **ソート駆動** `SortDrive(S₁)` | 第 1 ソートキーの値索引をカーソル位置から歩き、各行で残りの述語を点検索 | ✅ | 条件の選択率が高い（多くの行が通る） |
| **フィルタ駆動** `FilterDrive(f)` | 条件のうち索引で引ける 1 項 f の範囲を拾い、残りを点検索、ソート値を引いて上位 L 件 | ❌（候補を全部見る） | f が十分に絞れる |
| **認可駆動** `PolicyDrive` | 行述語の各選言（`owner = me` の範囲・`部門 ∈ D` の範囲・共有 id 列）の和集合から入る | ❌ | 見える行がごく少ない利用者（§1.2 ③） |
| **交差駆動** `IntersectDrive(f, g)` | 等値条件 2 つの範囲を `record_id` 順で突き合わせる（等値範囲は `record_id` 順に並んでいる） | ❌ | 各条件は中程度だが、両方を満たす行が少ない |
| **複合索引駆動** `CompositeDrive` | 材料化済みの複合索引（§5.3）を歩く | ✅ | 複数ソートで第 1 キーの同値群が大きい |

> 認可駆動は Salesforce の説明にある「利用者が見られる行が少ないときは共有表から入る」と同じ発想で、
> **Postgres のプランナには材料の大きさが見えないので原理的に選べない**。自前プランナで取れる利得の中で最も大きい。

**任意列（null あり）でのソートは 2 区間に分けて歩く。** data-platform §3.5 では「システム擬似列から入って
`LEFT JOIN` し `NULLS LAST`」としていたが、これだと早期終了が効かない。代わりに:

1. **区間 1**: ソート列の値索引を値順に歩く（値を持つ行だけが値順に並んでいる）
2. **区間 2**: 区間 1 を使い切ったら、擬似列 `created_at`（`field_id = 1`）を**主キー順＝`record_id` 順**に歩き、
   「ソート列の値が無い」ことを点検索で確かめる

`NULLS LAST` なら先頭ページはほぼ必ず区間 1 で埋まるので、**任意列でも早期終了が効く**。
カーソルには区間番号を入れる（§6.3）。`NULLS FIRST`・降順は区間の順番と走査方向を入れ替える。

### 5.2 コストモデル

コストは**予測レイテンシ（µs）**で表す。抽象的なコスト単位にしないのは、§5.4 の受付制御と
`statement_timeout` の判断にそのまま使うためである。

| 単価 | 意味 | 初期値 |
|---|---|---|
| `c_tuple` | 索引の範囲走査 1 エントリ | 1 µs |
| `c_probe` | 点検索 1 回（PK 降下＋可視性確認） | 5 µs |
| `c_fetch` | 本体 1 行の取得（TOAST 展開を含まない） | 10 µs |
| `c_detoast` | TOAST された本体 1 行の展開 | 行幅から算出 |
| `c_sort(n, L)` | n 件から上位 L 件 | `n · log₂L · 0.05 µs` |
| `c_rtt` | DB 往復 1 回 | 300 µs |

初期値は仮置きで、**起動時の較正ベンチ**（既知のデータで各操作を計測）で環境ごとに置き換える。

主要な戦略の式（`n` = 行数、`s(X)` = X の推定選択率、`pᵢ` = i 番目の検査述語の選択率、`cᵢ` = その単価）:

```text
検査の期待コスト  probe(R) = Σᵢ ( Π_{j<i} pⱼ ) · cᵢ        … 安くてよく落ちる述語から順に評価

SortDrive   = (L / s(Q∧P)) · (c_tuple + probe(Q∧P の残り)) + L · c_fetch
FilterDrive = n·s(f) · (c_tuple + probe(残り)) + n·s(Q∧P) · c_probe(ソート値) + c_sort(n·s(Q∧P), L) + L · c_fetch
PolicyDrive = Σ_d n·s(d) · c_tuple + n·s(P) · (probe(Q) + c_probe(ソート値)) + c_sort(…) + L · c_fetch
```

- 検査の順序は**「(1 − 選択率) / 単価」の大きい順**（よく落ちて安い述語を先に）。これは独立性の仮定の下での最適順序として知られている
- SortDrive の `L / s` は「同時に満たす行が一様に散らばっている」仮定で、§1.2 ④のように相関があると外れる。
  補正係数（§8）を掛け、さらに §6.2 の予算で上限を切る
- 複数ソートの SortDrive は、第 1 キーの同値群の大きさ（最頻値の頻度 × n）が L × K（既定 8）を超えると
  先読みが破綻するので、その場合は SortDrive を候補から外して FilterDrive か CompositeDrive に回す

### 5.3 頑健な選択

推定の点だけで最小の戦略を選ぶと、推定が外れたときの損失が大きい戦略を拾いやすい。
各戦略のコストを推定区間の両端 `[cost(lo), cost(hi)]` で評価し、次の規則で選ぶ。

1. 推定値でのコストが最小の戦略を A とする
2. A の最悪コスト（区間の悪い側）が、**全戦略の最悪コストの最小値の R 倍（既定 4）**を超えるなら、
   最悪コストが最小の戦略を選ぶ
3. 信頼度が「推測」の述語に依存する選択では、§4.3 の上限付き件数探索を 1 回だけ行い、区間を狭めてから選び直す

### 5.4 予測コストの使い道

- **受付制御**: 予測コストが読取予算（既定 2 秒）を超えるクエリは実行せず、構造化エラーで
  「絞り込みの追加」または「索引の昇格（§10）」を提案する。グリッドが数秒固まるより、理由が分かって断られる方がよい
- **公平性**: §16.8 のテナント単位の同時実行制限を「本数」ではなく**予測コストのトークン**で消費する。
  重いクエリを 1 本流すテナントと軽いクエリを 100 本流すテナントを同じ物差しで測れる
- **予測コストは利用者に返さない**（§7.3）

## 6. 降下と実行

### 6.1 プランナ耐性 SQL

選んだ戦略を、**Postgres が別の計画を選びようのない形**の SQL に落とす。拡張は使わず、標準の構文だけで計画を固定する。

| 固定したいもの | 手段 |
|---|---|
| 駆動索引と走査順 | 駆動を「索引の並びと一致する `ORDER BY` ＋ `LIMIT`」を持つ部分問い合わせにする。`LIMIT` 付きの部分問い合わせは平坦化されない |
| 点検索であること（ハッシュ半結合にさせない） | 検査の `EXISTS` 内に **`OFFSET 0`** を置く。Postgres は `OFFSET` を持つ `EXISTS` を半結合へ引き上げないため、行ごとの点検索（SubPlan）として残る |
| 検査の順序 | `CASE WHEN p₁ THEN (CASE WHEN p₂ THEN p₃ ELSE false END) ELSE false END` の入れ子にする。`WHERE` の並びは Postgres が自身のコスト推定で並べ替えるが、`CASE` の評価順は保証されている |
| フィルタ駆動の候補集合 | `WITH cand AS MATERIALIZED (…)` で囲み、外側から押し込まれないようにする |

ソート駆動の例（「状態=承認待ちを金額の高い順に 20 件」・2 ページ目）:

```sql
SELECT d.record_id, d.val
FROM (
  SELECT i.record_id, i.val
  FROM data_index_num i
  WHERE i.tenant_int = $1 AND i.table_int = $2 AND i.field_id = $3        -- 金額
    AND (i.val, i.record_id) < ($4, $5)                                    -- カーソル
  ORDER BY i.val DESC, i.record_id DESC
  LIMIT $scan_budget                                                       -- 走査予算（§6.2）
) d
WHERE CASE WHEN EXISTS (SELECT 1 FROM data_index_text f
                        WHERE f.tenant_int = $1 AND f.table_int = $2 AND f.field_id = $6
                          AND f.record_id = d.record_id AND f.val = $7 OFFSET 0)   -- 状態
           THEN ( <Guard(P) を同じ形で> )
           ELSE false END
ORDER BY d.val DESC, d.record_id DESC
LIMIT $8;
```

> ⚠️ **`OFFSET 0` で引き上げを止めるのは Postgres の実装に依存した振る舞い**である（`EXISTS` の単純化処理が
> `OFFSET` を持つ部分問い合わせを対象外にしている）。data-platform §15.1 の移植性予算に 1 行足し、
> **EXPLAIN 回帰テスト（§9.1）で版ごとに固定する**。Postgres の版を上げるときの確認項目に入れる。

**汎用プランとの関係**: 形を固定しているので、汎用プランでも個別プランでも計画は同じになる。
むしろ汎用プランで計画のやり直しを省けるのが利点である。`EXPLAIN (GENERIC_PLAN)`（Postgres 16 以降）で、
汎用プランも想定どおりの形であることを CI で確かめる。

**汎用プランとパーティション枝刈り（実測で分かった注意点）**: `table_int` はバインド値なので、
汎用プランでは**計画時の枝刈りが効かない**。計画には全パーティションが載り、実行開始時の枝刈り
（`Subplans Removed: N−1`）で 1 つに絞られる。実測では枝刈り自体は駆動・各 SubPlan のすべてで効いたが、
**汎用プランの計画時間が 16 分割・検査 2 本で 8.6ms** かかった（個別プランは 0.4ms 前後）。
計画時間は「パーティション数 × 部分問い合わせの数」に比例するので、64 分割では 30ms を超える見込みである。

- 汎用プランの計画は**接続ごと・形状ごとに 1 回**なので、接続プールが温まっていれば毎回は払わない。
  ただし形状の種類を増やしすぎない（§16.3 の形状数の上限）こと、接続の作り直しを頻繁にしないことが前提になる
- `table_int` を SQL テキストに埋め込めば計画時に枝刈りできるが、テーブルごとに別の SQL になり
  形状キャッシュが効かなくなるので採らない
- CI の EXPLAIN 回帰では、汎用プランの**実行時**に `Subplans Removed` が「分割数 − 1」であることも確かめる
- パーティション数を決めるとき（data-platform §3.8）は、この計画時間も判断材料に入れる

**プランキャッシュのキー**（§16.3）に**戦略の種別**を足す。戦略は閲覧者の材料の大きさで変わるが、
キャッシュに入るのは「どの戦略を選んだか」だけで、材料そのものは入らない。

### 6.2 予算付き実行と切替

推定は外れる（§1.2 ④）。外れたときの損失に上限を付けるため、**ソート駆動は走査予算付きで実行する**。

```text
1. 戦略 A（例: SortDrive）を、走査予算 B_A で実行する
     B_A = 次善の戦略 B の推定コストを A の 1 エントリあたり単価で割った件数
2. L 件そろえば終了
3. 予算を使い切って L 件に届かなければ、
     観測した選択率（ヒット数 / 走査数）で推定を更新して計画し直す
     → B に切り替える（A の途中結果は捨てる。混ぜない）
```

予算を「次善の戦略の推定コスト」に合わせるのが要点で、こうすると**最悪でも「最良の戦略のコストの約 2 倍」＋
推定誤差分**に収まる（スキーレンタル問題と同じ構造）。フィルタ駆動も同様に候補件数の上限を
推定の R 倍に置き、超えたら打ち切りの印を返して切り替える（候補 CTE の件数を 1 列足して返せば往復は増えない）。

- 切替は**1 リクエスト内で最大 1 回**。それでも足りなければ安全計画（擬似列駆動・全述語検査。正しいが遅い）に落とす
- 切替が起きたことはフィードバック（§8）に記録し、次回以降の推定に効かせる

### 6.3 カーソルは戦略に依存させない

次のページを別の戦略で取ってよいように、**カーソルにはソートキーの値・`record_id`・区間番号（§5.1）だけを入れる**。
走査位置や戦略名は入れない。どの戦略も「カーソルより後ろ」を同じ全順序（ソートキー → `record_id`）で定義するので、
戦略が変わってもページ間の重複・欠落は起きない（ライブページングの契約・data-platform §3.3 はそのまま）。

### 6.4 一括実行（バッチ駆動）

単発の SQL で表しにくい形——リンクを 2 段以上たどる条件、グリッドのルックアップ列の解決（§16.9 の N+1）——は、
Rust 側で段を分けて実行する。

```text
段 1: 駆動から record_id を最大 B 件取る
段 2: 各条件について  … WHERE record_id = ANY($ids)  で一括検査（外側が小さい配列なので Postgres は必ず点検索を選ぶ）
段 3: 足りなければ段 1 へ。観測した選択率で B を調整
```

往復は増えるが、**どの段も Postgres に計画の選択肢を残さない**ので、§6.1 の実装依存の手段も要らない。
単発 SQL が使える形では単発 SQL を優先し（往復 1 回）、バッチ駆動はリンク多段とルックアップ解決に使う。

## 7. 認可との関係

### 7.1 最適化は行述語を弱めない

`Guard(P)` は**生成される SQL のすべての出力行に、P 全体の検査が付いている**ことを型で保証する。

- 降下（`lower.rs`）の出力は「駆動」「検査列」「`Guard`」の 3 部からなる中間表現で、`Guard` を持たない値は作れない
- **認可駆動のときも P 全体の検査を残す**。和集合の各要素は P のどれかの選言を満たすので理屈の上では冗長だが、
  冗長に検査しておけば「駆動の組み立てを間違えた」が漏洩につながらない。検査は最初に当たった選言で止まるので安い
- 計画のどこかで失敗したら安全計画に落とす。**行述語を省いた計画に落ちる経路は存在しない**

### 7.2 事後検査（Rust による独立した再評価）

v1 の行述語は SQL の中だけで評価している。v2 ではオプティマイザが述語の置き場所と順序を変えるため、
**本体（`data_record`）を取ったあとで、同じ `PolicyExpr` を Rust で独立に評価し直す**。

- 評価器は SQL へのコンパイラ（`policy/compile.rs`）とは別実装にする（`mask.rs` のロール水準の評価器と同じ層）。
  同じバグを二度書かないため
- 対象はページの行（≤ L）だけなので、コストは無視できる
- 不一致の行は応答から落とし、**セキュリティ指標として記録して警報を出す**（オプティマイザか SQL 生成のバグを意味する）
- これで、オプティマイザの誤りは「見えるべきでない行が出る」ではなく「見えるはずの行が欠ける」に倒れる。
  CLAUDE.md の「二段 authz」を構造化データの読取でも文字どおりにする
- 集計と件数には行が無いので事後検査が効かない。ここは §9 の強制戦略テストと `policy_threat_it.rs` で担保する

### 7.3 統計はサイドチャネルになる（PIT-75）

統計は**可視性を無視して全行から**集める。したがって:

- **推定値・最頻値・ヒストグラム・選んだ戦略名・予測コストを利用者に返さない。** エラー文言にも含めない
- **UI の値候補（フィルタのプルダウン）に値頻度表を使わない。** 見えない行にしかない値が候補に出る。
  候補は可視行に対するクエリで作る
- 計画の違いは応答時間の差として観測できる（見えない行に「承認待ち」が多いかどうかで速さが変わる）。
  これは消せない残余リスクとして記録する。機微なテーブルでは、テーブル設定でコストベース選択を止めて
  固定戦略にできるようにする

### 7.4 既存の不変条件との対応

| 不変条件 | オプティマイザでの扱い |
|---|---|
| 値は必ずバインド（PIT-21） | 変更なし。降下は `lower.rs` 1 箇所 |
| プランキャッシュに材料を混ぜない（§16.3） | 戦略の種別だけをキーに足す。材料の大きさは計画時に使って捨てる |
| リクエストを跨いだ材料キャッシュの禁止（PIT-18） | 統計は材料ではない（全員共通・権限を表さない）のでキャッシュしてよい。材料は §16.4 のリクエストスコープのメモ化のみ |
| マスク列を filter/sort に出せない（PIT-19） | 変更なし。マスク列は統計を持っていても駆動・検査に出てこない |

## 8. フィードバック

- 実行ごとに `(形状ハッシュ, 戦略, 各段の推定行数, 実測行数, 所要時間)` を記録する（メモリ上のリングバッファ＋OTel へ抽出）
- **補正係数**: ソート駆動で「予想した走査数」と「実際の走査数」の比を、`(テーブル, フィルタ列, ソート列)` ごとに
  指数移動平均で持つ。§1.2 ④の相関はこの係数で次回から吸収される
- 推定と実測が 10 倍以上ずれることが続いたら、そのテーブルの統計収集を前倒しで起動する
- 深いページで劣化し続ける複数ソートの形は、**複合索引の材料化（§5.3）の候補**として管理画面に出す。
  未索引列でのフィルタ要求が多い列は**索引の昇格（§10）の候補**として出す
- 学習した値は**テーブルと列の組の単位**に限る。利用者ごとには持たない（利用者ごとの推定は材料から毎回作る）

## 9. 検証

### 9.1 計画の回帰（EXPLAIN）

data-platform §14 の代表クエリ集合について、戦略ごとに**期待する計画の形**（駆動索引・SubPlan であること・
ハッシュ結合が無いこと）をアサートする。個別プランと `EXPLAIN (GENERIC_PLAN)` の両方で確かめる。

### 9.2 正しさの差分テスト

| テスト | 内容 |
|---|---|
| **強制戦略テスト** | 同じクエリを**全戦略で強制実行**し、結果の集合と順序が一致することを確かめる。コストモデルは速さにだけ効き、結果には効かないことを固定する |
| **参照実装との比較** | 擬似列で全件を歩き Rust で条件を評価する素朴な実装を参照とし、乱数で生成したスキーマ・データ（偏り・相関・値なし・多値・切り詰め値を含む）・クエリで結果を比べる（proptest） |
| **TLP（Ternary Logic Partitioning）** | 任意の述語 p について「Q の結果 = (Q ∧ p) ∪ (Q ∧ ¬p)」が成り立つことを確かめる。§3.1 の 2 値論理の下では区分は 2 つ。SQL 前段と IR 経路の意味の一致もこれで見る |
| **正規化の 1 規則ずつ** | §3.2 の各規則の前後で結果が一致すること |
| **認可** | `policy_threat_it.rs` を**全戦略で強制実行**して通す。§7.2 の事後検査が 1 件も落とさない（＝SQL 側で既に正しい）ことも同時に確かめる |
| **切替の一貫性** | 予算を極端に小さくして切替を必ず起こし、結果が切替なしと一致すること |

### 9.3 性能

- 偏り（Zipf）・相関（状態と作成日）・値なしの多い列・多テナントの雑音を含むデータで、
  **「Postgres 任せの単発 SQL」と比べた p50 / p95 / p99** を測る。自前プランナの採否はこの差で判断する
- **後悔比**（実際の所要時間 ÷ 全戦略を試した中での最短時間）を代表クエリごとに出し、**p95 で 2 倍以内**を目標にする

## 11. 判断待ちの事項

| 事項 | 推奨 | 理由 |
|---|---|---|
| **IR の意味論を 2 値論理にする**（§3.1） | 採る | workflow IR と揃えないと `data.query` に翻訳層が要る。SQL 前段だけが 3 値論理を翻訳すればよい |
| **事後検査を必須にする**（§7.2） | 採る | オプティマイザが述語の配置を変える以上、独立した二段目が無いと誤りが漏洩に直結する |
| **機微なテーブルでコストベース選択を止められるようにする**（§7.3） | 採る（既定はオン） | 応答時間のサイドチャネルを消す手段がこれしか無い |
| **`record_id` を内部整数（テーブル内連番 `int8`）にする** | **今は採らない** | 得られるのは索引行の縮小（約 7%）と、Rust 側でのビットマップ演算（O3 のバッチ駆動・交差）。等値範囲は uuid でも `record_id` 順に並ぶので、交差駆動は uuid のままでも成立する。**入れるなら JSONB キーを書き換える 15.1 と同時でなければ高くつく**ので、O3 の要件が固まる前に決める必要がある |
