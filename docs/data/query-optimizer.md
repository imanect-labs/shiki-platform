# 構造化データ v2 のクエリオプティマイザ（自前プランナ）

> 位置づけ: [data-platform.md](../data-platform.md) §3.5（クエリの形）・§5（クエリ IR）・§14（統計）・
> §16.2（最適化層）の詳細設計。実装は [Phase 15](../roadmap/phase-15.md) の Task 15.3（最小構成 O1）と
> Task 15.12（O2・O3）。落とし穴は [PIT-69](../design-caveats.md)（駆動索引の誤選択）・
> PIT-75（統計のサイドチャネル）・PIT-76（書き換えと適応切替の正しさ）。

## 0. 結論

- **プランナは自前で持ち、実行は Postgres に任せる。** 自前にするのは「どの索引から入り、どの順で絞り、
  どこで打ち切るか」（アクセスパスと結合順）だけで、索引走査・ソート・集約の実行エンジンは作らない。
- 効くのは平均ではなく**裾（p99）**である。pivot 索引では駆動の選び方ひとつで桁違いの差が出る
  （§1.2 の試算で 100〜1000 倍、§1.3 の実測で 17〜61 倍。逆向きの決め打ちでは 1 万倍超）。
  自前プランナの価値は「平均を 2 割速くする」ことではなく「最悪ケースを 1〜2 桁潰す」ことにある。
- 構成は 4 本柱: ①テーブル×フィールド単位の**自前統計** ②閲覧者の認可材料まで含めた**コストベースの戦略選択**
  ③推定が外れても損失を抑える**予算付きの適応切替** ④Postgres に別の計画を選ばせない**プランナ耐性 SQL**。
- 安全側の不変条件を 2 つ足す。**最適化は認可述語を弱めない**（型で強制）と、
  **本体取得後に行述語を Rust 側で独立に再評価する**（オプティマイザの誤りを漏洩ではなく欠落に倒す）。

## 1. なぜ Postgres のプランナに任せられないか

### 1.1 構造的な理由

| 理由 | 中身 |
|---|---|
| **統計の粒度が合わない** | `data_index_text` の統計は「プール全体」のもの。「テーブル T のフィールド F で `val = '承認待ち'` が何件か」を Postgres は知らない。拡張統計（`CREATE STATISTICS`）も relation 単位で、`(table_int, field_id)` の切片には効かない |
| **閲覧者ごとに最適が変わる** | 同じクエリでも、全行が見える管理者と 1% しか見えない担当者では最適な駆動が違う。Postgres から見れば行述語は「`ANY($n)` の配列が長いか短いか」でしかなく、汎用プランではその差も消える |
| **汎用プラン** | sqlx は prepared statement を使う。Postgres は 6 回目以降に汎用プラン（パラメータ値を見ない計画）へ切り替え得るため、値に依存した選択が効かなくなる |
| **`ORDER BY … LIMIT` の病理** | 「ソート索引を歩いてフィルタで捨て、`LIMIT` で止める」計画は、フィルタの選択率を楽観すると索引を延々と歩く。Postgres で古くから知られる問題で、pivot ではフィルタが全部 `EXISTS` になるため常に起き得る |
| **半結合の数** | 条件木の葉がそれぞれ `EXISTS` になる。`join_collapse_limit`（既定 8）・`geqo_threshold`（既定 12）を超えると結合順の探索が打ち切られたり遺伝的探索になったりして、計画が実行ごとに揺れる |

### 1.2 差の大きさ（試算）

前提: 100 万行のテーブル、1 ページ 20 行。単価は §5.2 の初期値（索引タプル 1µs・点検索 5µs・本体取得 10µs）。
**数値は計画選択の差を示すための試算で、実測ではない**（Task 15.12 のベンチで置き換える）。

| ケース | ソート索引から入る | フィルタ索引から入る | 比 |
|---|---|---|---|
| ① `状態=承認待ち`（300 行・0.03%）を金額順 | 約 6.7 万エントリを歩く ≈ 400ms | 300 行を拾って並べ替え ≈ 3ms | 約 130 倍 |
| ② `状態=完了`（90%）を金額順 | 22 エントリで止まる ≈ 0.2ms | 90 万行を拾う ≈ 5s 超 | 約 25,000 倍（逆向き） |
| ③ 見える行が 0.01%（100 行）の利用者がフィルタなしで更新日順 | 20 万エントリ × 述語検査 ≈ 1s 超 | 行述語の和集合から入る ≈ 1ms | 約 1,000 倍 |
| ④ `状態=未着手`（5%）を作成日の古い順。ただし未着手は新しい行に偏っている | 独立性の仮定では 400 エントリ（≈2.4ms）のはずが、実際は約 95 万エントリ ≈ 5.7s | 5 万行を拾う ≈ 0.3s | 推定どおりならソート駆動が正解だが、実際はフィルタ駆動の約 19 倍遅い |

①と②は同じクエリの値違いであり、**どちらか一方に決め打ちした実装は必ずどちらかで破綻する**。
③は認可材料で最適が変わる例、④は統計が正しくても相関で推定が外れる例で、④への備えが §6 の適応切替になる。

### 1.3 実測（ローカル PostgreSQL 16・2026-10）

上の試算を、data-platform §3.3 と同じ形の pivot 表（ハッシュ 16 分割。計測時点のレコードキーは uuid）で確かめた。対象テーブル 100 万行に加え、
**別テナントの 40 テーブルに `状態=承認待ち` を計 100 万行**入れてある（プール全体の統計を汚す雑音）。
キャッシュが温まった状態の 1 回計測で、性能目標の判定ではなく**計画の差の桁を確かめるため**のもの。

| ケース | Postgres 任せ（素朴な `EXISTS`） | 自前で固定した計画 | 備考 |
|---|---|---|---|
| ① 承認待ち 300 行を金額順 20 件 | **373 ms**（ソート索引を並列で 12.8 万行歩いた） | フィルタ駆動 **6.1 ms** | 約 61 倍。雑音テナントの「承認待ち」で、Postgres は承認待ちを多いと見積もった |
| ② 完了（95%）を金額順 20 件 | **0.6 ms**（ソート駆動・21 行で停止） | フィルタ駆動に決め打ちすると **8,375 ms** | 決め打ちが破綻する側。ここはソート駆動が正解 |
| ③ 担当=user5（0.05%）だけ見える利用者・作成日の新しい順 | 13.7 ms（ハッシュ半結合を選べた） | 認可駆動 5.8 ms | `user5` がプール中でこのテーブルにしか無いため、偶然プール統計が正しかった |
| ④ 未着手（5%・新しい行に偏る）を作成日の古い順 | **4,566 ms**（95 万行歩いた） | フィルタ駆動 **268 ms** | 約 17 倍。相関で外れる典型 |
| ①を予算付きソート駆動で | — | 走査予算 2,000（計測のため手で置いた値）で打ち切りまで **7.4 ms** → 切替後のフィルタ駆動 6.1 ms | 合計 約 14 ms。推定を誤っても桁は外さない（§6.2。O1 の予算の決め方は §6.2 の手順） |

- Postgres は**いつも間違えるわけではない**（②③）。問題は、正しく選べるかどうかが**他テナントのデータ分布という
  制御できない要因**で決まることにある。①の誤りは対象テーブルではなく雑音テナントが原因だった
- `WHERE` 最上位の `EXISTS` に `OFFSET 0` を入れると、半結合に引き上げられず行ごとの SubPlan として残ることを確認した（§6.1）
- 予算切れの判定に必要な「走査件数・最後に読んだキー」を 1 往復で返す形（§6.1 の例）も、再ソートなし・早期停止ありで動くことを確認した

### 1.4 作らないもの

| 作らない | 理由 |
|---|---|
| 実行エンジン（自前の走査・結合・集約） | Postgres の索引走査・ソート・集約は十分速い。外す必要があるのは計画選択だけ |
| `pg_hint_plan` 依存 | 拡張の有無が環境に依存する（オンプレ・マネージドの差）。data-platform §15.1 の「Postgres の飛び道具に賭けない」方針に反する |
| Cascades / Volcano 型の汎用最適化フレームワーク | 計画空間が小さい（単一テーブル＋半結合＋リンク）。戦略を列挙して全部の費用を測るので足りる。計画時間は件数探索を除いて 1ms 未満、件数探索（§4.3）を含めて 3ms 以内を目標にする |
| 学習型（ML）カーディナリティ推定 | 説明可能性と再現性を優先する。学習は「補正係数」に留める（§8） |

## 3. 意味論の固定と正規化

オプティマイザは式を書き換える。書き換えが正しいと言うには、まず「その式が何を意味するか」が
決まっていなければならない。**v2 の文書は `Not` を許しているが、値の欠損（null）と多値列での意味を
まだ定めていない**。ここで固定する。

### 3.1 2 値論理を採る（2026-10 決定）

`data.query` ノードは workflow IR の `Condition` を変換なしで渡す（data-platform §5.1）。その workflow IR の
評価器（`crates/workflow-engine/src/control/eval.rs`）は、単値については **2 値論理**で、`Neq` は欠損値に対して真になり、
`Not` は単純な真偽の反転である。data 側が SQL の 3 値論理を採ると、**同じ条件がワークフローの分岐と
`data.query` で別の行を選ぶ**ことになる。

→ **クエリ条件 Q の意味論は 2 値論理にする（決定）。** 各レコードのフィールドは「値なし」または「値の集合」（単値なら要素 1 個）
で、比較は次のとおり定義する。**行述語 P はこの表の対象外**で、v1 の意味論をそのまま保つ（§3.3）。

| 演算子 | 単値フィールド | 多値フィールド（`multi_select`・`link`） | 値なし |
|---|---|---|---|
| `Eq c` | 値 = c | c を含む | 偽 |
| `Neq c` | `Not(Eq c)` と同じ | c を含まない | **真** |
| `In [..]` | いずれかに等しい | いずれかを含む | 偽 |
| `Lt` / `Lte` / `Gt` / `Gte` | 通常の比較 | **使えない**（スキーマ検証で 422） | 偽 |
| `StartsWith` / `Contains` / `EndsWith` | 文字列判定 | いずれかの要素が満たす | 偽 |
| `Exists` | 値がある | 要素が 1 個以上 | 偽 |
| `IsNull` | `Not(Exists)` | `Not(Exists)` | 真 |
| `Not X` | X の補集合 | X の補集合 | — |

- これで **`Not(Eq c) ≡ Neq c`、`Not(Exists) ≡ IsNull` が全型で成り立つ**。否定の押し下げ（§3.2）が型を見ずに書ける
- 比較の否定は値なしを含む: `Not(Lt c) ≡ Gte c ∨ IsNull`
- **SQL 前段（data-platform §16.1・Task 15.10）は 3 値論理の SQL を 2 値論理の IR へ翻訳する。** `f <> c` は `Exists f ∧ Neq c`、
  `NOT (f < c)` は `Gte c`（`IsNull` を足さない）になる。翻訳表は `crates/data/src/sql/` に 1 箇所だけ置き、
  TLP テスト（§9.2）で SQL 経路と IR 経路の一致を確かめる
- `row_policy`（`PolicyExpr`）は従来どおり `Not` を持たない。この非対称は data-platform §5.1 の注のとおり意図的

**workflow の評価器と一致するのは単値の比較だけである。** 現行の `eval.rs` とは次の点で食い違う。

| 項目 | 上の表（data） | 現行 `eval.rs` |
|---|---|---|
| 多値列の `Eq c` | c を含む | 配列全体との一致 |
| 多値列の `In [..]` | いずれかを含む | 左辺が配列だと常に偽 |
| 多値列の `Contains` | いずれかの要素が部分文字列を含む | 要素の一致（`items.contains(&v)`） |
| 空の多値列の `Exists` | 偽（要素 0 個＝索引行なし） | 真（`[]` は null ではない） |
| 数値の等値 | 数値として比較（`1 = 1.0`） | JSON 値として比較（`1 ≠ 1.0`） |

**決定（2026-10）: `eval.rs` をこの表に合わせる。** 「`data.query` に変換層が要らない」（data-platform §11）を保ち、
利用者が 2 つの解釈を覚えずに済むようにするため。ワークフローの既存の分岐の振る舞いが変わるので、Task 15.7 で次を行う。

- `eval.rs` の `Eq` / `Neq` / `In` / `Contains` / `Exists` を上表の多値・数値の規則に合わせる
- 保存済みのワークフロー定義のうち、**配列値に対して `eq` / `neq` / `in` / `contains` を使っている条件を検出**し、
  切替前に一覧化する（振る舞いが変わる候補）。ワークフローの検証器にも同じ検出を入れ、保存時に警告する
- data の評価規則と `eval.rs` が同じ結果を返すことを、共通のテスト表（演算子 × 型 × 値なし/空/多値）で固定する

> 3 値論理（SQL と同じ）を採る案は退けた。`data.query` ノードに IR → data の翻訳層が必要になり、ワークフローの分岐と
> テーブル検索で同じ条件が別の行を選ぶ。「担当者 ≠ 佐藤」に未割り当てを含めるのは Excel のフィルタとも同じで、業務の直感に合う。

### 3.2 正規化の規則

適用順に並べる。**どの規則も意味を変えない**ことが条件で、§9 の差分テストで 1 規則ずつ検証する。

1. **否定の押し下げ（NNF）**: §3.1 の表で `Not` を葉まで降ろす。`Not(All[a,b]) → Any[Not a, Not b]`
2. **平坦化・重複除去**: `All[All[a,b],c] → All[a,b,c]`、同一の葉を 1 つに
3. **定数畳み込み**: `HasRole` は材料解決後に TRUE/FALSE（v1 と同じ）。`All[.., FALSE] → FALSE`、
   `Any[.., TRUE] → TRUE`。**行述語 P 全体が FALSE になったらクエリを実行せず空を返す**
4. **同一フィールドの併合**: `Any[Eq a, Eq b] → In[a,b]`、`All[Gte 10, Lt 20] → Range[10,20)`、
   単値フィールドの `All[Eq a, Eq b]`（a≠b）→ FALSE。多値フィールドでは `All[Eq a, Eq b]` は矛盾ではない
   （a と b の両方を含む）ので併合しない
5. **`StartsWith p` を範囲に**: `Range[p, succ(p))`。`succ` は**最後のコードポイントを 1 進めた文字列**として作る
   （U+10FFFF なら落として 1 つ前を進める。サロゲート域は飛ばす）。UTF-8 はコードポイント順とバイト順が一致するので
   `COLLATE "C"` の範囲として正しい。**最後のバイトを 1 増やす作り方は不正な UTF-8 を生むので使わない**。
   p が `MAX_INDEX_KEY_BYTES` を超えるときは、文字境界で切り詰めた p で範囲を引き、候補を本体で再確認する
6. **否定の範囲化**: `Neq c`（単値）は索引で引けない。駆動候補から外し、検査（probe）側でだけ使う

### 3.3 認可述語との合成

正規化後の条件 `Q` と行述語 `P`（`row_policy` ∨ 個別共有）を `Q ∧ Guard(P)` に合成する。
`Guard` の扱いは §7.1。**正規化は `Q` の内部にだけ掛け、`P` には定数畳み込みと平坦化以外を掛けない**
（`P` の書き換えを増やすほど、認可の正しさを示す範囲が広がる）。

**P は §3.1 の 2 値論理に乗せない。** v1 の `policy/compile.rs` では `Ne` は値の無い行で**不成立**
（SQL の `<>` の NULL 伝播＝fail-closed）であり、数値の比較は `::numeric` で行う。§3.1 の表で P を降ろすと
`Ne` が値なしの行を通し、**認可が広がる**。したがって:

- `Guard(P)` の SQL は、クエリ条件の降下規則ではなく**行述語専用の降下**（`policy/compile.rs` を索引表向けに
  書き直したもの）で作る。値なしの扱い・数値比較の型は v1 と同一にする
- §7.2 の事後検査の評価器も**行述語の意味論**（値なしの `Ne` は偽）で評価する。2 値論理のクエリ評価器を流用しない
- 「値の無い行で `Ne` を含む行述語が不成立になる」ことを、v1 と v2 の両方でテストに固定する（Task 15.3）

## 4. 統計とカーディナリティ推定

### 4.1 統計の種類

| 統計 | 単位 | 中身 | 更新 | 用途 |
|---|---|---|---|---|
| **行数** | テーブル | `n_rows`（正確） | outbox 消費側で増減（非同期・数秒遅れ） | 全推定の分母 |
| **値頻度表** | テーブル × フィールド × 値 | 値ごとの件数（正確） | outbox 消費側。**種類数が上限（既定 1,024）以下のフィールドだけ** | `select` / `status` / `user_ref` / `owner` 擬似列の `Eq` / `In`——最頻出のフィルタと行述語の大半 |
| **フィールド統計** | テーブル × フィールド | 値を持つ行数・異なり数・最頻値 100 件・等深ヒストグラム 100 区間・切り詰め率・平均要素数（多値） | 統計収集ジョブ（§4.2） | 範囲・前方一致・高異なり数の `Eq` |
| **リンク統計** | リンク列 × 方向 | 平均・最大ファンアウト、リンクを持つ行の割合 | 同上 | リンク経由の条件・ロールアップ |
| **行幅** | テーブル | 本体の平均バイト数・TOAST 率 | 同上 | covering read の判定（data-platform §16.5） |
| **補正係数** | テーブル × （フィルタ列, ソート列） | 推定に対する実測の比（指数移動平均） | §8 | 相関の補正（§1.2 ④） |

格納は `data_table_stats` / `data_field_stats` / `data_value_count` / `data_link_stats` の 4 表。
いずれも `tenant_int` / `table_int` を先頭に持ち、**purge 経路と tenant スコープの CI ゲート（Phase 12.9）の対象に入れる**。

> **値頻度表を書込 Tx で更新しない理由**: 人気の値（`状態=未着手`）の 1 行に全書込が集中し、行ロック待ちで
> 書込スループットが落ちる。outbox 消費側でバッチにまとめ、`INSERT … ON CONFLICT DO UPDATE SET cnt = cnt + excluded.cnt`
> で反映する。**冪等性は消費位置（`delivery_seq`）で担保する**（同じバッチを二度足さない）。

### 4.2 統計収集ジョブ

- 起動条件は Postgres の autoanalyze と同じ形にする: **前回収集からの変更行数 > 50 + 0.1 × `n_rows`**。
  加えて ①索引の昇格完了時（data-platform §10）②フィードバックで推定外れが続いたとき（§8）
- ヒストグラムは**値索引を値順に読むだけで作れる**（`(tenant_int, table_int, field_id, val, record_int)` の範囲走査）。
  100 万行までは全件を読む。それを超えたらその行数に比例したサンプリングに切り替える
- jobq のバッチジョブとして動かし、**テナントの公平性の枠（data-platform §16.8）で消費する**。重いテナントの統計収集が
  他テナントの読取を圧迫しないようにする

### 4.3 計画時の上限付き件数探索

統計が無い・古い・信頼度が低い述語は、計画時に**上限付きの件数**を直接数える。

```sql
SELECT count(*) FROM (
  SELECT 1 FROM data_index_text
  WHERE tenant_int = $1 AND table_int = $2 AND field_id = $3 AND val = $4
  LIMIT $cap            -- 既定 1,000
) s;
```

上限内なら正確な件数、上限に達したら「cap 以上」と分かる。駆動の選択に必要なのは
「数百件か、数十万件か」の区別なので、上限 1,000 で十分に判定できる。
1 回 1ms 未満で、**計画 1 回あたり最大 3 本**（候補上位の述語と、認可駆動を検討するときの行述語の選言）に制限する。

- **クエリ条件 Q の述語**の結果は `(テーブル, フィールド, 述語)` をキーに**プロセス内で短時間（既定 60 秒）キャッシュしてよい**。
  全員共通で権限を表さないので、PIT-18 の「材料をキャッシュしない」の対象外である（ただし利用者へ返さない・PIT-75）
- **行述語 P の選言**（`owner = me`・`部門 ∈ D` など）の探索は、キーが principal と認可材料から作られるので
  **リクエストを跨いでキャッシュしない**（data-platform §16.4 のリクエストスコープのメモ化だけ）
- 多値列の探索は索引行を数えるので、レコード数より多めに出る（同じレコードの要素が複数行ある）。
  推定には上限として使えば足りる
- **O1（§10）は統計表を持たず、この探索とキャッシュだけで戦略を選ぶ。** 値頻度表は outbox 消費側
  （Task 15.6）を要し、15.3 の時点では存在しないためである。それでも判定が成り立つ理由:
  候補の件数 c が上限内なら、フィルタ駆動のコストは c で直接決まり、上限 1,000 なら高々 10ms 程度で済む。
  上限を超えたなら絶対数として絞れていないので、ソート駆動を予算付き（§6.2）で走らせ、
  予算を使い切ったら切り替えればよい。行数 n が分からなくても、この 2 分岐と予算で最悪ケースは抑えられる

### 4.4 推定式

| 述語 | 推定 | 信頼度 |
|---|---|---|
| `Eq c`（値頻度表あり） | `cnt(c) / n_rows` | 正確 |
| `Eq c`（最頻値に含まれる） | `freq(c)` | 統計 |
| `Eq c`（それ以外） | `(1 − Σ最頻値の頻度) / (異なり数 − 最頻値の数)` | 統計 |
| `In [..]` | 各要素の和（単値）。多値は `1 − Π(1 − sᵢ)` | 要素の最弱 |
| `Range` / `StartsWith` | ヒストグラムの区間内を線形補間 | 統計 |
| `Contains` / `EndsWith` | 固定値 0.01。必要なら §4.3 で探索 | 推測 |
| `Exists` / `IsNull` | 値を持つ行の割合／その補数 | 統計 |
| `Neq` / `Not X` | `1 − s(X)` | X に同じ |
| `All[..]` | **指数バックオフ**: 選択率の小さい順に `s₁ · s₂^(1/2) · s₃^(1/4) · …` | 最弱 |
| `Any[..]` | `1 − Π(1 − sᵢ)`（同一フィールドの `In` は §3.2 で併合済み） | 最弱 |
| `IsOwner` / `owner = me` | owner 擬似列の値頻度表 | 正確 |
| 個別共有 `id ∈ S` | `\|S\| / n_rows`（材料から正確に分かる） | 正確 |

- `All` を単純な積にしないのは、業務データの条件が独立でないことの方が多いからである
  （`部門=営業 ∧ 担当=佐藤` は積よりずっと大きい）。積は過小推定に倒れ、過小推定は
  「ソート索引から入って延々と歩く」という最悪側の選択を招く。バックオフはその偏りを弱める
- 推定は点ではなく**区間 [lo, hi] と信頼度**で持つ。§5.3 の頑健な選択がこれを使う

## 5. 戦略とコストモデル

### 5.1 戦略

主要な形は「条件 `Q ∧ P`・ソート `S`（k キー）・`LIMIT L`・カーソル `C`」である。戦略は次の 6 つ。

| 戦略 | 入口 | 早期終了 | 向く場面 |
|---|---|---|---|
| **ソート駆動** `SortDrive(S₁)` | 第 1 ソートキーの値索引をカーソル位置から歩き、各行で残りの述語を点検索 | ✅ | 条件の選択率が高い（多くの行が通る） |
| **フィルタ駆動** `FilterDrive(f)` | 条件のうち索引で引ける 1 項 f の範囲を拾い、残りを点検索、ソート値を引いて上位 L 件 | ❌（候補を全部見る） | f が十分に絞れる |
| **認可駆動** `PolicyDrive` | 行述語の各選言（`owner = me` の範囲・`部門 ∈ D` の範囲・共有 id 列）の和集合から入る | ❌ | 見える行がごく少ない利用者（§1.2 ③） |
| **OR 駆動** `UnionDrive(Any[..])` | 条件 Q の中の `Any[a, b, …]`（**別の列どうしの OR**）の各項の索引範囲の和集合から入る。認可駆動はこれの P 版 | ❌ | 「状態=至急 OR 担当=自分」のように、各項は絞れているが同じ列ではない OR |
| **交差駆動** `IntersectDrive(f, g)` | 等値条件 2 つの範囲を `record_int` 順で突き合わせる（等値範囲は `record_int` 順に並んでいる） | ❌ | 各条件は中程度だが、両方を満たす行が少ない |
| **複合索引駆動** `CompositeDrive` | 材料化済みの複合索引（data-platform §5.3）を歩く | ✅ | 複数ソートで第 1 キーの同値群が大きい |

> 認可駆動は Salesforce の説明にある「利用者が見られる行が少ないときは共有表から入る」と同じ発想で、
> **Postgres のプランナには材料の大きさが見えないので原理的に選べない**。自前プランナで取れる利得の中で最も大きい。
>
> **OR 駆動を足した理由**: 別の列どうしの OR は、どの 1 項も単独では駆動にできない（他の項を満たす行を取りこぼす）。
> OR 駆動が無いと、絞れている OR でもソート駆動で全件近くを歩くことになる。kintone も「OR 条件の複合」を
> 絞り込みが遅くなる条件として公式に挙げている（§12）。各項の候補件数を §4.3 の件数探索で数え、
> **すべての項が上限内のときだけ**候補になる。和集合は `UNION`（`record_int` で重複除去）で作り、
> 項が 3 つを超えたら Rust 側のビットマップ（Roaring の 64 ビット版）で合わせる（往復を増やさないため、
> 各項の取得は 1 本の SQL に `UNION ALL` で並べる）。多値列の項は同じレコードが複数行出るので重複除去は必須

**任意列（null あり）でのソートは 2 区間に分けて歩く。** data-platform §3.5 では「システム擬似列から入って
`LEFT JOIN` し `NULLS LAST`」としていたが、これだと早期終了が効かない。代わりに:

1. **区間 1**: ソート列の値索引を値順に歩く（値を持つ行だけが値順に並んでいる）
2. **区間 2**: 区間 1 を使い切ったら、擬似列 `created_at`（`field_id = 1`）を**主キー順＝`record_int` 順**に歩き、
   「ソート列の値が無い」ことを点検索で確かめる

**値なしの位置は昇順・降順とも末尾に固定する**（Excel と同じ。v2 の `SortKey` は `NULLS FIRST` を受け付けない）。
Postgres の降順の既定は `NULLS FIRST` なので、降順でも明示的に末尾へ置く。こうすると先頭ページはほぼ必ず
区間 1 で埋まり、**任意列でも早期終了が効く**。カーソルには区間番号を入れる（§6.3）。

- **区間 2 にも予算を掛ける。** 値なしの行が疎だと、区間 2 は擬似列をほぼ全件歩く O(n) の走査になる
  （末尾のページに来たときだけ起きる）。予算を超えたら、値なしの行を拾う索引が無い以上は
  「値を持つ行の集合の補集合」を作るしかなく高くつくので、**末尾ページを頻繁に使う列には値なしの印の行を
  材料化する**（索引の昇格・data-platform §10 で、未設定レコードにも印の行を持たせる）。印があれば区間 2 も範囲走査になる
- **複数ソートでは、区間 2（第 1 キーが値なしの群）は第 1 キーの同値群**として扱う。
  第 2 キー以降での並べ替えは data-platform §5.3 の同値群の規則（先読み上限・複合索引）にそのまま従う
- **多値列から入るフィルタ駆動・認可駆動**は、同じレコードの要素が複数行あるので候補を `record_int` で重複除去する

### 5.2 コストモデル

コストは**予測レイテンシ（µs）**で表す。抽象的なコスト単位にしないのは、§5.4 の受付制御と
`statement_timeout` の判断にそのまま使うためである。

| 単価 | 意味 | 初期値 |
|---|---|---|
| `c_tuple` | 索引の範囲走査 1 エントリ | 1 µs |
| `c_probe` | 点検索 1 回（PK 降下＋可視性確認） | 5 µs |
| `c_fetch` | 本体 1 行の取得（TOAST 展開を含まない） | 10 µs |
| `c_detoast` | TOAST された本体 1 行の展開 | 行幅から算出 |
| `c_sort(n, L)` | n 件から上位 L 件 | `n · log₂L · 0.05 µs` |
| `c_rtt` | DB 往復 1 回 | 300 µs |

初期値は仮置きで、**起動時の較正ベンチ**（既知のデータで各操作を計測）で環境ごとに置き換える。

主要な戦略の式（`n` = 行数、`s(X)` = X の推定選択率、`pᵢ` = i 番目の検査述語の選択率、`cᵢ` = その単価）:

```text
検査の期待コスト  probe(R) = Σᵢ ( Π_{j<i} pⱼ ) · cᵢ        … 安くてよく落ちる述語から順に評価

SortDrive   = (L / s(Q∧P)) · (c_tuple + probe(Q∧P の残り)) + L · c_fetch
FilterDrive = n·s(f) · (c_tuple + probe(残り)) + n·s(Q∧P) · c_probe(ソート値) + c_sort(n·s(Q∧P), L) + L · c_fetch
PolicyDrive = Σ_d n·s(d) · c_tuple + n·s(P) · (probe(Q) + c_probe(ソート値)) + c_sort(…) + L · c_fetch
UnionDrive  = Σ_a n·s(a) · c_tuple + n·s(Any[..]) · (probe(残り) + c_probe(ソート値)) + c_sort(…) + L · c_fetch
```

- 検査の順序は**「(1 − 選択率) / 単価」の大きい順**（よく落ちて安い述語を先に）。これは独立性の仮定の下での最適順序として知られている
- SortDrive の `L / s` は「同時に満たす行が一様に散らばっている」仮定で、§1.2 ④のように相関があると外れる。
  補正係数（§8）を掛け、さらに §6.2 の予算で上限を切る
- 複数ソートの SortDrive は、第 1 キーの同値群の大きさ（最頻値の頻度 × n）が L × K（既定 8）を超えると
  先読みが破綻するので、その場合は SortDrive を候補から外して FilterDrive か CompositeDrive に回す

### 5.3 頑健な選択

推定の点だけで最小の戦略を選ぶと、推定が外れたときの損失が大きい戦略を拾いやすい。
各戦略のコストを推定区間の両端 `[cost(lo), cost(hi)]` で評価し、次の規則で選ぶ。

1. 推定値でのコストが最小の戦略を A とする
2. A の最悪コスト（区間の悪い側）が、**全戦略の最悪コストの最小値の R 倍（既定 4）**を超えるなら、
   最悪コストが最小の戦略を選ぶ
3. 信頼度が「推測」の述語に依存する選択では、§4.3 の上限付き件数探索を 1 回だけ行い、区間を狭めてから選び直す

### 5.4 予測コストの使い道

- **受付制御**: 予測コストが読取予算（既定 2 秒）を超えるクエリは実行せず、構造化エラーで
  「絞り込みの追加」または「索引の昇格（data-platform §10）」を提案する。グリッドが数秒固まるより、理由が分かって断られる方がよい
- **公平性**: data-platform §16.8 のテナント単位の同時実行制限を「本数」ではなく**予測コストのトークン**で消費する。
  重いクエリを 1 本流すテナントと軽いクエリを 100 本流すテナントを同じ物差しで測れる
- **予測コストは利用者に返さない**（§7.3）

## 6. 降下と実行

### 6.1 プランナ耐性 SQL

選んだ戦略を、**Postgres が別の計画を選びようのない形**の SQL に落とす。拡張は使わず、標準の構文だけで計画を固定する。

| 固定したいもの | 手段 |
|---|---|
| 駆動索引と走査順 | 駆動を「索引の並びと一致する `ORDER BY` ＋ `LIMIT`」を持つ部分問い合わせにする。`LIMIT` 付きの部分問い合わせは平坦化されない |
| 点検索であること（範囲全体を読む形にさせない） | 検査の `EXISTS` 内に **`OFFSET 0`** を置く。`OFFSET` を持つ `EXISTS` は単純化の対象外になり、①`WHERE` 最上位では半結合への引き上げが止まる ②`CASE` の中などでは `ANY` への変換によるハッシュ化 SubPlan（範囲全体を先に読んでハッシュ表を作る形）が作られない。どちらでも行ごとの点検索（SubPlan）として残る |
| 検査の順序 | `CASE WHEN p₁ THEN (CASE WHEN p₂ THEN p₃ ELSE false END) ELSE false END` の入れ子にする。`WHERE` の並びは Postgres が自身のコスト推定で並べ替えるが、`CASE` の評価順は保証されている |
| フィルタ駆動の候補集合 | `WITH cand AS MATERIALIZED (…)` で囲み、外側から押し込まれないようにする |

ソート駆動の例（「状態=承認待ちを金額の高い順に 20 件」・2 ページ目）。予算付きで実行するため、
**通過した行に加えて「走査の最後の行」も返し**、予算切れ・索引の終端・観測した選択率を 1 往復で判定できるようにする。

```sql
SELECT record_int, val, pos, pass FROM (
  SELECT d.record_int, d.val,
         row_number() OVER w             AS pos,      -- 何件目を読んだか
         lead(d.record_int) OVER w IS NULL AS is_last, -- 走査の最後の行か
         CASE WHEN EXISTS (SELECT 1 FROM data_index_text f
                           WHERE f.tenant_int = $1 AND f.table_int = $2 AND f.field_id = $6
                             AND f.record_int = d.record_int AND f.val = $7 OFFSET 0)  -- 状態
              THEN ( <Guard(P) を同じ形で> )
              ELSE false END             AS pass
  FROM (
    SELECT i.record_int, i.val
    FROM data_index_num i
    WHERE i.tenant_int = $1 AND i.table_int = $2 AND i.field_id = $3      -- 金額
      AND (i.val, i.record_int) < ($4, $5)                                  -- カーソル
    ORDER BY i.val DESC, i.record_int DESC
    LIMIT $scan_budget                                                     -- 走査予算（§6.2）
  ) d
  WINDOW w AS (ORDER BY d.val DESC, d.record_int DESC)   -- 入力と同じ順なので再ソートは入らない
) x
WHERE pass OR is_last
LIMIT $8 + 1;
```

| 返り値 | 判定 |
|---|---|
| `pass` の行が L 件 | 完了。カーソルは L 件目から作る |
| 最後の行が `is_last` で `pos = 予算` | **予算切れ**。観測した選択率 =（`pass` の件数）/ `pos`。最後の行のキーから再開できる |
| 最後の行が `is_last` で `pos < 予算` | **索引の終端**。区間 2 へ進む（任意列の場合）か、結果はこれで全部 |

> ⚠️ **`OFFSET 0` で単純化を止めるのは Postgres の実装に依存した振る舞い**である（`EXISTS` の単純化処理
> `simplify_EXISTS_query` が `OFFSET` を持つ部分問い合わせを対象外にしている）。data-platform §15.1 の移植性予算に 1 行足し、
> **EXPLAIN 回帰テスト（§9.1）で版ごとに固定する**。Postgres の版を上げるときの確認項目に入れる。

**汎用プランとパーティション枝刈り（実測で分かった注意点）**: `table_int` はバインド値なので、
汎用プランでは**計画時の枝刈りが効かない**。計画には全パーティションが載り、実行開始時の枝刈り
（`Subplans Removed: N−1`）で 1 つに絞られる。実測では枝刈り自体は駆動・各 SubPlan のすべてで効いたが、
**汎用プランの計画時間が 16 分割・検査 2 本で 8.6ms** かかった（個別プランは 0.4ms 前後）。
計画時間は「パーティション数 × 部分問い合わせの数」に比例するので、data-platform §3.8 の 64 分割では 30ms を超える見込みである。
駆動索引・SubPlan・走査順という計画の形は汎用でも個別でも同じで、違うのは枝刈りの時点と計画時間だけである。

- **data の読取用の接続では `plan_cache_mode = force_custom_plan` を既定にする**（接続確立時に設定する）。
  個別プランは計画時に 1 パーティションへ枝刈りされ、計画時間が毎回 1ms 未満で読める。
  汎用プランは接続ごと・形状ごとに初回 30ms 超を払い、その揺れが p99 に出る。prepared statement による
  構文解析の省略（data-platform §16.3）は個別プランでも効く。性能測定（§9.3）で見直す
- `table_int` を SQL テキストに埋め込めば汎用プランでも計画時に枝刈りできるが、テーブルごとに別の SQL になり
  形状キャッシュが効かなくなるので採らない
- パーティション数を決めるとき（data-platform §3.8）は、この計画時間も判断材料に入れる

**プランキャッシュのキー**（data-platform §16.3）に**戦略の種別**を足す。戦略は閲覧者の材料の大きさで変わるが、
キャッシュに入るのは「どの戦略を選んだか」だけで、材料そのものは入らない。

### 6.2 予算付き実行と切替

推定は外れる（§1.2 ④）。外れたときの損失に上限を付けるため、**ソート駆動は走査予算付きで実行する**。
予算切れの判定は §6.1 の SQL の返り値で行う。

```text
1. 戦略 A（ソート駆動）を、走査予算 B で実行する
2. L 件そろえば終了
3. 予算切れなら、観測した選択率で推定を更新し、次のどちらかを選ぶ
     a. 次善の戦略（フィルタ駆動）の方が安い → 切り替える。A の途中結果は捨てる（混ぜない）
     b. まだ A の方が安い → 最後に読んだキーから予算を 2 倍にして A を続ける（途中結果は保持してよい）
```

- **同じ戦略を続けるときだけ途中結果を保持できる**（同じ全順序の上を先へ進むだけなので、重複も欠落も起きない）。
  別の戦略へ移るときは必ず捨てる（PIT-76）
- 別戦略への切替は **1 リクエスト内で最大 1 回**。切替先も候補件数の上限付きで実行し、それも超えたら
  安全計画（擬似列駆動・全述語検査。正しいが遅い）に落とす。**安全計画のコストに上限は無く**、
  `statement_timeout` と受付制御（§5.4）でしか抑えられない
- 切替が起きたことはフィードバック（§8）に記録し、次回以降の推定に効かせる

**予算の決め方**:

| 段 | 予算 B |
|---|---|
| **O1**（統計表なし） | フィルタ駆動の候補件数 c が件数探索の上限内なら、**フィルタ駆動の実コスト（c から直接決まる）を A の 1 エントリあたり単価で割った件数**。上限を超えたら c が分からないので、**`L × K`（K = 8）から始めて倍々に増やす**。予算切れのたびに件数探索の上限を「これまでの走査件数の 10 倍」に広げて c を測り直し、c が測れた時点で上の式に切り替える |
| **O2**（統計あり） | 次善の戦略の推定コストを A の 1 エントリあたり単価で割った件数 |

**この方式で言える上限と、その前提**: 予算を「次善の戦略のコスト」に合わせる方式は、スキーレンタル問題と同じ構造で、
**次善の戦略のコストが正しく分かっていて、単価が較正されていれば**、最良の戦略の約 2 倍に収まる。
倍々方式（O1 で c が分からない間）は、各回の件数探索を含めて最良の約 4 倍を目標とする。
次善の戦略のコストを過大に見積もると、A が予算内に終わっても比は上限なく悪化し得る。
**前提が崩れたときの最終的な上限は `statement_timeout` と受付制御**であって、この方式ではない。

### 6.3 カーソルは戦略に依存させない

次のページを別の戦略で取ってよいように、**カーソルにはソートキーの値・`record_int`・区間番号（§5.1）だけを入れる**（スナップショット読取では、これに基準位置の `snapshot_seq` を加えて後続ページも同じ集合に束縛する・data-platform §3.3）。
走査位置や戦略名は入れない。どの戦略も「カーソルより後ろ」を同じ全順序（ソートキー → `record_int`）で定義するので、
戦略が変わってもページ間の重複・欠落は起きない（ライブページングの契約・data-platform §3.3 はそのまま）。

### 6.4 一括実行（バッチ駆動）

単発の SQL で表しにくい形——リンクを 2 段以上たどる条件、グリッドのルックアップ列の解決（data-platform §16.9 の N+1）——は、
Rust 側で段を分けて実行する。

```text
段 1: 駆動から record_int を最大 B 件取る
段 2: 各条件について  … 一括検査。`WHERE record_int = ANY($ids)` だけでは点検索を保証できない（配列長と
      `plan_cache_mode` で計画が変わり得る）ので、§9.1 で計画形状を検査し、点検索にならない場合は下の形に倒す
段 3: 足りなければ段 1 へ。観測した選択率で B を調整
（集合の和・積・差は record_int の Roaring ビットマップで Rust 側に持つ。個別共有の集合も同じ形で持てる）
```

往復は増える。各段を別 SQL に分けても実行計画を選ぶのは Postgres なので、**点検索であることは §9.1 の
回帰検査で確かめる**。既定の形は `ANY($ids)` だが、検査で点検索にならない配列長・`plan_cache_mode` の組み合わせが
見つかった場合は、外側を `unnest($ids) AS b(id)` にし、各検査を `OFFSET 0` 付きの相関 `EXISTS` にした形へ倒す
（外側が配列の各要素になり、内側は §6.1 と同じく行ごとの SubPlan になる）。配列長には上限（既定 1,000）を置き、
超える場合は段を分ける。
単発 SQL が使える形では単発 SQL を優先し（往復 1 回）、バッチ駆動はリンク多段とルックアップ解決に使う。

## 7. 認可との関係

### 7.1 最適化は行述語を弱めない

`Guard(P)` は**生成される SQL のすべての出力行に、P 全体の検査が付いている**ことを型で保証する。

- 降下（`lower.rs`）の出力は「駆動」「検査列」「`Guard`」の 3 部からなる中間表現で、`Guard` を持たない値は作れない
- **認可駆動のときも P 全体の検査を残す**。和集合の各要素は P のどれかの選言を満たすので理屈の上では冗長だが、
  冗長に検査しておけば「駆動の組み立てを間違えた」が漏洩につながらない。検査は最初に当たった選言で止まるので安い
- 計画のどこかで失敗したら安全計画に落とす。**行述語を省いた計画に落ちる経路は存在しない**

### 7.2 事後検査（Rust による独立した再評価）

v1 の行述語は SQL の中だけで評価している。v2 ではオプティマイザが述語の置き場所と順序を変えるため、
**本体（`data_record`）を取ったあとで、同じ `PolicyExpr` を Rust で独立に評価し直す**。

- 評価器は SQL へのコンパイラ（`policy/compile.rs`）とは別実装にする（`mask.rs` のロール水準の評価器と同じ層）。
  同じバグを二度書かないため
- 評価は**行述語の意味論**で行う（§3.3。値の無い行の `Ne` は偽、数値は数値として比較）。
  クエリ条件の 2 値論理の評価器を流用すると、Guard の降下の誤りと同じ誤りを犯して検出できなくなる
- 対象はページの行（≤ L）だけなので、コストは無視できる
- 不一致の行は応答から落とし、**セキュリティ指標として記録して警報を出す**（オプティマイザか SQL 生成のバグを意味する）
- これで、オプティマイザの誤りは「見えるべきでない行が出る」ではなく「見えるはずの行が欠ける」に倒れる。
  CLAUDE.md の「二段 authz」を構造化データの読取でも文字どおりにする
- 集計と件数には行が無いので事後検査が効かない。ここは §9 の強制戦略テストと `policy_threat_it.rs` で担保する

### 7.3 統計はサイドチャネルになる（PIT-75）

統計は**可視性を無視して全行から**集める。したがって:

- **推定値・最頻値・ヒストグラム・選んだ戦略名・予測コストを利用者に返さない。** エラー文言にも含めない。
  **テーブルの owner にも見せない**（owner も行述語の対象であり、最頻値やヒストグラムは見えない行の値そのものである）。
  運用向けには、値を含まない数値の指標（推定と実測の比・戦略の内訳・予算切れの率）だけを出す
- **UI の値候補（フィルタのプルダウン）に値頻度表を使わない。** 見えない行にしかない値が候補に出る。
  候補は可視行に対するクエリで作る
- 計画の違いは応答時間の差として観測できる（見えない行に「承認待ち」が多いかどうかで速さが変わる）。
  これは消せない残余リスクとして記録する。機微なテーブルでは、テーブル設定でコストベース選択を止めて
  固定戦略にできるようにする

### 7.4 既存の不変条件との対応

| 不変条件 | オプティマイザでの扱い |
|---|---|
| 値は必ずバインド（PIT-21） | 変更なし。降下は `lower.rs` 1 箇所 |
| プランキャッシュに材料を混ぜない（data-platform §16.3） | 戦略の種別だけをキーに足す。材料の大きさは計画時に使って捨てる |
| リクエストを跨いだ材料キャッシュの禁止（PIT-18） | クエリ条件の統計と件数探索は材料ではない（全員共通・権限を表さない）のでキャッシュしてよい。**行述語の選言の件数探索はキーが材料から作られるのでキャッシュしない**。材料は data-platform §16.4 のリクエストスコープのメモ化のみ |
| マスク列を filter/sort に出せない（PIT-19） | 変更なし。マスク列は統計を持っていても駆動・検査に出てこない |

## 8. フィードバック

- 実行ごとに `(形状ハッシュ, 戦略, 各段の推定行数, 実測行数, 走査した索引エントリ数, 返した行数, 所要時間)` を記録する（メモリ上のリングバッファ＋OTel へ抽出）
- **第一の指標は「走査エントリ数 ÷ 返した行数」**（走査効率）。応答時間は同居テナントやキャッシュで揺れるが、
  走査数は計画の良し悪しを直接表す。テーブル・ビュー単位の p95 をダッシュボードに出す（data-platform §14）
- **補正係数**: ソート駆動で「予想した走査数」と「実際の走査数」の比を、`(テーブル, フィルタ列, ソート列)` ごとに
  指数移動平均で持つ。§1.2 ④の相関はこの係数で次回から吸収される
- 推定と実測が 10 倍以上ずれることが続いたら、そのテーブルの統計収集を前倒しで起動する
- 深いページで劣化し続ける複数ソートの形は、**複合索引の材料化（data-platform §5.3）の候補**として管理画面に出す。
  未索引列でのフィルタ要求が多い列は**索引の昇格（data-platform §10）の候補**として出す
- 学習した値は**テーブルと列の組の単位**に限る。利用者ごとには持たない（利用者ごとの推定は材料から毎回作る）

## 9. 検証

### 9.1 計画の回帰（EXPLAIN）

data-platform §14 の代表クエリ集合について、戦略ごとに**期待する計画の形**（駆動索引・SubPlan であること・
ハッシュ結合が無いこと・計画時に 1 パーティションへ枝刈りされていること）をアサートする。
§6.4 のバッチ駆動の検査クエリ（`= ANY($ids)` と `unnest` 形）も、配列長（1・100・上限）× `plan_cache_mode`
（既定・`force_custom_plan`・`force_generic_plan`）の組み合わせで計画が点検索であることを確かめる。
既定の個別プランに加え、汎用プランの形も確かめる。`EXPLAIN (GENERIC_PLAN)` は `ANALYZE` と併用できないので、
形は `GENERIC_PLAN` で、実行時の枝刈り（`Subplans Removed`）は `SET plan_cache_mode = force_generic_plan` の下で
`EXPLAIN ANALYZE EXECUTE` で確かめる。

### 9.2 正しさの差分テスト

| テスト | 内容 |
|---|---|
| **強制戦略テスト** | 同じクエリを**全戦略で強制実行**し、結果の集合と順序が一致することを確かめる。コストモデルは速さにだけ効き、結果には効かないことを固定する |
| **参照実装との比較** | 擬似列で全件を歩き Rust で条件を評価する素朴な実装を参照とし、乱数で生成したスキーマ・データ（偏り・相関・値なし・多値・切り詰め値を含む）・クエリで結果を比べる（proptest） |
| **TLP（Ternary Logic Partitioning）** | 任意の述語 p について「Q の結果 = (Q ∧ p) ∪ (Q ∧ ¬p)」が成り立つことを確かめる。§3.1 の 2 値論理の下では IR 経路の区分は 2 つ。**SQL 前段の経路（Task 15.10）では 3 値論理なので `p IS NULL` を加えた 3 区分**で確かめ、SQL と IR の意味の一致を見る |
| **正規化の 1 規則ずつ** | §3.2 の各規則の前後で結果が一致すること |
| **認可** | `policy_threat_it.rs` を**全戦略で強制実行**して通す。§7.2 の事後検査が 1 件も落とさない（＝SQL 側で既に正しい）ことも同時に確かめる。値の無い行で `Ne` を含む行述語が不成立になることを固定する（§3.3） |
| **切替の一貫性** | 予算を極端に小さくして切替を必ず起こし、結果が切替なしと一致すること |

### 9.3 性能

- 偏り（Zipf）・相関（状態と作成日）・値なしの多い列・多テナントの雑音を含むデータで、
  **「Postgres 任せの単発 SQL」と比べた p50 / p95 / p99** を測る。自前プランナの採否はこの差で判断する
- **後悔比**（実際の所要時間 ÷ 全戦略を試した中での最短時間）を代表クエリごとに出し、**p95 で 2 倍以内**を目標にする
- **ベンチのデータは顧客データを使わず、統計から合成する。** 実テナントのテーブルの形（行数・列の型・値の種類数・
  最頻値の頻度の形・値なしの率・列の間の相関の強さ）だけを、値を含まない数値として取り出し、それに合う疑似データを
  生成する。Garoon の性能改善でも、本番データを直接使わず統計処理の結果だけを参照して疑似データを作っている（§12）。
  取り出す数値は値そのものを含まないので、統計を利用者に見せない原則（PIT-75）とも衝突しない

## 11. 判断の記録

| 事項 | 決定 | 理由 |
|---|---|---|
| **クエリ条件の意味論を 2 値論理にする**（§3.1） | **採る**（2026-10・human） | workflow IR と揃えないと `data.query` に翻訳層が要る。SQL 前段だけが 3 値論理を翻訳すればよい。行述語は v1 の意味論のまま（§3.3） |
| **多値列と数値の等値で、workflow の評価器（`eval.rs`）とどう揃えるか**（§3.1） | **`eval.rs` を data の表に合わせる**（2026-10・human） | `eval.rs` の現行の配列の扱い（`Eq` が配列全体一致・`In` が常に偽）は業務の条件として直感に反する。既存の分岐への影響は Task 15.7 で検出・警告してから切り替える |
| **`record_id` を内部整数 `record_int`（`int8`）にする** | **採る**（2026-10・human） | 索引行の縮小（約 7%）と、和集合・交差・共有集合の Rust 側ビットマップ演算（§5.1 の OR 駆動・§6.4）。kintone・SharePoint も内部は整数キー。採番はプール共通のシーケンス、外部には出さない（data-platform §3.2）。JSONB キーの書換えと同じ Task 15.1 で入れる |
| **事後検査を必須にする**（§7.2） | 採る | オプティマイザが述語の配置を変える以上、独立した二段目が無いと誤りが漏洩に直結する |
| **機微なテーブルでコストベース選択を止められるようにする**（§7.3） | 採る（既定はオン） | 応答時間のサイドチャネルを消す手段がこれしか無い |
| 件数を既定で数えない | 採る | data-platform §5.4。kintone も件数取得を遅くなる要因として挙げる（§12） |
| SharePoint の固定 5,000 件しきい値・kintone の固定ヒントを真似るか | 採らない | 固定の件数制限は予測コストによる受付制御（§5.4）で代える。Postgres は行ロックが表ロックへ広がらないので、件数で縛る必要が無い。固定ヒントは「データ量や分布が変わると足かせになる」（kintone 自身の認識）ので、リクエストごとの選択と回帰テストで代える |

## 12. 他社の実装との対照

同じ制約（全テナント・全アプリ共有の表 × アプリごとに違うスキーマ）に当たった 3 社の公開情報を並べる。
**3 社とも「本体は汎用の表、検索は型ごとの索引表」という本設計と同じ形に行き着いており、同じところで苦労している。**

### 12.1 kintone（サイボウズ）

- **構造**: レコード本体はスキーマレスに保存し、検索用に**データ型ごとのインデックステーブル**（`column_id` でフィールド、
  `row_id` でレコードを特定）を別に持つ。複数値（複数選択・ユーザー選択）は親レコードにぶら下がる子行として持つ
  （[Cybozu Inside Out 2026-07](https://blog.cybozu.io/entry/2026/07/23/133000)）
- **JOIN 順序の自前決定**: 「各テーブルの行数の概算値を見積もり、どのテーブルから JOIN すれば良いのかを計算して組み立てる」
  改善が 2018 年 7 月の更新で最も効き、ある利用者の 99 パーセンタイル応答時間が約 1/6 になった。行数は COUNT が遅いため
  MySQL の EXPLAIN の推定で代えている（[Cybozu Inside Out 2018-08](https://blog.cybozu.io/entry/2018/08/08/080000)）。
  kintone はこのほかにも、検索条件から JOIN 順序を決めたりクエリを書き換えたりする最適化機構を持つ
  （[Cybozu Inside Out 2019-01](https://blog.cybozu.io/entry/2019/01/31/080000)）
- **アクセス権**: 読取時の判定はサブクエリで表され、大量のレコードを走査することがあった（カバリングインデックスで緩和）。
  レコードのアクセス権は保存時に事前評価して DB に持つ方式で、権限変更が重い（data-platform §6.6）
- **複数値の絞り込み**: EXISTS の相関サブクエリになり、100 万件で約 3 秒。`SEMIJOIN(DUPSWEEDOUT, FIRSTMATCH)` ヒントで約 0.75 秒。
  ヒントは「効果を確認できた箇所に限って」有効にし、「データ量や分布、DBのバージョンが変わると最適な実行計画も変わる」と認識している
- **巨大 OFFSET** は「未だ我々を悩ませる問題」とされ、ID 基準のページングを利用者に案内している
- **遅い絞り込みとして公式に挙がるもの**: 複数選択・ユーザー選択・テーブル内フィールド・部分一致・OR の複合、件数取得（`totalCount`）
  （[cybozu.dev](https://cybozu.dev/ja/kintone/tips/best-practices/performance/complement-technical-consideration-points/)）
- **Garoon（同社）**: 表示するユーザーが 1 人か多数かで駆動表を切り替え、ヒントで指定している。性能検証の疑似データは
  本番データの統計処理の結果だけから作っている（[Cybozu Inside Out 2024-08](https://blog.cybozu.io/entry/2024/08/12/080000)）

### 12.2 SharePoint / Microsoft Lists

- **構造**: 全リストのデータを単一の表（AllUserData）に持つ（[TechNet](https://learn.microsoft.com/en-us/archive/technet-wiki/53460.sharepoint-troubleshooting-5000-list-view-threshold-limit-issue)）
- **5,000 件しきい値**: 5,000 行を超えて行ロックを取ると SQL Server が表全体のロックへ切り替えるため
  （[Microsoft サポート](https://support.microsoft.com/en-us/sharepoint/lists/data-and-lists/list-view-threshold-for-large-lists-and-libraries)）
- **索引**: 1 リスト 20 本まで。しきい値を超えるビューは、最初の絞り込みが索引列で、かつ件数を閾値未満に減らす場合に限り表示される。
  保存済みビューと並べ替えで索引が自動作成され、2 万件以上は裏で作られる（[PnP](https://pnp.github.io/community-docs/articles/large-lists-large-libraries-in-SharePoint.html)）
- **ルックアップ**: 結合は 12 本まで。項目ごとの固有権限は 5 万まで（推奨 5,000）

### 12.3 Salesforce（参考）

マルチテナントのため DB の統計に頼らず**自前の統計と事前の問い合わせ（pre-query）**で計画を選び、
**共有設定による絞り込みの選択性も**駆動の候補として比べる
（[Force.com Query Optimizer Secrets](https://developer.salesforce.com/blogs/engineering/2013/12/force-com-query-optimizer-secrets-you-can-use-today)・
[Large Data Volumes ガイド](https://developer.salesforce.com/docs/platform/salesforce-large-data-volumes-bp/guide/ldv-deployments-infrastructure-salesforce-query-optimizer.html)）。

### 12.4 本設計への反映

| 学び | 出典 | 反映先 |
|---|---|---|
| 駆動（JOIN 順序）を行数の見積もりで自前に決める | kintone・Salesforce | 本書 §4〜§5。見積もりは DB の推定ではなく上限付きの件数探索（Postgres の推定はプールの雑音で外れる・§1.3） |
| 利用者の見える範囲で駆動を変える | Salesforce・Garoon | 認可駆動（§5.1） |
| 別の列どうしの OR が遅い | kintone | OR 駆動（§5.1） |
| 複数値の絞り込みが子行への相関サブクエリで遅い | kintone | 本設計は多値を同じ `record_int` の `ord` 違いの行で持つので子行への結合が無い。点検索 1 回で済む |
| 巨大 OFFSET | kintone | OFFSET を廃止して keyset（data-platform §5.3） |
| 件数取得が遅い | kintone | 件数は既定で数えず、別リクエストで非同期に取る（data-platform §5.4） |
| 応答時間より走査行数を見る | kintone | 第一の指標を走査効率に（§8・data-platform §14） |
| 固定ヒントはデータが変わると足かせ | kintone | リクエストごとの選択＋回帰テスト。テーブル単位の固定戦略は機微なテーブル用に限る（§7.3） |
| 事前評価の ACL は権限変更が重い | kintone | 事前展開しない（data-platform §6.6） |
| ルックアップの結合数に上限 | SharePoint | 1 ビュー 12 列まで・列ごとに一括解決（data-platform §8.2） |
| 索引の本数上限と自動作成 | SharePoint | 1 テーブル 20 列・2 万行未満は即時、それ以上は裏で（data-platform §10） |
| 整数のレコードキー | kintone・SharePoint | `record_int`（data-platform §3.2） |
| 本番データを使わない性能検証 | Garoon | 統計から合成したベンチデータ（§9.3） |
| 固定の件数しきい値 | SharePoint | **採らない**。予測コストによる受付制御（§5.4） |
