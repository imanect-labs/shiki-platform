# SLO: チャット・エージェント・LLM・検索・サンドボックス・AI の品質

原則・段・アラート・バジェットの方針は [README.md](./README.md)。数値の列は **SaaS ／ オンプレ**。

## 0. この領域の考え方

AI の流れは、普通の Web API と次の点が違う。SLO の形はここから決めた。

| 違い | 帰結 | 出典 |
| --- | --- | --- |
| 応答の長さが入力・モデル・ツールの使い方で大きく変わる | 回答完了までの時間は SLO にしない。「動き出すまで」「途中で止まらない」「最後まで終わる」を測る | MLflow、arXiv 2410.14257 |
| エージェントはツールを使ってから本文を書く。推論モデルは考える時間が仕様 | 本文の初回トークン（TTFT）ではなく、**最初に見える進捗**を主にする。TTFT はモデル別の監視指標 | Google AI/ML 信頼性ガイド、vLLM／NVIDIA の定義 |
| 平均のトークン間隔は、途中の長い停止を隠す | 途中の停止（一定時間イベントが途切れたか）を run 単位で数える | arXiv 2410.14257 |
| 最大の依存先は外部のモデル提供元（SLA 99.5〜99.9%） | 「shiki 起因の失敗」と「利用者から見た失敗」を分けて 2 本持つ。後者は切り替えが入るまで目標扱い | Vertex AI・Microsoft の SLA、[dependencies.md §3](./dependencies.md#3-llm-の提供元) |
| 意味の品質は、正解が本番に無く、抜き取りの件数が少なく、判定器も誤る | 品質は SLO にせず、リリース前の評価ゲートと、最低件数付きの監視指標で扱う | Anthropic の評価の記事、統計的な評価の記事 |
| エージェントの「完了した」という自己申告は当てにならない | 成否は、環境の状態など**検証できた結果**で判定する（評価ゲート側） | Anthropic、tau-bench |

## 1. チャットの run

チャットの送信は単一 Tx で run（`generation_run`）を作って jobq に積み、ワーカーが claim して実行する。イベントは `generation_event(run_id, seq)` に記録され、SSE は DB の再生＋ライブで届く（design §4.4.1）。
SLI はこのイベント列から run 単位で計算する（[measurement.md §1](./measurement.md#1-計測の方針)）。

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| CHAT-1 | T1 | run が**着手可能になってから**開始（`status{running}`）まで 2s 以内の割合 | 99% ／ 99% | 〔設〕ワーカーの空振り待ち 300ms |
| CHAT-2 | T1 | 開始から**最初に見える進捗**まで、標準モデル: 3s 以内 ／ 10s 以内の割合 | SaaS 95% ／ 99%、オンプレ 5s で 95% ／ 15s で 99% | 〔業〕〔測〕〔仮〕 |
| CHAT-2r | T1 | 同、推論モデル: 15s 以内 ／ 45s 以内の割合 | 95% ／ 99%（両方とも） | 〔設〕最初の応答の上限 60s〔仮〕 |
| CHAT-3 | T1 | 途中で、標準モデルは 30s・推論モデルは 60s を超えてイベントが途切れなかった run の割合 | 99% ／ 99% | 〔仮〕 |
| CHAT-4 | T1 | **shiki 起因で**失敗しなかった run ÷ 終わった run | 99.9% ／ 99.9% | human 決定の水準 |
| CHAT-5 | T1（目標扱い） | **利用者から見て**最後まで答えた run ÷ 終わった run（モデル提供元の障害を含む） | 99.5% ／ 99.5% | 〔業〕提供元の SLA |
| CHAT-6 | T2 | 再接続（`Last-Event-ID`）で、抜けも重複もなく続きが届いた割合 | 99.9% ／ 99.9% | 〔仮〕 |
| CHAT-7 | T2 | 取消の要求から run の取消確定まで 10s 以内の割合 | 99% ／ 99% | 〔設〕ステップ境界・ストリーム読取での検知〔仮〕 |
| CHAT-8 | T2 | ワーカーが落ちた run が、3 分以内に別のワーカーへ引き継がれた割合 | 99.9% ／ 99.9% | 〔設〕リース失効後の猶予 120s＋回収の周期 30s |

### 1.1 定義の細目

**CHAT-1（開始）**
- 起点の「着手可能」は `max(run の作成時刻, 同じスレッドの前の run が終わった時刻)`。チャットは 1 スレッドで 1 run ずつ直列に実行するので、前の run の待ちは利用者の操作による待ちとして除く。
- 送信の受付（`POST /threads/{id}/messages` の 202）は API-1・API-2 で測る。

**CHAT-2（最初に見える進捗）**
- 「最初に見える進捗」は `token`・`thinking`・`tool_call`・`plan` のいずれか最初のイベント。shiki が出す `status` や `context_usage` は数えない（内容が変わらないため）。
- モデルの区分（標準／推論）はモデルカタログに持たせる。区分の無いモデルは標準として扱う。
- 推論モデルで、提供元が思考を流さない（要約が遅れて届く）場合、最初の進捗は本文まで来ない。CHAT-2r の 45s はそのための値で、最初の応答の上限 60s〔設〕より内側に置いた。
- オンプレの値は、GPU を共有した構成での TTFT 4.11〜4.96s〔測・1 点のみ〕と、GPU のサイジング（Task 8.13・未作成）を前提にした仮置き。基準構成が決まったら負荷試験で置き直す。
- SaaS の値は、MLPerf の対話シナリオ（TTFT ≤ 2s）〔業〕に、検索・ツール選択の 1 往復ぶんを足したもの。

**CHAT-3（途中で止まらない）**
- イベント間の空白を数える。次の区間は空白に数えない:
  - ツールの実行中（`tool_call` から対応する `tool_result` まで）。画面に「実行中」が出ている。ツールそのものの遅さは TOOL-1・SBX で見る
  - 承認待ち（`approval_requested` から `approval_resolved` まで）。待ちの持ち主は承認者
  - サブエージェントの実行中（`subagent_run` の区間）。中のイベントは親に中継される
- ワーカーの引き継ぎ（CHAT-8）で生じた空白は、CHAT-3 に**数える**（利用者には止まって見える）。
- **提案**: 長い思考・長いツールの間も、ワーカーが一定間隔（例 10s）で進捗のイベントを出すと、利用者の安心と、本物の停止の検知が両立する（Temporal の heartbeat の考え方〔業〕）。イベントの語彙が増えるので実装時に判断する。

**CHAT-4・CHAT-5（完走）**
- 終わり方を次の 4 つに分ける（今は `status` だけでは区別できないので、終わり方の列を足す・[measurement.md §4](./measurement.md#4-計測の現状と穴)）。

  | 区分 | 例 | CHAT-4 | CHAT-5 |
  | --- | --- | --- | --- |
  | 正常 | 回答を出し終えた | 良 | 良 |
  | 意図した停止 | 利用者の取消・予算による停止・ポリシーによる拒否・承認の却下／期限切れ | 対象外 | 対象外 |
  | shiki 起因の失敗 | 内部エラー・引き継ぎの失敗・出力上限での途中切れ（書き直し 3 回で収まらない）・ツール呼び出しの形式エラーで打ち切り・ループ検出 | 悪 | 悪 |
  | 提供元起因の失敗 | 提供元の 5xx・最初の応答のタイムアウト・ストリーム途中の切断（再送でも救えない） | 対象外 | 悪 |

- 途中切れとループ検出を「shiki 起因」に入れるのは、出力上限・プロンプト・ツールの設計で防ぐべきものだから。モデルの性質で多発する場合も、モデルの選定と設定は shiki の責任とする。
- llm-gateway の再送（接続前の失敗を最大 4 回・ストリーム開始直後の切断を最大 2 回〔設〕）で救えた run は良。
- **CHAT-5 が目標扱いの理由**: 外部の提供元は SLA 99.5%（Vertex）〜99.9%（Azure）で、別モデルへの切り替えは未実装。重要な依存先より高い信頼性は出せないので、99.5% は依存先と同じ水準になる。
  切り替え（design §4.5 のフォールバック）が入ったら 99.9% に上げ、目標扱いを外す。オンプレはローカル推論が 1 系統なら目標扱いのまま、GPU を N+1 で冗長化した構成で 99.9% にする。
- テナントの下限（README §6）を CHAT-4 に適用する。

**CHAT-6（再接続）**
- サーバ側だけでは抜けを判定できないので、Web のクライアントが `seq` の飛び・重複を検知して報告する（送るのは件数だけ）。加えて合成監視で、接続を切って再接続する試験を定期的に流す。

**CHAT-8（引き継ぎ）**
- 引き継ぎは、ステップ境界のチェックポイントから再開する（生成途中の LLM ストリームは捨てて、そのステップだけ作り直す）。引き継ぎに失敗した run は CHAT-4 の悪に数える。

### 1.2 監視指標（T3）

| 指標 | 見ること |
| --- | --- |
| モデル別の TTFT・トークン間隔（ITL）の分布 | 遅いのが提供元か shiki かの切り分け。トークン間隔の中央値は毎秒 10 トークン以上（人が読む速さより速い）を目安にする〔業〕 |
| ステップ上限・トークン上限・費用上限に達した run の割合 | 上限の設定が厳しすぎないか。通常チャットの 6 ステップを使い切るのは 96 run 中 2 件（2026-10）〔測〕 |
| 途中切れ（Truncated）・ループ検出・失敗からの回復（`failure_recovery`）の率 | モデル・プロンプトの変更で増えていないか |
| 承認待ちの時間・期限切れの率 | 承認の運用が回っているか（SLO の対象外） |
| サブエージェントの失敗率 | 親の失敗につながっていないか |
| 正常に終わった run 1 件あたりのトークン量・費用 | 安いモデルで失敗が増えると悪化して見える（成功あたりで見る）〔業〕 |
| run あたりのイベントの間隔が急に縮む・同じツールを同じ引数で繰り返す | 暴走の兆候 |

## 2. エージェントのツール

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| TOOL-1 | T3 | ツール別の失敗率と所要時間（原因の区分つき） | — | — |

- ツールの失敗を 4 つに分ける: **成功** ／ **利用者・入力の誤り**（存在しない URL・権限の無い文書）／ **外部の失敗**（Web 検索・取得先の 5xx・タイムアウト）／ **shiki の失敗**。
- 外部の Web に依存するツール（`web_search`・`web_fetch`・`browser`）は、外部に SLO が無いので SLO から外す（GitLab が外部依存のジョブを外すのと同じ考え方〔業〕）。shiki の失敗だけが CHAT-4 に効く。
- 文書検索（`doc_search`）は §4 の SRCH で、コード実行は §5 の SBX で測る。
- ツール呼び出しの引数がスキーマに合わない率は、モデル別に評価ゲート（§7.1）で見る。本番では T3。

## 3. LLM（llm-gateway）

llm-gateway は LLM 呼び出しの単一チョークポイントなので、提供元・モデル別の計測はここで行う。

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| LLM-1 | T2（目標扱い） | 論理モデルごとに、再送・切り替えのあとで成功した呼び出しの割合（利用者自身の上限による拒否・不正な要求を除く） | 99.9% ／ 99.5% | 〔業〕 |
| LLM-2 | T3 | llm-gateway 自身が足す時間（提供元との通信を除く）が 99% で 50ms 以内 | — | 〔仮〕 |

- LLM-1 は内部の依存先 SLO（チャット・ワークフロー・ミニアプリの土台）。切り替えが入るまでは目標扱い。
- **429 の扱い**:
  - 利用者自身の月次上限・ミニアプリの日次予算による拒否: 対象外（T3 で率を見る）
  - 提供元の 429・529 を再送で吸収した: 良（再送率は T3）
  - 提供元の 429・5xx が利用者に届いた: 悪
- **切り替えで成功したもの**は良に数えるが、別モデルで答えたことは「品質の劣化」なので、切り替えで答えた割合を T3 で必ず出す（Google の Quality SLI〔業〕）。ストリームが始まった後の失敗は切り替えられない（利用者には途中で止まって見える）。
- **T3 の指標**: 提供元別のエラー（5xx・429・タイムアウト・途中切断）、再送の率、最初の応答のタイムアウト（60s〔設〕）の率、提供元の毎秒トークン数（Vertex の保証は Gemini 2.5 Flash で毎秒 80 トークン〔業〕）。
- **オンプレのローカル推論（vLLM）の先行指標**: 要求の待ち時間（`vllm:request_queue_time_seconds`）の p95、待ち要求数、KV キャッシュの使用率（1.0 に近いと追い出しが起きてトークン間隔が跳ねる）、受付の拒否。GPU が飽和すると TTFT は待ち時間で決まるので、CHAT-2 より先にこちらが動く〔業〕。
- **バックグラウンドの仕事は後回しにできる**: 自律エージェントの長い run・サブエージェント・ワークフローの `llm.invoke` は、GPU が飽和したら対話の run より後に回す（Gateway API Inference Extension の Critical／Sheddable の考え方〔業〕）。実装は優先度の判断が要るので、オンプレのサイジング（Task 8.13）で決める。

## 4. 検索（RAG）

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| SRCH-1 | T1 | 検索（`POST /search`・`doc_search`）が成功した割合（結果 0 件も成功） | 99.9% ／ 99.9% | human 決定の水準 |
| SRCH-2 | T1 | 検索が 2.5s 以内 ／ 8s 以内に返った割合（pre-filter・post-filter を含む） | 90% ／ 99%（両方とも） | 〔測〕rerank 1.6s（CPU） |
| SRCH-3 | T2 | 共有の付与から 5s 以内に、付与された人の検索結果へ出た割合（合成監視） | 99.9% ／ 99.9% | 〔既〕PIT-3 |

- SRCH-2 は reranker を GPU に載せたら 1s／4s に締める（API-3 と同じ）。
- 権限の解除・ファイルの削除の後に結果へ出るのは不変条件の破れでインシデント（README §7）。SLO にしない。
- テナントの下限（README §6）を SRCH-1 に適用する。
- **T3 の指標**（本文に触れずに出せるもの）:

  | 指標 | 見ること |
  | --- | --- |
  | **post-filter で落ちた割合**（post-filter が除いた件数 ÷ 取得した件数） | ほぼ 0 のはず。上がったら pre-filter の構造タグか索引が古い。利用者は二段目で守られているが、防御が一段減っている |
  | pre-filter の可読タグが上限 500 を超えて、テナント単位に縮退した検索の割合 | 縮退が増えると post-filter の負担と、結果の取りこぼしが増える |
  | 結果 0 件の率・上位の類似度の分布 | 索引の欠け・埋め込みモデルの不一致 |
  | 引用の付いた回答の割合（文書検索を使った run のうち） | 根拠を示さずに答えていないか |
  | 引用先が、その回答のために取得した文書に含まれている割合 | 必ず 100%。外れたら不具合として調べる（権限の外ならインシデント） |
  | 埋め込み・rerank・Qdrant・Tantivy・OpenFGA の所要時間 | どこが遅いかの切り分け |
  | ヘルプ検索のキーワード縮退率（`shiki.help.keyword_fallbacks`） | 埋め込みが使えていない |

## 5. サンドボックス（コード実行）

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| SBX-1 | T2 | 実行が基盤の失敗（起動失敗・監督プロセスの異常・結果の喪失）で終わらなかった割合 | 99.5% ／ 99.5% | 〔仮〕 |
| SBX-2 | T2 | gVisor の起動（作成から準備完了）が 500ms 以内 ／ 2s 以内の割合 | 95% ／ 99%（両方とも） | 〔測〕p50 131ms・p95 133ms（KVM なしの LXC） |
| SBX-2w | T3 | wasm の起動が 200ms 以内の割合 | 99% | 〔測〕p95 13ms |

- 実行の結果を 5 つに分ける: 成功 ／ 利用者・エージェントのコードの誤り（終了コード非 0・例外） ／ 利用者の上限（壁時計 30s・メモリ 512MB〔設〕） ／ 方針による拒否（egress 等） ／ 基盤の失敗。**SLO に数えるのは基盤の失敗だけ**。
- コードの誤りの率は、エージェントの品質の指標として T3 で見る（モデル・プロンプトの変更で増えていないか）。
- 温機プール（Task 4.5・起動 200ms 未満）が入ったら、SBX-2 を 95% ≤ 200ms に締める。
- Firecracker は未計測。KVM のあるホストで計測してから SLO を置く。
- サンドボックスの脱出・egress 方針の違反はインシデント（README §7）。

## 6. ワークフロー・ミニアプリから使う AI

ワークフローの `llm.invoke`・`agent.invoke`・ミニアプリの AI API は、所要時間が生成で決まるので、ステップの所要時間を SLO にしない。
エンジン側の SLO（[async.md](./async.md) の WF-1・WF-4）と、LLM-1 で守る。`agent.invoke` の成否の区分は CHAT-4 と同じ表を使う。

## 7. AI の品質（評価ゲートと監視指標）

意味の品質（正しさ・根拠への忠実さ・関連性・安全性）は SLO にしない。理由は 3 つ。

- **正解が本番に無い**: 本番の監視は「起きたことへの反応で、正解を持たない」（Anthropic）。
- **件数が足りない**: 95% の率を 400 件で測ると、95% 信頼区間は 92.4〜96.7% になる（Wilson）。90% が 85% に落ちたことを検出するには、比べる 2 つの期間それぞれで約 685 件が要る（有意水準 5%・検出力 80%）。週に数百件の抜き取りでは、5 ポイント以上の悪化しか検出できない。
- **悪化の多くは変更が起こす**: モデル・プロンプト・検索設定の変更。変更の前に止めるほうが確実で安い。

代わりに、次の 3 段で守る（Anthropic の「スイスチーズ」の考え方〔業〕）。

### 7.1 リリース前の評価ゲート

モデル・プロンプト・ツール・検索設定を変えるときに通す。指標ごとに閾値を持ち、1 つの合計点にまとめない。

| ゲート | 内容 | 合格の目安 |
| --- | --- | --- |
| 回帰スイート | 本番で起きた失敗から作った課題（20〜50 件から始める〔業〕）。**結果を環境の状態で判定**する（予約が DB にあるか、など。エージェントの申告では判定しない） | ほぼ 100% |
| 一貫性（pass^k） | 業務上重要なエージェントの課題を k = 3〜5 回流し、全回成功した割合 | 課題ごとに閾値。1 回あたり 75% の課題は 3 回全成功が 42% になる点に注意〔業〕 |
| 道筋とツール | ツールの選択の正しさ・引数の妥当性・呼ばなくてよいときに呼ばないこと・ステップ数・費用 | 現行版から悪化しない |
| 検索（RAG） | 参照付きの評価セットで、文脈の適合率・再現率・忠実さ・回答の関連性 | 現行版との**対の比較**（同じ問題で比べる）で悪化しない |
| **権限の漏れ** | 別ユーザー・別グループ・別テナントへの問い合わせ、権限解除の直後、pre-filter と post-filter を片方ずつ止めた状態 | **100%**。0 件の漏れから言える上限は約 3/n なので、生成した数千件で回す |
| 過剰な拒否 | 危険に見えるが安全な問い（XSTest 型）と、業務領域の正当な問い | 現行版から悪化しない |
| 注入（プロンプトインジェクション） | 取得した文書・Web ページ・ツール結果に仕込んだ指示 | 0 件の追従 |
| 判定器の較正 | LLM の判定器と人の判定の一致（κ）。判定器・判定プロンプトを変えたら取り直す | κ の閾値を下回る判定器は使わない |

- 評価は自社で用意したコーパス（ヘルプの正本・合成データ）で行い、顧客のデータを使わない。
- 判定器は「分からない」と答えられるようにし、評価の観点ごとに分ける〔業〕。
- 合格した変更は、一部のテナント（同意したテナント）へのカナリアで、本文に触れない指標（途中切れ・ツールの失敗・ステップ数・費用・👎 の率）を対の比較で確かめてから全体に出す。

### 7.2 本番の監視指標（T3）

本文に触れずに出せるものを主にする。

| 指標 | 扱い |
| --- | --- |
| 👎 の率と理由のカテゴリ（`message_feedback`）・作り直しの率・途中で止めた率 | モデル・プロンプトの版ごとに分け、変化点で通知する。👎 は満足度の KPI ではなく、調べるきっかけとして使う |
| 引用・検索の指標（§4 の T3） | 同上 |
| 拒否の率・ガードレールの発動率 | ガードの版ごとに見る。デプロイ後の段差で通知する。「正しい率」が分からないので SLO にしない |

- 割合には最低件数（7 日で 400 件）を付け、満たないときは判断しない。通知は、信頼区間が前の期間と重ならないときだけにする。
- **本番の回答本文を LLM で採点する**のは、組織の設定でオンにしたときだけにする（AI 活用分析の用途分類と同じ扱い）。
  採点は llm-gateway を通してテナント内（そのテナントに許可された提供元・オンプレはローカルの判定器）で行い、保存・送出するのはラベルと集計だけにする。
  集計は最低件数（例: 50 人以上）を満たす単位でだけ出す（Anthropic Clio の考え方〔業〕）。ベンダーコンソールから本文に届く経路は作らない。

### 7.3 インシデント（README §7 の再掲のうち AI に固有のもの）

- 権限の無い人に、文書の断片・引用・ツール結果・生成 UI のデータが見えた（引用が、その回答のために権限内で取得した文書の外を指していた場合を含む）

- 実行ごと・テナントごとのコスト上限を超えた
