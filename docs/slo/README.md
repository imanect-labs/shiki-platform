## 1. 原則

1. **利用者が体感するものを、良い事象の割合で測る。** レイテンシも「1 秒以内に返した割合」と書く。部品の指標（CPU 等）は原因の調査に使う。
2. **流れ（ジャーニー）から決める。** [journeys.md](./journeys.md) の台帳を業務への影響で順位付けし、上位から SLO を割り当てる。台帳に載った流れで SLO も監視指標も持たないものを残さない。
3. **段（Tier）で数を抑える。** 網羅はするが、人を呼び出す SLO は少数に絞る（§3）。「優先順位の議論で持ち出して勝てない SLO は持つ価値がない」。
4. **待ちの持ち主を分ける。** 利用者・承認者・外部サービス・利用者自身が設けた上限による待ちは、shiki の SLI から外して別に数える。shiki が持つ待ちだけを測る。
5. **入力の大きさで決まる所要時間は SLO にしない。** チャットの回答完了・ワークフローの run 全体・大きなファイルの転送など。代わりに「動き出すまで」「止まらないこと」「最後まで終わること」を測る。
6. **AI は 3 層に分ける。** 運用（可用性・応答）と構造（途中切れ・ツールの破綻）は SLO。意味の品質（正しさ・根拠への忠実さ）は評価ゲートと監視指標（[ai-agents.md §7](./ai-agents.md#7-ai-の品質評価ゲートと監視指標)）。
7. **依存先より高い信頼性は、依存を弱めない限り出せない。** 依存先の予算を計算し、届かないところは設計で直すか目標扱いにする（[dependencies.md](./dependencies.md)）。
8. **セキュリティ上の性質は SLO にしない。** 1 件でもインシデント（§7）。バジェットで相殺しない。
9. **期間は 28 日のローリング**（週の整数倍・暦月は使わない）。
10. **緩く始めて締める。** 実測が無い数値には〔仮〕を付け、校正（§8）で置き換える。

### 1.1 根拠の印

各数値に付ける。

| 印 | 意味 |
| --- | --- |
| 〔既〕 | 既存の正本（design・data-platform・roadmap 等）の目標を引き継いだ |
| 〔測〕 | 開発環境での実測を根拠にした（本番の実測ではない） |
| 〔業〕 | 業界の公開値（Google SRE・GitLab・Temporal・Cadence・Keycloak 等）を根拠にした |
| 〔設〕 | 実装の設定値（周期・タイムアウト）から下限が決まる |
| 〔仮〕 | 根拠の弱い仮置き |

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| SLI | 良い事象 ÷ 対象の事象 |
| SLO | SLI の目標値と期間（例: 28 日で 99.9%） |
| エラーバジェット | `1 − SLO`。28 日で 99.9% なら約 40 分、99.5% なら約 3.4 時間、99% なら約 6.7 時間、99.99% なら約 4 分 |
| burn rate | バジェットを消費する速さ。1 なら 28 日ちょうどで使い切る |
| 目標扱い（aspirational） | 計測と報告はするが、割っても §5 の対応（リリース停止）を取らない SLO。依存先の制約などで今は届かないことが分かっているもの |
| 最初に見える進捗 | チャットで、利用者の画面が初めて内容で変わるイベント（本文・思考・ツール呼び出し・計画） |
| 動作条件 | オンプレで SLO が成り立つ前提（構成・規模・負荷）。外れたら SLO は適用しない |

## 3. 段（Tier）とリクエストのクラス

### 3.1 段

| 段 | 扱い | 対象 |
| --- | --- | --- |
| **T1** | エラーバジェット＋呼び出し（page）＋チケット | 主要な流れの入口（API・チャット・検索・ワークフローの着手・取り込み） |
| **T2** | エラーバジェット＋チケットのみ | 重要だが、即時の呼び出しは要らないもの（定時実行・取消・管理系・連携） |
| **T3** | 監視指標（閾値でチケット・バジェットなし） | 原因の切り分け・容量・品質・コスト |

SLO の ID には段を併記する（例: `CHAT-3 (T1)`）。T1 は全体で 20 個以内に保つ。増やすときは、既存の T1 を T2 に下げられないかを先に検討する。

### 3.2 リクエストのクラス

API のリクエストは、ルート定義（`crates/api/src/server.rs` の `route_table()`）に付けたクラスで目標を決める。
GitLab の urgency と Google の request class の考え方による〔業〕。クラスの付いていないルートは CI で落とす（[measurement.md §2](./measurement.md#2-slo-の単一定義)）。

| クラス | 例 | 目標の所在 |
| --- | --- | --- |
| `interactive` | 一覧・詳細・小さな更新・共有・`POST /data/tables/{id}/query` 等の読取 | [platform.md §1](./platform.md#1-apiすべての流れの土台) API-1〜3 |
| `interactive_heavy` | `POST /search`・`POST /data/sql`・Office セッション作成など、数秒かかりうる対話 | API-1 と、各領域の個別 SLO |
| `long_running` | finalize・エクスポート・資料生成など（ヘッダまで 300s） | API-1 と API-4 |
| `streaming` | チャット・ワークフローの SSE・共同編集の WebSocket・data の SSE | 各領域の個別 SLO（接続の成功・最初のイベント） |
| `admin` | 組織管理・監査・プロビジョニング | API-1（目標は低め）・[platform.md §7](./platform.md#7-管理運用) |
| `no_slo` | ヘルスチェック・メトリクス・開発用 | 対象外 |

読取かどうかは HTTP メソッドで判定しない（検索・data の読取は POST）。

## 4. アラート

### 4.1 多窓の burn rate（T1・T2 に適用）

| 重さ | 条件 | 意味 | 適用 |
| --- | --- | --- | --- |
| 呼び出し | 1 時間と 5 分の両方で burn rate ≥ 14.4 | 1 時間でバジェットの 2% を消費 | T1 |
| 呼び出し | 6 時間と 30 分の両方で burn rate ≥ 6 | 6 時間でバジェットの 5% を消費 | T1 |
| チケット | 1 日と 2 時間の両方で burn rate ≥ 3 | 1 日でバジェットの 10% を消費 | T1・T2 |
| チケット | 3 日と 6 時間の両方で burn rate ≥ 1 | このままだと期間内に使い切る | T1・T2 |

- 短い窓（長い窓の 1/12）は、障害が収まった後に長い窓だけが鳴り続けるのを防ぐ。`for:`（継続時間）での遅延は使わない〔業〕。
- 同じ障害で複数の行が同時に鳴るので、まとめて 1 件にする。
- 可用性の目標が 99% 未満の SLO は、1 時間で 2% という条件が成り立たない（全停止でも届かない）。その SLO はチケットだけにする。

### 4.2 件数の少ない環境

1 時間に 10 件の環境では、1 件の失敗が 1 時間でバジェットの 1 割以上を使い、呼び出しが乱発する〔業〕。

- 呼び出しの条件に最低件数を付ける: 1 時間の窓で 100 件以上、6 時間の窓で 300 件以上。満たないときはチケットに落とす。失敗は SLI に必ず記録する（変えるのは呼び出しの経路だけ）。
- 件数の少ない流れ（オンプレ・夜間・定時実行）は、合成監視（[measurement.md §3](./measurement.md#3-合成監視とプローバ)）で事象を足す。合成監視の失敗は本物の失敗と同じに数える。
- 「処理が 0 件になった」アラートは、需要がある（投入がある）ことと組で出す。需要が無い 0 件で鳴らさない。

### 4.3 呼び出し以外の運用アラート

SLO の burn rate は、利用者に影響が出てから鳴る。早めに知るため、各領域の文書に「先行指標」を置く（キューの最古の待ち・スケジューラの生存・証明書の残り日数など）。
先行指標は T3 として扱い、呼び出すのは「このままだと数分で T1 を割る」と言えるものだけにする（例: スケジューラのリーダー不在・chat ワーカーの全停止）。

## 5. エラーバジェットの方針

Google SRE の例（Example Error Budget Policy）に沿う〔業〕。

1. **使い切ったら**: その SLO に関わる機能追加のリリースを止め、信頼性の修正を優先する。P0・セキュリティ修正は止めない。
   再開は、原因の修正がマージされ、直近 7 日の SLI が目標を上回ってから。止める・再開するの判断は human が行う。
2. **大きな障害**: 1 回の障害で 28 日のバジェットの 20% を超えて使ったら、ポストモーテムを書き、P0 の対策を 1 つ以上入れる。
   同じ種類の障害が四半期でバジェットの 20% を超えたら、次の四半期の計画に P0 として入れる。
3. **原因が外部のとき**（モデル提供元・クラウド基盤・外部 Web）: 記録はするがリリースは止めない。
   代わりに、依存を弱められたか（切り替え・キャッシュ・縮退）を振り返り、[dependencies.md](./dependencies.md) の予算を見直す。
4. **目標扱いの SLO**: 割っても 1〜3 の対応を取らない。四半期ごとに、目標扱いを外せるか（依存の手当てが入ったか）を見直す。
5. **計画メンテナンス**: 社内 SLO では数える（除外しない）。利用者には止まって見えるため。SLA を作るときに除外を検討する。
6. **リリースの関所**: カナリア（一部のテナント・レプリカ）で、旧版との比較と SLO の絶対値の両方を見て、悪化なら自動で戻す。
   モデル・プロンプト・検索設定の変更は、さらに評価ゲート（[ai-agents.md §7.1](./ai-agents.md#71-リリース前の評価ゲート)）を通す。
7. **争いになったら**: バジェットの計算や対応で意見が割れたら human が決める。

### 5.1 バジェットの内訳（SaaS の T1・99.9%）

28 日の 40 分を、あらかじめ次のように見込む（Microsoft の合成 SLO の例に倣う〔業〕）。

| 区分 | 見込み | 含むもの |
| --- | --- | --- |
| 依存先 | 15 分 | マネージドサービス・自前運用の部品（[dependencies.md §2](./dependencies.md#2-依存先の予算)） |
| 自分のコード・デプロイ | 15 分 | 不具合・リリース・移行 |
| 設定・運用作業 | 10 分 | 設定変更・証明書・DNS・手作業 |

28 日に 2 回の障害を見込むと、1 回あたり検知から復旧まで 10 分程度しか使えない。
したがって、検知は 2 分以内（1 分ごとの合成監視と 5 分窓の burn rate）、切り戻しは 5 分以内（ワンコマンドのロールバック）を運用の前提にする。

## 6. テナントの下限（SaaS）

全体の割合は、件数の少ないテナントの全停止を隠す（全体 99.99% でも 1 社が全滅していることがある）〔業〕。

- **下限 SLO**: 「28 日で対象の事象が 1,000 件以上あったテナントのうち **99% 以上**が、その SLO の目標を満たす」。
  適用する SLO は各領域の文書で指定する（API-1・CHAT-4・SRCH-1）。
- 件数が足りないテナントは「判定不能」として別に数え、合格扱いにしない。最悪の 1 社を SLO にしない（件数の少ないテナントで値が大きく揺れる）。
- 1 社でも API-1 の 28 日の値が 99% を下回ったら、個別にチケットにする。
- 集計は、テナント別の日次の件数（良・全）を集計テーブルに持って行う。`tenant_id` はメトリクスのラベルに付けない（[measurement.md §1](./measurement.md#1-計測の方針)）。

## 7. SLO の外に置くもの（インシデント扱い）

次は 1 件でもインシデントとして扱い、エラーバジェットで数えない。

- 権限の解除・削除の後に、その人へデータが返った（二段 authz の破れ）。引用・ツール結果・生成 UI のデータを含む
- pre-filter をすり抜けた結果が本番で見つかった（post-filter が止めても、防御の一段が壊れているので重大な不具合として扱う）
- 別テナントのデータが見えた・書けた（tenant_id の落ち）
- 監査ログの欠落・ハッシュチェーンの破れ（NFR-6）
- テナント消去の取りこぼし（NFR-10）
- サンドボックスからの脱出・egress 方針の違反・シークレットの流出
- テナントの方針で禁じた提供元・地域へデータが送られた（国外処理の同意なし・オンプレからクラウドへの切り替え等）
- 取消の後に、または必要な承認なしに、副作用のある操作が実行された
- 副作用のある操作が 2 回実行された（冪等性の破れ。ワークフローの effect_journal・定時実行の二重発火）
- 利用者の確定した編集が失われた（共同編集の保存漏れ）
- 実行ごと・テナントごとのコスト上限を超えて費用が発生した

## 8. 校正の手順

数値は次の順で実測に置き換える。

1. **計装**（#1349）: SLI を測れるようにする。
2. **負荷試験**: [dependencies.md §4](./dependencies.md#4-オンプレの動作条件) の基準構成ごとに、想定負荷で試験する。合格は「目標の処理量の 80% 以上・成功率 99% 以上・各 SLO の閾値」（GitLab の性能試験の基準に倣う〔業〕）。
3. **ベースライン**（アルファ運用の最初の 28 日）: SLI を測るだけにし、アラートはチケットのみ（呼び出しにしない）。
4. **目標の置き直し**: 実測から、可用性は有効数字 2 桁で切り下げ、レイテンシは 50ms 単位で切り上げる〔業〕。
   過去の障害やチケットと SLI の落ち込みが一致するかを確かめ、一致しない SLI は定義を見直す。
5. **呼び出しの有効化**: T1 の呼び出しを有効にし、印を〔測〕から「本番実測」に書き換える。

## 9. 統治

- **見直し**: 最初の 3 か月は毎月、その後は四半期ごと。目標を変えるときは文書を変え、理由（実測値）を残す。
- **持ち主**: 各 SLO の持ち主は GitHub の area ラベル（`area:chat` 等）の担当。バジェットを使った原因の領域に計上する。
- **報告**: 28 日ごとに、各 SLO の達成値・バジェットの残り・使った原因の上位を出す。修正の優先順位は「割った回数」で付ける（最悪値ではない）〔業〕。
- **SLA との関係**: 顧客に約束する SLA を作るときは、SLO より緩い値で別に定める。SLO をそのまま SLA にしない。
  SLO を大きく上回り続けるときは、利用者がそれを前提にし始めるので、目標を上げるか、意図的な停止の訓練を検討する〔業〕。
