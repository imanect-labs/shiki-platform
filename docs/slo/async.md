# SLO: ワークフロー・定時実行・イベント配送・ジョブキュー・文書の取り込み

原則・段・アラート・バジェットの方針は [README.md](./README.md)。数値の列は **SaaS ／ オンプレ**。

## 0. この領域の考え方

非同期の仕組みは、Temporal・Cadence・Step Functions・Airflow・GitLab（Sidekiq）・Google SRE のデータパイプラインの章に、共通する定石がある。SLO の形はこれに従った。

| 定石 | 中身 | 出典 |
| --- | --- | --- |
| **待ちと実行を分ける** | 「キューで待った時間（schedule-to-start）」と「実行にかかった時間」を別々に測る。全体の所要時間は SLO にしない | Temporal、Step Functions、GitLab |
| **待ちの持ち主で外す** | 再試行の待ち（backoff）・利用者自身が設けた同時実行数や流量の上限による待ち・人の承認待ち・タイマーで寝ている時間は、エンジンの SLI から外す | GitLab（外部依存のジョブを外す）、Airflow の Deadline Alerts |
| **再試行で救えたら良、ただし期限内に限る** | 論理的な 1 件を 1 回と数える。期限を過ぎて成功したものは遅延として悪、DLQ・破棄は悪 | OneUptime、EventBridge |
| **「来るはずだったもの」を外の台帳で数える** | 定時実行は cron の定義から予定を計算し、発火しなかった予定も悪として数える。取り込みは受け付けた件数と索引済みの件数を突き合わせる | Google の分散 cron、Spotify の配送監査 |
| **件数より最古の年齢を見る** | キューの滞留は件数ではなく、最も古いものの年齢で見る。件数が多くても年齢が若ければ忙しいだけ | AWS SQS、Pub/Sub、outbox の実務 |
| **静かなときのために合成の心拍を流す** | 件数の少ない経路は、ダミーの事象を通して最後まで届くかを見る。「処理 0 件」は需要と組で見る | Prometheus、Cadence のカナリア、Temporal |
| **正しさは独立したプローバで** | 既知の入力を流し、既知の出力が出るかを、作った仕組みと別の方法で確かめる | Google SRE の Example SLO Document |

## 1. ワークフロー

実行エンジンの設計は [workflow/engine.md](../workflow/engine.md)。ワーカーは ready の step を `FOR UPDATE SKIP LOCKED` で claim し（空振り 200ms）、スケジューラは単一リーダーが 5s ごとに回る〔設〕。

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| WF-1 | T1 | step が**着手可能になってから**実行開始まで 2s 以内の割合 | 99% ／ 99% | 〔業〕Cadence の配送 SLO 2s・Temporal の警告 p99 5s〔設〕空振り 200ms |
| WF-2 | T1 | 定時実行の予定のうち、予定時刻から 15s 以内 ／ 60s 以内に run が作られた割合 | 99% ／ 99.9% | 〔設〕tick 5s・時刻どおりの猶予 60s |
| WF-3 | T2 | イベントの確定から、それに反応した run が作られるまで 15s 以内の割合 | 99% ／ 99% | 〔設〕tick 5s〔仮〕 |
| WF-4 | T1 | **エンジン起因で**失敗しなかった run ÷ 終わった run | 99.9% ／ 99.9% | human 決定の水準 |
| WF-5 | T2 | 待ちの解除（タイマーの期限・待っていたイベントの到着）から 10s 以内に後続が動き出した割合 | 99.9% ／ 99.9% | 〔設〕tick 5s。Cadence はタイマーの遅れを独立した SLI にしている〔業〕 |
| WF-6 | T2 | 取消の要求から 30s 以内に run が取消確定になった割合 | 99% ／ 99% | 〔設〕猶予 10s＋tick 5s |
| WF-7 | T2 | ワーカーが落ちた step が 2 分以内に別のワーカーで再開した割合 | 99.9% ／ 99.9% | 〔設〕リース 30s＋tick 5s |
| WF-8 | T2 | 承認ノード: 承認依頼の作成から承認者への通知まで 1 分以内、決定から後続の開始まで 5s 以内の割合 | 99% ／ 99% | 〔仮〕実装時（承認ノードは計画中）に有効化 |

### 1.1 定義の細目

**WF-1（着手）**
- 起点の「着手可能」は `max(step が ready になった時刻, 再試行の予定時刻 next_retry_at)`。再試行の待ち（backoff）は外す。
- 次の待ちも外す: テナント・ワークフロー・ノード種別の同時実行の上限（tenant 64・workflow 16・node kind 8〔設〕）による順番待ち、流量制限（`rate_limited`）による待ち。
  どれも利用者の設定か、利用者自身の負荷による待ちで、エンジンの遅れではない（engine.md §8）。外すためには、上限で待たされたことを記録する必要がある（[measurement.md §4](./measurement.md#4-計測の現状と穴)）。
- 上限による待ちの時間は T3 で、テナント別に出す（利用者が上限を上げるかの判断材料）。

**WF-2（定時実行）**
- 分母は、cron の定義から計算した「来るはずだった予定」（有効なトリガのみ）。発火しなかった予定は 60s の側でも悪になる。
- `catchup: skip` で意図して捨てた予定（スケジューラが止まっていた間の穴）は、**悪として数える**。捨てたのは利用者の設定だが、穴を作ったのはスケジューラの停止だから。
- `max_parallel_runs` を超えて `on_trigger_overflow: skip` で作られなかった予定は対象外（利用者の設定）。`queue` で滞留したものは、run が作られた時刻で判定する。
- 同じ予定の二重発火は SLO ではなくインシデント（副作用の二重実行につながる・README §7）。UNIQUE 制約で防いでいる（engine.md §5.3）。

**WF-4（run の成功）**
- 失敗の理由（`fail_reason`）を次のように分ける。今は自由文に近いので、区分を足す（[measurement.md §4](./measurement.md#4-計測の現状と穴)）。

  | 区分 | 例 | WF-4 |
  | --- | --- | --- |
  | 成功 | 全 step が終わった | 良 |
  | 利用者・ワークフローの誤り | script の例外・入力の検証エラー・`permanent` を返したノード・利用者が設けた run のタイムアウト | 対象外 |
  | 外部の失敗 | `http.request` の相手の 5xx・タイムアウト（再試行を使い切った） | 対象外（T3 で見る） |
  | 委譲の失効 | 有効化した人の権限が無くなった（`delegation_invalid`） | 対象外（意図した fail-closed・T3 で見る） |
  | 取消 | 利用者・管理者による取消 | 対象外 |
  | エンジン起因 | 内部エラー・リースの喪失で再開できない・チェックポイントの破損・shiki の内部能力ノード（storage・data・rag）の失敗 | **悪** |

- 内部能力ノードの失敗をエンジン起因に入れるのは、そのノードが shiki の SLO で守られる部品を呼んでいるから。

**全体の所要時間は SLO にしない**
- run の所要時間はワークフローの中身と待ち（タイマー・承認）で決まる。業務の指標として T3 で出す（利用者が「いつもより遅い」に気づけるように、ワークフローごとの通常の所要時間と比べる）。

### 1.2 監視指標（T3）と先行指標

| 指標 | 見ること |
| --- | --- |
| **スケジューラのリーダーが不在**（`scheduler_lease` の期限切れが 30s 以上） | 定時実行・タイマー・取消・リース回収がすべて止まる。**呼び出し**にする先行指標 |
| 着手可能な step の最古の年齢（キュー別） | ワーカーが足りないか止まっている |
| ワーカーの生存数が 0 なのに、着手可能な step がある | 需要と組の「処理 0 件」 |
| 上限で待たされた時間（テナント・ワークフロー別） | 利用者の設定の見直し材料 |
| 外部の失敗・委譲の失効の率 | 外部 API の不調・権限の棚卸し漏れ |
| 再試行の率・DLQ | 再試行が増えたら、相手が小さすぎる・不調の兆候〔業〕 |
| 終わった run の GC の所要時間 | 1 バッチ 10.5s（生存 25 万 run）〔測〕から悪化していないか |
| **合成のカナリア**: 5 分ごとに、定時実行・step・タイマー・再試行を含む小さなワークフローを専用テナントで流す | 件数の少ない時間帯でも WF-1・WF-2・WF-5 に事象を足す。最後の成功から 15 分を超えたら呼び出す（デッドマンスイッチ） |

## 2. イベント配送（outbox → relay → コンシューマ）

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| EV-1 | T2 | イベントの確定から、各コンシューマ（ワークフロー・ミニアプリ）の受け取りまで 10s 以内の割合 | 99% ／ 99% | 〔仮〕 |
| EV-2 | T2 | 確定したイベントのうち、購読している全コンシューマが 1 時間以内に受け取った割合（日次の突き合わせ） | 99.99% ／ 99.99% | 〔業〕Spotify の配送監査 |

- EV-1 は再試行を含めて測る（EventBridge の方式〔業〕）。RAG 向けの配送は ING-1 の中で測る。
- 24 時間を超えて届いていないイベントはインシデントとして調べる（自動化が黙って動かなかったことになる）。
- **計測値の注意**: 開発環境の計測（2026-10-22）では、待ち無しの relay は p99 37〜62ms だったが、本番と同じ周期で 100 件/秒を流すと、ワークフロー・ミニアプリのコンシューマは p50 約 53s まで滞留した〔測〕。
  その後ワークフロー側の relay は 1 tick で最大 32×500 件に変わっている（RAG 側は 64 件／500ms のまま）。**変更後の再計測が無い**ので、EV-1 は仮置き。基準構成の負荷試験（README §8）で、毎秒何件まで EV-1 を満たすかを測り、[dependencies.md §4](./dependencies.md#4-オンプレの動作条件) の動作条件に書く。
- **T3**:
  - relay の遅れ（未配送の最古の outbox 行の年齢）。件数ではなく年齢で見る
  - コンシューマ別の遅れ（未受信の最古のイベントの年齢）。Burrow の考え方で、進んでいない（STALLED）・止まった（STOPPED）を判定する〔業〕
  - 重複配送の率（冪等キーで捨てた件数）は診断用
  - **心拍イベント**: 1 分ごとにダミーのイベントを出し、各コンシューマで受け取れたかを見る（静かなときの遅れの見逃しを防ぐ）

## 3. ジョブキュー（jobq）

jobq の各キューは、利用者の流れの SLO で守る。キュー自体は T3 の指標で見る。

| キュー | 守る SLO |
| --- | --- |
| `chat_generation` | CHAT-1・CHAT-8 |
| `rag_ingest` | ING-1・ING-2 |
| `data_bulk_import` | DATA-4 |
| `data_index_backfill`・`data_stats_analyze`・`data_field_key_migration`・`storage_version_optimize`・`workflow_gc` | JOB-1・JOB-2（T3） |

| ID | 段 | 指標 | 閾値 | 根拠 |
| --- | --- | --- | --- | --- |
| JOB-1 | T3 | キュー別の、着手可能なジョブの最古の年齢 | 対話系（`chat_generation`）30s、バッチ系 1 時間（通常の最大処理時間の 1.5 倍を目安に置き直す） | 〔業〕AWS の推奨アラーム |
| JOB-2 | T3 | DLQ（`job_queue_dead`）の件数と最古の年齢、キュー別の増加率 | 増え続けたら通知 | 〔業〕 |

- **Postgres の先行指標**: 最も古いトランザクションの年齢（5 分超で通知）と、`job_queue` の死行数。長いトランザクションが VACUUM を止めると、`SKIP LOCKED` の走査が遅くなり滞留が雪だるま式に増える〔業〕。
- jobq は成功したジョブの行を消すので、待ち時間は今の DB からは取れない（[measurement.md §4](./measurement.md#4-計測の現状と穴)）。claim の時点でメトリクスに出す。

## 5. 文書の取り込み（アップロード → 検索に出る）

アップロードの確定（finalize）で outbox に記録され、RAG の relay が `rag_ingest` に積み、コンシューマが解析（IW）→ チャンク化 → 埋め込み → Qdrant・Tantivy への登録を行う。
relay と consumer の待ちで、実処理の前に約 1 秒かかる〔設〕。解析の同時実行は 2 で、超えると 503 で押し返す〔設〕。

| ID | 段 | SLI | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| ING-1 | T1 | **小さい文書**（テキストを持つ 10 ページ以下・または 1MB 以下）: アップロードの確定から検索に出るまで 60s ／ 5 分以内の割合 | 95% ／ 99%（両方とも） | 〔仮〕 |
| ING-1L | T2 | **大きい文書・OCR が要る文書**: 同 15 分 ／ 60 分以内の割合 | 95% ／ 99%（両方とも） | 〔仮〕 |
| ING-2 | T1 | 受け付けた文書のうち、24 時間以内に索引済みになった割合 | 99.9% ／ 99.9% | 〔業〕パイプラインの網羅（coverage） |
| ING-3 | T2 | 正しさのプローバ: 既知の文書を 15 分ごとに上げ、権限のある利用者の既知の問い合わせで 5 分以内に見つかった割合 | 99.9% ／ 99.9% | 〔業〕Google SRE の正しさプローバ |
| ING-4 | T2 | 既存の文書の更新・改名・移動が、5 分以内に検索結果へ反映された割合 | 99% ／ 99% | 〔仮〕 |

### 5.1 定義の細目

- **大きさでバケットに分ける**（ページあたりで割らない）。小さい文書は固定の待ちが支配的で、割り算をすると目標がゆがむ〔業〕。ページ数は解析後に分かるので、判定は解析後のチャンクのページ数とファイルの大きさで行う。
- **ING-1・ING-2 の対象外**: 壊れた文書・暗号化された文書・非対応の形式（受付時に拒否するか、文書起因として DLQ に送ったもの）。これらの率は T3 で見る（急に増えたら解析器の不具合を疑う）。
- **ING-2 の突き合わせ**: アップロードの記録（`node_version`）・取り込みの状態（`rag_ingest_job`）・Qdrant の件数を日次で突き合わせ、受け付けたのに索引に無いものを数える（数える元はパイプラインの外に置く〔業〕）。
- **ING-3 は権限の確認を兼ねる**: 同じ文書が、**権限の無い利用者の問い合わせでは見つからない**ことも毎回確かめる。見つかったらインシデント（README §7）。
- **削除・権限の解除の反映は SLO にしない**: 直後の検索から消えることは不変条件（post-filter が保証する）。外れたらインシデント。
- 「古いデータより、間違ったデータのほうが悪い」〔業〕。取り込みが詰まったときは、途中までの結果を出すより止めて待つほうを選ぶ。

### 5.2 監視指標（T3）

| 指標 | 見ること |
| --- | --- |
| 段階（解析・OCR・埋め込み・登録）ごとの、最も古い文書の年齢 | どこで詰まっているか（Dataflow の system lag に相当〔業〕） |
| 解析器の押し返し（503 `parser_busy`）の率 | 解析の同時実行数 2 が足りているか |
| 文書起因の失敗（壊れた・非対応）の率 | 解析器の不具合・対応形式の要望 |
| 埋め込み・LLM の失敗率 | 原因側の指標 |
| 1 文書あたりの処理時間の分布（バケット別） | 容量計画（同時実行 2・1 件 1 秒なら全体で毎秒 2 文書が上限〔測〕） |
