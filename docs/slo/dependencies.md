# 依存先の予算・オンプレの動作条件・復旧目標

原則・段・バジェットの方針は [README.md](./README.md)。

## 1. 考え方

Google の "The Calculus of Service Availability"（Treynor ほか）と AWS・Microsoft の可用性設計の資料に従う〔業〕。

- **サービスは、重要な依存先すべての共通部分より高い可用性を出せない。** 直列の依存は掛け算になる（`A = A1 × A2 × …`）。
- **重要な依存先は、自分より 9 を 1 つ多く持つ**（99.9% のサービスなら依存先は 99.99%）。届かない依存先は、キャッシュ・縮退・fail-open で「弱い依存」に変えるか、目標を下げる。
- **同じ依存先は深さに関係なく 1 回だけ数える。** N 個の重要な依存先があれば、依存先に回す予算の 1/N ずつを配る。
- **SLA は下限であって実態ではない。** マネージドサービスの実際の可用性は SLA より高いことが多い。ただし同じゾーン・同じ地域・同じクォータを共有する依存先は同時に落ちる（独立ではない）。
- **自分の予算には、コード・設定・運用作業の分も要る**（README §5.1 の内訳）。

## 2. 依存先の予算

### 2.1 SaaS のマネージドサービス（公開 SLA・2026-11 時点）

| サービス | 構成 | 月間の SLA | shiki での使いみち |
| --- | --- | --- | --- |
| Cloud SQL | Enterprise・HA | 99.95% | Postgres（全ドメインの正本・jobq・outbox） |
| Cloud SQL | Enterprise Plus・HA | 99.99% | 同上（推奨） |
| Memorystore for Redis | Standard Tier | 99.9% | セッション・pub/sub・トークンバケット |
| Memorystore（Redis Cluster／Valkey） | 複数ゾーンの HA | 99.99% | 同上（推奨） |
| Cloud Storage | Standard・リージョン | 99.9% | ファイル本体（ドライブ・取り込み） |
| GKE | リージョンのコントロールプレーン | 99.95% | 実行基盤 |
| GKE Autopilot | 複数ゾーンの Pod | 99.9% | 実行基盤 |
| Vertex AI（Gemini のオンライン推論） | — | 99.5% | LLM（§3） |

出典: [Cloud SQL SLA](https://cloud.google.com/sql/sla)・[Memorystore SLA](https://cloud.google.com/memorystore/sla)・[Cloud Storage SLA](https://cloud.google.com/storage/sla)・[GKE SLA](https://cloud.google.com/kubernetes-engine/sla)・[Vertex AI 生成 AI の SLA](https://cloud.google.com/vertex-ai/generative-ai/sla)。

### 2.2 流れごとの重要な依存先

| 流れ | 重要な依存先（止まると失敗する） | SLA の積（今の想定構成） |
| --- | --- | --- |
| すべての API（セッション検証） | Postgres・Redis（セッションの保管先）・Keycloak（access token の更新・§2.3）・実行基盤 | 99.95 × 99.9 × 99.9 ≈ **99.75%**（Keycloak を除く） |
| ドライブ | 上記＋OpenFGA＋オブジェクトストア | 上記 × 99.9 ≈ **99.65%** |
| 検索 | 上記（オブジェクトストアを除く）＋Qdrant・Tantivy・ingestion-worker（埋め込み・rerank） | 自前運用の部品の目標次第 |
| チャット | すべての API の依存先＋LLM の提供元 | × 99.5% ≈ **99.25%**（切り替えなし） |

**結論**: SLA の下限を積むだけでは、99.9% の SLO を正当化できない。次のどちらかが要る。

1. 依存先の構成を一段上げる（human の判断が要る・費用が増える）:
   - Postgres を Cloud SQL Enterprise Plus の HA（99.99%）にする
   - Redis を複数ゾーンの HA（99.99%）にする。**Redis はセッションの保管先なので、止まると全 API が止まる**
   - 実行基盤を複数ゾーンに分散させる
2. 依存を弱める（§2.3）。

どちらも採らない場合は、API-1 の 99.9% を「実態の可用性が SLA より高いことを前提にした目標」と明記し、ベースラインの 28 日（README §8）で実態を確かめる。

### 2.3 依存を弱める候補

設計の判断が要るので、ここでは候補として挙げる（採るかは human が決める）。

| 依存先 | 今の結合 | 弱める案 | 引き換えになるもの |
| --- | --- | --- | --- |
| Keycloak | access token の期限前にセッションごとに更新する。一時的な失敗なら今の access token で続けるが、期限が切れたら 500（`middleware/session.rs`） | 更新が一時的に失敗している間、セッションを一定時間（例 30 分）延命する | 権限剥奪の反映が、その時間だけ遅れる（今は access token の寿命まで） |
| Redis | セッションの保管先（強い依存）。pub/sub は起床通知だけ（チャットの SSE は 700ms の保険 poll がある） | セッションを Postgres に退避する／Redis を HA 構成にする | Postgres の負荷・費用 |
| OpenFGA | 認可の判定ごとに問い合わせる | 判定の短期キャッシュ（古さの上限つき・拒否側は fail-closed のまま） | 権限変更の反映の遅れ（共有付与の 5 秒〔既〕の範囲内に収める） |
| Qdrant | 検索の必須部品 | Qdrant が落ちたら全文検索（Tantivy）だけで返し、結果に「縮退」の印を付ける | 検索の質（縮退した割合を T3 で出す） |
| LLM の提供元 | 1 つのモデルに固定 | 別の提供元・モデルへの切り替え（design §4.5） | 回答の質の変化（切り替えた割合を T3 で出す） |

### 2.4 自前運用の部品の目標

shiki が自分で動かす部品は、それを使う流れの SLO より 9 を 1 つ多く持たせる。部品の SLO は内部用（T2）で、利用者の流れの SLO で消費したバジェットの原因を特定するのに使う。

| 部品 | 目標（SaaS） | 主な前提 |
| --- | --- | --- |
| OpenFGA | 可用性 99.99%・check の 99% が 50ms 以内〔仮〕 | 2 レプリカ以上・Postgres の HA |
| Keycloak | 可用性 99.95%（ログインの流れ）・認証の 95% が 250ms 以内（Keycloak 公式の例〔業〕） | 2 レプリカ以上 |
| Qdrant | 可用性 99.95%（縮退がある場合）／99.99%（無い場合） | レプリカ 2 以上 |
| ingestion-worker（埋め込み・rerank の推論） | 可用性 99.95%（検索の問い合わせの埋め込み） | 検索用と取り込み用で資源を分ける（取り込みの山が検索を遅くしないように） |
| sandbox-orchestrator | SBX-1・SBX-2 に同じ | — |
| llm-gateway | LLM-1・LLM-2（in-process なので可用性は shiki-server と同じ） | — |

## 3. LLM の提供元

| 提供元 | SLA | 停止の定義・除外 |
| --- | --- | --- |
| Vertex AI（Gemini のオンライン推論） | 月 99.5%（提供期間の短いモデルは 95%） | サーバ側のエラー率が **5% を超える状態が 5 分以上続いた**時間だけを停止に数える。**クォータによるエラーは除外**。Provisioned Throughput では、5 分ごとの中央値の毎秒トークン数（Gemini 2.5 Flash で 80）を 99% の区間で満たす遅延の保証もある |
| Azure（Foundry Models） | 月 99.9% | 1 分ごとのエラー率から計算。プロビジョンドには毎秒トークン数の保証がある |

出典: [Vertex AI 生成 AI の SLA](https://cloud.google.com/vertex-ai/generative-ai/sla)・[Microsoft Online Services の SLA](https://www.microsoft.com/licensing/docs/view/Service-Level-Agreements-SLA-for-Online-Services)。

- **実態**: 公開ステータスに基づく研究では、OpenAI の API は平均約 5.6 日、Anthropic の API は約 5.2 日に 1 回障害があり、復旧時間の中央値は 1.2 時間・0.8 時間だった。**提供元をまたいだ障害の相関は観測されなかった**（[arXiv 2501.12469](https://arxiv.org/html/2501.12469v2)）。
- **切り替えの効果**: 独立な 2 つの提供元（各 99.5%）を切り替えれば、理屈の上では `1 − 0.005²` ≈ 99.997%。実際には次の理由でそこまで上がらない:
  - llm-gateway・ネットワーク・同じクラウド地域・同じクォータを共有している
  - **ストリームが始まった後の失敗は切り替えられない**（利用者には途中で止まって見える）
  - 別のモデルで答えるのは品質の劣化で、成功とは区別して数える（[ai-agents.md §3](./ai-agents.md#3-llmllm-gateway)）
- **提供元の 429 は提供元の SLA の対象外**（クォータのエラーは除外）。shiki が引き受けて、再送・切り替え・クォータの確保で吸収する。
- **オンプレのローカル推論**（vLLM）は、GPU のプールが 1 系統なら切り替え先が無い。チャットの完走（CHAT-5）は 99.5% の目標扱いとし、GPU を N+1 で冗長化した構成でだけ 99.9% にする。

## 4. オンプレの動作条件

オンプレの SLO は、Kubernetes の scalability SLO と同じく**動作条件つき**で定める〔業〕。条件を満たす構成・負荷でだけ SLO を適用し、外れたら適用しない。顧客の運用者と shiki の責任も分ける。

### 4.1 構成の条件

| 項目 | 条件（標準構成） | 未決の点 |
| --- | --- | --- |
| 配備 | Kubernetes（Task 8.8 の Helm） | Helm・マニフェストは未作成 |
| shiki-server | 2 レプリカ以上（別ノード） | — |
| Postgres | HA 構成（同期レプリカ＋自動フェイルオーバー） | 推奨する方式（CloudNativePG 等）が未決 |
| Redis | HA 構成（Sentinel 等） | 同上 |
| OpenFGA・Keycloak・Qdrant | 2 レプリカ以上 | — |
| GPU | 想定の同時実行数・モデル・文脈長から見積もる（Task 8.13 のサイジング表） | サイジング表が未作成 |
| ネットワーク | 利用者からの往復 50ms 以下 | — |

- **docker compose の一発起動**（小規模・NFR-4）は単一ノードで冗長性が無いので、可用性の SLO（API-1・SRCH-1・CHAT-4/5・WF-4・ING-2 等）を適用しない。レイテンシの SLO は、§4.2 の負荷の範囲で適用する。

### 4.2 負荷の条件

基準構成ごとに、負荷試験で「この負荷までなら SLO を満たす」を測り、ここに書く（README §8）。GitLab の reference architecture のように、利用者数あたりの毎秒リクエスト数で表す〔業〕。

| 項目 | 値 |
| --- | --- |
| 登録利用者数・同時接続 | 計測後に記入（オンプレの目安 1,000 接続〔既〕） |
| API の毎秒リクエスト数 | 計測後に記入 |
| チャットの同時 run 数 | 計測後に記入（GPU のサイジングと連動） |
| 1 日のアップロード文書数・ページ数 | 計測後に記入 |
| outbox の毎秒イベント数 | 計測後に記入（EV-1 を満たす上限） |
| テナント数・テーブル数・行数 | data-platform §1.2 のスケール目標〔既〕 |

### 4.3 責任の分担

| shiki が持つ | 顧客の運用者が持つ |
| --- | --- |
| 動作条件の中で SLO を満たすソフトウェア | ハードウェア・OS・ネットワーク・ストレージ・GPU |
| SLO の定義・Prometheus のルール・ダッシュボード・アラートの同梱（[measurement.md §2](./measurement.md#2-slo-の単一定義)） | アラートを受ける体制・エラーバジェットの運用 |
| バックアップ・復元の手順と道具 | 手順に従ったバックアップの実行・保管・復元の訓練 |
| アップグレードの手順 | アップグレードの実施 |

顧客は目標値を上書きできる（構成・業務に合わせて）。

## 5. 復旧目標（RPO / RTO）

SLO とは別に、NFR-9・Task 12.10 で宣言する値の初期案。復元リハーサル（OPS-3）で実証してから確定する。

| 経路 | RPO（失ってよい最大の時間） | RTO（復旧までの最大の時間） | 根拠 |
| --- | --- | --- | --- |
| SaaS: プール全体の PITR | 15 分 | 4 時間 | 〔仮〕GitLab Dedicated は RPO 4h・RTO 8h〔業〕 |
| SaaS: 単一テナントの論理復旧 | 24 時間（日次の論理エクスポート） | 1 営業日 | 〔仮〕 |
| オンプレ（標準構成） | 24 時間（日次バックアップ） | 8 時間 | 〔仮〕 |
| 共同編集（ノート・スライド） | 30 秒（保存の最長間隔） | — | 〔設〕 |

- RTO には Qdrant / Tantivy の再構築（Postgres からの再索引）を含める。検索できない状態は復旧していない。
- 整合スナップショットの対象は Postgres・オブジェクトストア・OpenFGA の 3 つ（design §4.12・PIT-38）。
- Microsoft の RE:04 にあるとおり、復旧の訓練をしていない流れに復旧目標を約束しない〔業〕。
