# SLO（サービスレベル目標）

| 項目 | 値 |
| --- | --- |
| 状態 | 案（数値はすべて仮置き。§8 の初回校正で実測に置き換える） |
| 位置づけ | **社内運用の目標**。顧客との契約（SLA）ではない（human 決定・2026-11-21・#1348） |
| 対象 | SaaS（フルプール）とオンプレ（標準構成＝k8s 本番構成） |
| 承認者 | human（プロダクト判断）。承認日・次回見直し日は承認時に記入する |
| 要件 | [requirements.md](./requirements.md) NFR-12 |

## 1. 決め方の原則

業界の定番（Google SRE の book / workbook）と、生成 AI・エージェント向けの実務資料（§10）に沿う。

1. **利用者が体感するものを、良い事象の割合で測る。** レイテンシも「300ms 以内に返した割合」と書く。
   こう書くとエラーバジェット（許される失敗の量 = `1 − SLO`）が数えられる。部品の指標（CPU 等）は原因の調査に使い、SLO にしない。
2. **SLO は少なく持つ。** エラーバジェットとアラートを持つ SLO は §3 の 7 つだけにする。
   「優先順位の議論で持ち出して勝てない SLO は持つ価値がない」。それ以外は**監視指標**（§5・閾値で見る、バジェットなし）に置く。
3. **期間は 28 日のローリング。** 週の整数倍にすると、期間に含まれる週末の数が毎回同じになる。暦月は使わない。
4. **緩く始めて締める。** 実測が無いうちは仮置きで始め、§8 の手順で実測に合わせる。100% は狙わない。
5. **AI の信頼性を 3 層に分ける。**

   | 層 | 例 | 扱い |
   | --- | --- | --- |
   | 運用 | 可用性・応答の開始・途中の停止 | SLO（全件を機械的に測れる） |
   | 構造 | エラー終了・出力上限での途中切れ・ツール呼び出しの破綻 | SLO（全件を機械的に判定できる） |
   | 意味 | 正しさ・根拠への忠実さ・安全性 | **SLO にしない**。評価ゲートと監視指標で扱う（§6） |

   意味の品質は、判定が遅れて届き、抜き取りで揺れ、判定器（LLM）自体が誤る。burn rate で予算を管理すると
   誤報と見逃しが増えるため、リリース前の評価ゲートと、最低件数付きの閾値監視に分ける。
6. **セキュリティ上の性質は SLO にしない。** 1 件でもインシデントとして扱う（§7）。バジェットで相殺しない。
7. **プール全体の割合だけで満足しない。** 全体の割合は、件数の少ないテナントの全停止を隠す。テナントの下限を併せて持つ（§4）。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| SLI | 良い事象 ÷ 対象の事象 |
| SLO | SLI の目標値と期間（例: 28 日で 99.9%） |
| エラーバジェット | `1 − SLO`。99.9%／28 日なら対象の事象の 0.1%（時間に直すと約 40 分） |
| burn rate | バジェットを消費する速さ。1 なら 28 日ちょうどで使い切る |
| 最初に見える進捗 | チャットで、送信後に利用者の画面が初めて変わるイベント（本文・思考・ツール呼び出しのいずれか） |

## 3. SLO（エラーバジェットとアラートを持つもの）

数値の列は **SaaS ／ オンプレ**。オンプレの compose 一発起動（NFR-4・単一ノード）は冗長性が無いので SLO-1 を置かない。
根拠の列: **仮** = 仮置き（実測なし）、**既** = 既存の正本の目標を引き継いだもの。

| ID | 利用者の体験 | SLI（良い事象 ÷ 対象） | 目標 SaaS ／ オンプレ | 根拠 |
| --- | --- | --- | --- | --- |
| SLO-1 | 画面と API が使える | 5xx 以外で返した応答 ÷ 対象の応答 | 99.9% ／ 99.9% | 仮（水準は human 決定） |
| SLO-2 | 画面の操作が速い | 読取（GET）が 300ms 以内 ／ 1s 以内の割合、更新が 1s 以内の割合 | 95% ／ 99% ／ 99%（両方とも） | 仮 |
| SLO-3 | チャットが応答を始める | 送信から最初に見える進捗まで 3s 以内 ／ 10s 以内の割合 | 95% ／ 99%（両方とも） | 仮 |
| SLO-4 | チャットが途中で止まらない | 途中で 30s を超えてイベントが途切れなかった run の割合 | 99% ／ 99% | 仮 |
| SLO-5 | チャットが最後まで答える | 構造的に正常に終わった run ÷ 終わった run | 99.5% ／ 99.5% | 仮・**目標扱い**（下記） |
| SLO-6 | 上げた文書が検索に出る | アップロード完了から検索に出るまで 5 分以内の割合（50 ページ以下） | 95% ／ 95% | 仮 |
| SLO-7 | ワークフローが動き出す | step が ready になってから running になるまで 5s 以内の割合 | 99% ／ 99% | 仮（SLI は [db-observability](./guides/db-observability.md) の候補） |

### 3.1 各 SLO の細目

**SLO-1・SLO-2（API）**
- 対象外: 4xx、429（レート制限は意図した拒否・Task 12.11）、ヘルスチェック、ストリーミング（SSE）。
  SLO-2 はさらに、ファイル本体の転送・エクスポート・LLM を同期で呼ぶ経路を除く。所要時間が入力の大きさで決まるため。
  対象外かどうかはルート定義に区分として持たせ、手書きの除外リストを作らない（§9）。
- 5xx は SLO-1 でだけ数え、SLO-2 では除く（二重に数えない）。
- 計画メンテナンスで止めた時間も数える。
- SaaS ではサーバ側の計測に、外からの定期チェック（ロードバランサの手前から叩く）を併用する。
  サーバが落ちるとサーバ側の計測は 0 件になり、失敗として数えられないため。

**SLO-3・SLO-4（チャットの応答）**
- 本文の初回トークン（TTFT）ではなく**最初に見える進捗**で測る。エージェントは検索やツール呼び出しの後に本文を書くので、
  本文の TTFT は正常でも長くなる。利用者が待たされていると感じるのは、画面が何も変わらない時間である。
  本文の TTFT はモデル別に監視指標で見る（§5）。
- 推論（reasoning）系のモデルも対象に含める。思考のイベントが流れていれば進捗として数える。
- SLO-4 は、平均のトークン間隔では途中の長い停止が隠れるため置く（[arXiv 2410.14257](https://arxiv.org/html/2410.14257v2)）。
  **ツールの実行中**（`ToolCall` から対応する `ToolResult` まで）は「実行中」の表示が出ているので停止に数えない。
  ツールそのものの遅さは監視指標で見る。
- イベントは `generation_event(run_id, seq)` に記録されているので、SSE の接続とは独立に run 単位で計算できる。

**SLO-5（チャットの完走）**
- 正常でない終わり方: エラー終了、出力上限（max_tokens）による途中切れ、ツール呼び出しの形式エラー等でループが打ち切られた。
- 対象外: 利用者による中止、予算超過、ポリシーによる拒否（いずれも意図した終わり方）。
- **モデル提供元の障害も数える**（利用者から見れば失敗）。llm-gateway の再試行や別モデルへの切り替えで救えた run は成功として数える。
  失敗には原因の属性（`provider`／`shiki`）と提供元・モデルを付け、どちらがバジェットを使ったかを分けて見る。
- **目標扱い（aspirational）**: 外部モデル提供元の可用性は公開値で 99.5% 前後であり、別モデルへの切り替えが無い限り
  99.5% は依存先と同じ水準になる。重要な依存先より高い信頼性は、依存を弱めない限り出せない。
  切り替え（design §4.5 のフォールバック）が本番で効くまでは、SLO-5 を割っても §4 の対応（リリース停止）は取らない。

**SLO-6（取り込み）**
- 鮮度で測る。成功率は監視指標（§5）。壊れた文書・非対応の形式は対象外。

**SLO-7（ワークフロー）**
- スケジュール実行の遅れ（予定時刻からの遅延）は監視指標（§5）。

## 4. エラーバジェットとテナントの下限

### 4.1 アラート（多窓の burn rate）

| 重さ | 条件 | 意味 |
| --- | --- | --- |
| 呼び出し | 1 時間と 5 分の両方で burn rate ≥ 14.4 | 1 時間でバジェットの 2% を消費 |
| 呼び出し | 6 時間と 30 分の両方で burn rate ≥ 6 | 6 時間でバジェットの 5% を消費 |
| チケット | 3 日と 6 時間の両方で burn rate ≥ 1 | このままだと期間内に使い切る |

- 短い窓を併せるのは、障害が収まった後に長い窓だけが鳴り続けるのを防ぐため。`for:`（継続時間）での遅延は使わない。
- **件数の少ない環境**（オンプレ・夜間）: 1 時間に 10 件の環境では 1 件の失敗が 1 時間でバジェットの 1 割以上を使い、呼び出しが乱発する。
  呼び出しの条件に最低件数（1 時間の窓で 100 件以上）を付け、満たないときは外からの定期チェックとチケットで見る。
  失敗は SLI には必ず記録する（変えるのは呼び出しの経路だけ）。

### 4.2 テナントの下限（SaaS）

SLO-1・SLO-3・SLO-5 に付帯させる。

> 28 日で対象の事象が 1,000 件以上あったテナントのうち **99% 以上**が、その SLO の目標を満たす。

- 件数が足りないテナントは「判定不能」として別に数え、合格扱いにしない。
- 最悪の 1 社を SLO にしない。件数の少ないテナントで値が大きく揺れるため。
- 1 社でも SLO-1 で 99% を下回ったらチケットにする（下限とは別の個別対応）。

### 4.3 バジェットを使い切ったら

- その SLO に関わる機能追加のリリースを止め、信頼性の修正を優先する（P0・セキュリティ修正は除く）。
  再開は、原因の修正がマージされ、直近 7 日の SLI が目標を上回ってから。止める・再開するの判断は human が行う。
- 1 回の障害で 28 日のバジェットの 20% を超えて使ったら、ポストモーテムを書き、P0 の対策を 1 つ以上入れる。
- 原因が外部（モデル提供元・クラウド基盤）のときは記録するがリリースは止めない。代わりに、
  依存を弱められたか（切り替え・キャッシュ・縮退）を振り返る。
- オンプレは顧客の運用者が見る。shiki はダッシュボードとアラートの定義を同梱し、目標値は顧客が上書きできる。

## 5. 監視指標（閾値で見る・バジェットなし）

SLO にはしないが、閾値を超えたらチケットにする。数値は正本側の値を引き継ぐか、仮置き。

| 対象 | 指標と閾値 | 出典 |
| --- | --- | --- |
| 権限付与の反映 | 共有の付与から検索結果に出るまで 5 秒以内 | [design-caveats.md](./design-caveats.md) PIT-3（結合テストで担保） |
| 構造化データ | グリッド初回描画 p95 < 300ms、1 ページ p95 < 100ms、同一操作 p95 のテナント間比 3 倍で準備・5 倍で実行 | [data-platform.md](./data-platform.md) §1.2・§12 |
| イベント配送 | 発生から購読先に届くまで p99 < 10s（平常は 35〜72ms。10s は詰まりの検知線） | [events/bench](./events/bench/results-2026-10-22.txt) |
| モデル別の応答 | 本文の TTFT・トークン間隔の分布、提供元別のエラー率 | 原因の切り分け用 |
| ツールの所要時間 | `doc_search` 等、ツール別の所要時間とエラー率 | 原因の切り分け用 |
| 取り込みの成功率 | 成功 ÷ 終わった文書 < 99% でチケット | 仮 |
| スケジュール実行 | 予定時刻からの遅延 | 閾値は後で決める |
| コスト | 正常に終わった run 1 件あたりのトークン量・費用 | 安いモデルで失敗が増えたら悪化として見える |

## 6. AI の品質（意味の層）

SLO にせず、**リリース前の評価ゲート**と**本番の監視指標**の二本で扱う。

### 6.1 リリース前の評価ゲート

- モデル・プロンプト・検索（RAG）の設定を変えるときは、固定した評価セットで採点し、指標ごとの閾値を下回れば出さない。
  指標を 1 つの合計点にまとめない（どの層が壊れたか分からなくなる）。
- 評価は自社で用意したコーパス（ヘルプの正本や合成データ）で行い、顧客のデータを使わない。
- 非決定的なので、同じ入力を k 回流し、全回成功した割合で一貫性も見る。
- 採点に LLM を使うときは、同じ判定器・同じ較正セットを使い続け、人の判定と定期的に突き合わせる。

### 6.2 本番の監視指標

- 利用者の 👎 の率とカテゴリ（`message_feedback`・design §4.12）、ヘルプ検索のキーワード縮退率など、**本文に触れない**メタデータで見る。
- 割合には最低件数（例: 7 日で 200 件）を付け、満たないときは判断しない。
- 本番の回答の本文を LLM で採点するのは、組織の設定でオンのときだけにする（AI 活用分析の用途分類と同じ扱い）。
  採点は llm-gateway を経由してテナント内で行い、外へ出すのはラベルと集計だけにする。ベンダーコンソールから本文に届く経路を作らない。

## 7. SLO の外に置くもの（インシデント扱い）

次は 1 件でもインシデントとして扱い、エラーバジェットで数えない。

- 権限の解除後に、解除された人へデータが返った（二段 authz の破れ）
- 別テナントのデータが見えた・書けた（tenant_id の落ち）
- 監査ログの欠落・ハッシュチェーンの破れ（NFR-6）
- テナント消去の取りこぼし（NFR-10）

### 7.1 復旧目標（RPO / RTO）

SLO とは別に、NFR-9・Task 12.10 で宣言する値の初期案。復元リハーサルで実証してから確定する。

| 経路 | RPO（失ってよい最大の時間） | RTO（復旧までの最大の時間） |
| --- | --- | --- |
| SaaS: プール全体の PITR | 15 分 | 4 時間 |
| SaaS: 単一テナントの論理復旧 | 24 時間（日次の論理エクスポート） | 1 営業日 |
| オンプレ（標準構成） | 24 時間（日次バックアップ） | 8 時間 |

- RTO には Qdrant / Tantivy の再構築（Postgres からの再索引）を含める。検索できない状態は復旧していない。

## 8. 校正と見直し

1. **初回の校正**（アルファ運用の最初の 28 日）: SLI を測るだけにし、アラートはチケットのみ（呼び出しにしない）。
   実測と過去の障害を照らし、「この値なら困らない」と「困った」の境目に目標を置き直す。結果で §3 の根拠の列を「実測」に書き換える。
2. 最初の 3 か月は毎月、その後は四半期ごとに見直す。目標を変えるときは本書を変え、理由（実測値）を残す。
3. 顧客に約束する SLA を作るときは、本書の SLO より緩い値で別に定める。

## 9. 計測

- 計装は OTel → Prometheus（[design.md](./design.md) §4.9）。SLI は Prometheus の recording rule として一度だけ定義し、
  Grafana・アラート・ベンダーコンソールの集約 SLO（Task 12.4）は同じ rule を読む。
- LLM の呼び出しは llm-gateway（単一チョークポイント）で計る。メトリクス名は OTel の GenAI 規約
  （`gen_ai.client.operation.duration`・`gen_ai.client.token.usage`・`gen_ai.client.operation.time_to_first_chunk`）に合わせる。
  規約はまだ安定版ではないので、採用した版を固定する。
- チャットの SLO-3〜5 は `generation_event` から run 単位で計算する。
- **系列数を抑える。** `tenant_id` はメトリクスのラベルに付けず、テナントの下限（§4.2）はログ・監査・集計テーブルから日次で出す。
  ルートはパスそのものではなく、ルート定義のテンプレート（`/threads/{id}`）と経路の区分（読取／更新／ストリーミング／長時間系）で付ける。
- ベンダーコンソールに出すのは集約値（割合・件数）だけで、顧客データの本文には触れない（design §4.12）。

### 9.1 計測の現状（2026-11-21 時点）

| SLO | 状態 | 足りないもの |
| --- | --- | --- |
| SLO-1・SLO-2 | 一部あり | `http.server.requests` / `http.server.duration` の属性が method と status だけ。ルートのテンプレートと経路の区分が無く、SSE の長時間接続が同じヒストグラムに混ざる。外からの定期チェックが無い |
| SLO-3〜5 | 素材のみ | `generation_event` に必要なイベントはあるが、SLI への集計が無い。失敗の原因属性も無い |
| SLO-6 | なし | アップロード完了から索引済みまでの所要時間 |
| SLO-7 | なし | ready→running の待ち時間 |
| テナントの下限 | なし | テナント別の日次集計 |
| 監視指標 | 一部あり | 構造化データは `data.query.*`（走査効率など）のみ。LLM の GenAI メトリクスは無い |

計装とアラートの実装は #1349 で進める。
