# ドキュメント / 実装 整合性チェック（Phase 3-b）

## なぜ委譲するか

正本ドキュメントは合計で数万トークンある。本体の予算では読み切れず、読み切れないまま
「たぶん変わっていない」と進めると、**正本が変わったことに気づかないまま陳腐化した記述を push する**。

この Phase は独立性ではなく**コンテキスト経済**のために委譲する。読むのはサブエージェント、
返るのは所見だけ。ただし**意図を渡さない規律は同じ**（渡すと「その意図に沿っているか」しか見なくなる）。

### 実際に起きた事故

`/pr` スキル自身の PR で、main 側の別 PR が **1 ファイルの行数上限を 500 → 1000 行に変更**していた。
スキルは 3 箇所で「500 行」と書いており、rebase するまで誰も気づかなかった。
正本（`CLAUDE.md` / `AGENTS.md`）を読んでいれば push 前に分かった。

教訓は 2 つ:

- **数値・コマンド名・パスをドキュメントに焼き込むと、正本が動いた時に嘘になる。**
  可能なら導出手順（「上限は `scripts/check-file-size.sh` の `MAX_LINES`」）を書く。
- **base が動いている前提で点検する。** 自分の diff だけ見ても、正本側の変更は見えない。

## 手順

### 1. 正本の一覧を導出する

**ここに正本のファイル名を書き写さない**（増減で嘘になる）。`CLAUDE.md` が正本の一覧を持っている:

```bash
sed -n '/正本ドキュメント/,/^## /p' CLAUDE.md | grep -oE '(docs|\.claude)/[A-Za-z0-9_/*-]+\.md'
```

`.claude/skills/*` も対象に含める（このスキル自身がドリフトする）。

### 2. base が動いていないか確認する

```bash
BASE=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null); BASE=${BASE:-origin/main}
git fetch origin --quiet
# 分岐後に正本 / 規約ファイルが動いていたら、その差分は必ず読む
git diff --stat "$(git merge-base "$BASE" HEAD)".."$BASE" -- CLAUDE.md AGENTS.md docs/ .claude/ scripts/
```

ここに差分があるなら、**自分の diff より先にそれを読む**。上の事故はこの確認を飛ばして起きた。

### 3. サブエージェントに委譲する

`subagent_type: "general-purpose"`。プロンプトに書いてよいのは、パス・観点・出力形式だけ。

```
リポジトリ: <ROOT>
この PR の diff: <SCRATCH>/pr-diff.patch
base 側で分岐後に変更された正本: <上の手順 2 の出力にあるファイル>

読むこと:
- <ROOT>/CLAUDE.md（正本ドキュメントの一覧が書かれている。そこに挙がっているものを読む）
- 上に挙げた base 側の変更分
- diff が触れている領域に対応する docs/roadmap/phase-*.md

観点: 次の 2 方向の食い違いを探す。

(a) diff → ドキュメント
    この diff によって、正本の記述が事実と食い違うようになっていないか。
    コマンド名・ポート・env 名・バイナリ名・スクリプト名・エンドポイント・しきい値・
    ファイル構成・relation / スコープ / ツール名の語彙。

(b) ドキュメント → diff
    base 側で正本が変わった結果、この PR の中の記述（コード内コメント・
    .claude/skills/* を含む）が既に古くなっていないか。
    特に、数値・コマンド・パスをそのまま書き写している箇所。

さらに:
- roadmap のフェーズ完了条件を、この diff が満たしているのに roadmap が未更新でないか。
- ドキュメントに書かれた不変条件・制約と実装が乖離していないか。

各所見には「どのファイルの何行目が、何と食い違うか」を必ず書くこと。
推測で書かない。実際に両方を読んで確認したものだけを出す。

出力は次の形式のリストのみ。前置き・要約は書かない。所見が無ければ「所見なし」とだけ返す。

- doc: <パス>:<行>
  code: <パス>:<行>  （ドキュメント側だけの問題なら "-"）
  claim: <何がどう食い違うか 1 文で>
  kind: fact | design      （fact=コマンド名/ポート/数値などの明白な事実差、design=設計判断・要件・優先順位・relation schema・トレイト境界）
  fix: <どう直すべきかの案を 1 文で>

制約:
- スタイルの好み・表現の好みは出さない。
- 「書いた方がよい」だけの提案は出さない。食い違いだけを出す。
- ファイルは変更しない。
- 最大 10 件。
```

### 4. 所見に対応する

**判断と編集は自分でやる。** サブエージェントに直させない（正本の書き換えは影響が広い）。

- `kind: fact` → この PR 内で直す。PR 本文の「## ドキュメント整合」に書く。
- `kind: design` → **勝手に直さない。** `AskUserQuestion` で human に確認する。
  どのドキュメントをどう直すか具体案を添える。CLAUDE.md は
  「設計の誤りや実装との乖離がある場合は human に修正を提案する」と定めている。
- roadmap のフェーズ完了条件を満たしたなら、roadmap / issue の更新もこの PR に含める。
- 所見が無ければ何もしない。PR 本文には「N/A」と書く。

## 回す頻度

- **PR 作成前に 1 回**。
- Phase 6 で設計に触る修正を入れたら、その差分に対してもう 1 回。
- base を rebase して正本が動いたら、もう 1 回（手順 2 に差分が出るはず）。
