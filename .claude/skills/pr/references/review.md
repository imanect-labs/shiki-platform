# 独立エージェントレビュー（コンテキスト非共有）

## なぜやるか

自分は「何を作ろうとしたか」を知っている。だから diff を**意図通りに**読んでしまい、意図と実装のズレ・書いていない前提・見落とした分岐が見えない。AI レビュアー（CodeRabbit / Codex）が PR 後に指摘する内容の相当部分は、この盲点に由来する。

対策は、**会話文脈を一切持たないサブエージェント**に diff だけを渡すこと。サブエージェントはこのセッションの履歴を継承しないので、プロンプトに書いたものだけが情報になる。したがって**プロンプトに意図を書いた時点で独立性は失われる**。

このスキルでは Agent ツールの使用が明示的に要求されている（通常セッションの「ユーザが要求しない限り Agent を呼ばない」制約の対象外）。

## 手順

### 1. diff をファイルに落とす

プロンプトに diff を貼ると長い上に、説明を書き足したくなる。ファイルパスだけ渡す。

```bash
# base は必ず remote-tracking ref（origin/...）にする。ローカルの main はしばしば古く、
# `main...HEAD` は無関係な数千ファイルを差分に含めてしまう（実測 2427 件 vs 1 件）。
BASE=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null); BASE=${BASE:-origin/main}
# スタック PR なら BASE は親ブランチ（origin/<親ブランチ名>）
git diff "$BASE"...HEAD > "$SCRATCH/pr-diff.patch"
git diff --stat "$BASE"...HEAD    # 件数がおかしければ base が間違っている
```

`$SCRATCH` はセッションのスクラッチパッドディレクトリ。

### 2. finder を並列起動する

**4 観点を 1 メッセージで同時に投げる**（`subagent_type: "general-purpose"`・`model: "opus"`）。順に投げると直列化して遅い。

4 体とも完了通知が返るまで待ってから次へ進む。**結果を予測して書かない**（まだ返っていない finder の所見を推測で埋めない）。ユーザに途中経過を聞かれたら「まだ実行中」と答える。

プロンプトに書いてよいもの:

- diff ファイルの絶対パス
- リポジトリのルートパス
- 読むべき正本ドキュメントのパス
- 観点（レンズ）
- 出力形式
- 「推測で書くな」の制約

**プロンプトに書いてはいけないもの:**

- 変更の目的・背景・issue の内容
- 自分がなぜその設計にしたかの理由
- 「〜は意図的です」「〜は別 PR で対応します」といった先回りの弁明
- 「特に〜を見てほしい」という誘導（見てほしい所以外が見られなくなる）

### 共通の末尾（全 finder に付ける）

```
出力は次の形式のリストのみ。前置き・要約・励ましは書かない。所見が無ければ「所見なし」とだけ返す。

- file: <リポジトリ相対パス>:<行>
  claim: <欠陥の主張を 1 文で>
  failure: <実際に失敗する入力・状態 → 何が起きるか。具体的に>
  confidence: high | medium | low

制約:
- 実際に失敗する入力・状態を書けないものは出さない。「〜かもしれない」は出さない。
- スタイルの好み・命名の好み・「テストを追加すべき」だけの指摘は出さない。
- diff に含まれない既存コードの問題は、diff がそれを踏むことで壊れる場合のみ出す。
- 主張の裏を取るためにリポジトリ内のファイルを読んでよい。ファイルは変更しない。
- 最大 6 件。重要度の高い順。
```

### finder 1: 不変条件・認可

```
リポジトリ: <ROOT>
レビュー対象の diff: <SCRATCH>/pr-diff.patch

先に読むこと:
- <ROOT>/CLAUDE.md の「必ず守る不変条件」節
- <ROOT>/.claude/skills/architecture-invariants/SKILL.md
- <ROOT>/docs/design.md の §1・§4・§5
- <ROOT>/docs/design-caveats.md

観点: この diff が、次のいずれかを破っていないか。
- 単一チョークポイント（ストレージ=StorageService / 認可=OpenFGA クライアント / LLM=llm-gateway）を迂回していないか。個別ハンドラに権限チェックを散らしていないか。
- アンビエント権限。全データアクセスが AuthContext { principal, org, tenant_id } 経由か。tenant_id による隔離境界を壊していないか。
- 二段 authz。RAG・構造化データで pre-filter と post-filter の両方が効いているか。実効権限 = スコープ ∩ ユーザー ReBAC になっているか。
- トレイト境界。cloud/onprem 差が ObjectStore/VectorStore/LlmProvider/Sandbox/DocumentParser/EmbeddingProvider の外に漏れていないか。
- codegen が正。手書きの型・認可語彙（relation / スコープ / ツール名）を足していないか。
- confused-deputy、authz バイパス、サンドボックス由来入力の信頼、監査記録の欠落。

<共通の末尾>
```

### finder 2: パフォーマンス

```
リポジトリ: <ROOT>
レビュー対象の diff: <SCRATCH>/pr-diff.patch

先に読むこと:
- <ROOT>/.claude/skills/pr/references/perf.md の「A. 静的観点」

観点: perf.md の A に列挙された劣化パターンが、この diff に含まれていないか。
特に、全件取得→メモリでフィルタ、N+1 クエリ、N+1 の認可チェック、
新規の WHERE / ORDER BY 条件に対応するインデックスの欠落、直列 await、
無制限の並列度、ループ内の大きな clone、SSE のバッファリング。

インデックスの有無は <ROOT> の migrations を実際に読んで確認すること。

<共通の末尾>
```

### finder 3: ドキュメント / 実装 整合

```
リポジトリ: <ROOT>
レビュー対象の diff: <SCRATCH>/pr-diff.patch

先に読むこと（正本）:
- <ROOT>/CLAUDE.md
- <ROOT>/docs/design.md
- <ROOT>/docs/requirements.md
- <ROOT>/docs/roadmap.md と <ROOT>/docs/roadmap/phase-*.md のうち関連するもの
- <ROOT>/docs/miniapp-platform.md（ミニアプリ / ワークフロー / skill / シークレットに触れる場合）

観点: この diff によって、正本ドキュメントの記述が事実と食い違わなくなっているか。
- コマンド名・ポート・env 名・バイナリ名・スクリプト名・エンドポイントの不一致。
- 新規/変更した API・relation・スコープ・ツール名が、requirements / design の語彙や codegen の単一定義と不整合。
- roadmap のフェーズ・依存・完了条件と、この diff の実装範囲のズレ。
- ドキュメントに書かれた不変条件・制約と実装の乖離。

各所見には「どのドキュメントの何行目が、diff のどこと食い違うか」を必ず書くこと。

<共通の末尾>
```

### finder 4: 正確性・エッジケース

```
リポジトリ: <ROOT>
レビュー対象の diff: <SCRATCH>/pr-diff.patch

観点: この diff にバグがないか。
- エラー処理: unwrap / expect / panic、fallible な呼び出しの `let _ =` 握り潰し、
  エラーの握りつぶしや、失敗しても成功として返る経路。
- 境界: 空コレクション、単一要素、None / NULL、0 件、上限超過、長さ 0 の文字列。
- 並行性: 競合、TOCTOU、リトライ時の二重適用、部分適用（トランザクション境界の外での副作用）。
- 状態遷移: 途中で落ちた時に不整合な状態が残らないか。冪等性。
- 型の不一致: Rust 側と TS 側、DB のカラム制約（NOT NULL / 外部キー）と挿入値。

<共通の末尾>
```

### 3. 敵対検証

finder の所見をそのまま信じない。**別のサブエージェントに反証を試みさせる。**

`confidence: high` と `medium` の所見を検証する。`low` は捨ててよいが、**認可・テナント隔離・監査・サンドボックス境界に関わるものは confidence に関わらず必ず検証にかける**。所見が多い時は重要度上位 8 件までに絞り、絞ったことを報告に明記する。

各所見について（これも並列で投げる）:

```
リポジトリ: <ROOT>
diff: <SCRATCH>/pr-diff.patch

次の指摘を「反証」せよ。指摘が正しいと証明するのではなく、間違っている根拠を探す。

  file: <path>:<line>
  claim: <claim>
  failure: <failure>

実際にコードを読んで確認すること。次のいずれかなら REFUTED:
- 指摘された経路が到達不能、または呼び出し元で既にガードされている。
- 指摘が前提とする条件が、型・DB 制約・上位のチェックで成立しない。
- 主張されている失敗が実際には起きない（別の挙動になる）。
- 既存の他の箇所で同じパターンが意図的に使われており、この diff 固有の欠陥ではない。

判断がつかない場合は REFUTED を既定とする（偽陽性を通すより取りこぼす方がマシ）。
**ただし、認可・テナント隔離・監査・サンドボックス境界に関わる指摘は例外**。反証しきれなければ
REFUTED ではなく `UNRESOLVED` を返すこと（捨てずに human へ上げるため）。

出力は次の 2 行のみ:
verdict: CONFIRMED | REFUTED | UNRESOLVED
reason: <1〜2 文の根拠。読んだファイルと行を含める>
```

### 4. 生き残った所見に対応する

- CONFIRMED は着手する。
- **`UNRESOLVED`（認可・テナント隔離・監査・サンドボックス境界で反証しきれなかったもの）は捨てない。**
  自分で判断せず、PR 本文の「## 独立レビュー」に明記したうえで `AskUserQuestion` で human に上げる。
  CLAUDE.md は「判断に迷ったら必ず human に相談」、relation schema・トレイト境界は人が握る領域と定めている。
  **敵対検証の目的は偽陽性を減らすことであって、セキュリティ所見を人の目に触れさせずに消すことではない。**
- `confidence: low` を検証前に捨てる足切りも、上記の領域には適用しない（低確信でも必ず検証にかける）。
- 直したら Phase 1 の該当ゲートを再実行する。UI が変わったら Phase 2 をやり直す。
- CONFIRMED でも対応しない判断をしたなら、理由を PR 本文に書く。
- PR 本文の「## 独立レビュー」に、生き残った所見と対応を 1 行ずつ書く。所見ゼロなら「指摘なし」。

## 回す頻度

- **PR 作成前に 1 回**（push 前に直せる方が、bot レビュー往復より安い）。
- Phase 6 のレビュー解消で**設計に触る修正**を入れたら、その差分に対してもう 1 回。
- 誤字修正・コメント追加のような機械的な修正では回さない。

## 期待しないこと

このレビューは CodeRabbit / Codex の代わりにはならない（Phase 6 は必ず実施する）。役割は違う:

- **独立エージェントレビュー**: このプロジェクト固有の不変条件・正本ドキュメント・パフォーマンス規約に照らす。push 前に回せる。
- **CodeRabbit / Codex**: 汎用の欠陥検出。プロジェクト固有の語彙は知らないが、リポジトリ全体の文脈と過去の PR を見ている。

# bot 指摘の独立判定（Phase 6）

## いつ使うか

**「却下する」と判断した bot 指摘だけ**にかける。採用する指摘には不要（直すのだから判定が要らない）。

自分の実装に対する指摘の妥当性を自分で判定すると、庇う方向に倒れる。「これは誤検知」「これはスコープ外」は
**都合の良い結論**なので、独立した目を通す。逆に「直す」は都合の悪い結論なので、バイアスの心配が無い。

指摘が本当に誤検知であることを示せるなら、その根拠はスレッドへの返信にそのまま使える
（`review-status.sh` は返信の有無ではなく指摘の残存を見るため、根拠は人と bot の両方に向けて書く）。

## プロンプト

`subagent_type: "general-purpose"`・`model: "opus"`。却下したい指摘ごとに 1 体、並列で投げる。

```
リポジトリ: <ROOT>

次はコードレビュー bot がこの変更に対して出した指摘である。この指摘が妥当かどうかを、
実際にコードを読んで判定せよ。

対象ファイル: <path>:<line>

指摘（原文）:
---
<bot コメントの本文をそのまま貼る>
---

判定基準:
- VALID   … 指摘のとおりの問題が実在する。失敗する入力・状態を示せる。
- INVALID … 実在しない。次のいずれかが言える場合:
            - 指摘された経路が到達不能、または呼び出し元で既にガードされている
            - 前提とする条件が型・DB 制約・上位のチェックで成立しない
            - 主張されている失敗が実際には起きない（別の挙動になる）
- UNCERTAIN … 読んでも決められない。

出力は次の 3 行のみ:
verdict: VALID | INVALID | UNCERTAIN
reason: <1〜2 文。読んだファイルと行番号を必ず含める>
evidence: <INVALID なら、そう言える根拠のコード位置。VALID なら失敗する具体的な入力・状態>

制約:
- 推測で判定しない。ファイルを実際に読むこと。
- 「どちらとも言える」は UNCERTAIN にする。無理に断定しない。
- ファイルは変更しない。
```

**プロンプトに「自分はこう思うので却下したい」と書かない。** 書いた時点で判定が引きずられ、
独立判定の意味が無くなる。渡すのは指摘の原文とファイルパスだけ。

## 判定の扱い

- `VALID` → **自分の却下判断が間違っている。** 直す。
- `INVALID` → 却下してよい。`evidence` をそのまま根拠にしてスレッドへ返信する。
- `UNCERTAIN` → 却下しない。直すか、human に上げる。判断が付かないものを黙って落とさない。

判定が bot の指摘と割れた（`INVALID` だが bot が強く主張している、複数の bot が同じ指摘をしている）場合は、
自分で決めず human に上げる。

## 反論する時は実測を添える

bot の指摘が事実誤認（「この API は存在しない」「このフィールドは無い」等）なら、
**実際の出力を貼って反論する**。過去に `fields.elapsed` の有無で反論した際、実 JSON を貼ったことで
議論が 1 往復で終わっている。ただし**指摘の結論まで無効になるとは限らない**
（この例では前提は誤りだったが「単位が混在してソートが壊れる」という結論は正しく、修正が必要だった）。
**前提の誤りと結論の誤りを分けて評価すること。**
